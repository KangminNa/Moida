# Moida 서버 브라우저

로그인된 브라우저로 하는 일(탭 읽기, 브라우저 에이전트: 사이트 일 · 둘러보기 · 결재된 클릭)을 이 문서 하나에 모은다.
결정의 이유는 [기획서](기획서.md) 결정 기록(2026-11-08 · 2026-11-14), 2차의 목표는 [서브 나](서브나.md) 7장, 기능 패키지의 틀은 [객체설계](객체설계.md) 12장, 배포 순서는 [README](../README.md) 6장.

## 1. 하는 일

| 일 | 흐름 | AI | 남는 것 |
|---|---|---|---|
| 탭 읽기 | 관리자가 주소를 맡긴다 → 러너가 탭으로 열어 제목과 보이는 글자만 읽고 닫는다 | 없음 | `browser_tabs.reads` |
| 사이트 일 | 관리자(또는 대표의 위임)가 사이트에 일을 맡긴다 → 서버 러너의 AI가 로그인된 프로필로 양식을 채우고 마지막 버튼 앞에서 멈춘다 → 러너가 버튼을 붙잡아 결재를 올린다 → 승인되면 러너가 같은 버튼인지 보고 누른다 | 서버 러너의 구독 CLI(Claude · Codex) + Playwright MCP | 작업 · 결재 · `clicks` · `shots` |
| 둘러보기 | 대상 없이 맡긴다 → 일마다 새 빈 창(로그인 없음)으로 공개 사이트를 조사한다. 아무것도 제출하지 않는다 | 같음 | 작업(결과 글) · `shots` |
| 요청 기록 → API 도구 | 사이트 일 동안 러너가 그 사이트로 가는 XHR · fetch의 모양(값 없음)을 모은다 → 사이트에 남긴다 → 처음 읽을 만한 API가 생기면 그 기록으로 화면 대신 API를 부르는 읽기 사이트 도구를 굳힌다 (2026-11-20, B2 · B3) | 기록은 없음, 굳히기는 서버 러너의 Claude | `endpoints` · 사이트 도구 |
| 로그인 필요 | 사이트 일이나 둘러보기가 로그인 화면을 만나면 러너가 "로그인 필요" 결재를 올린다 (둘러보기면 그 출처로 사이트를 만든다, 등록 없이 2026-11-19) → 관리자가 콘솔 화면에서 로그인하고 "로그인했어요" → 같은 작업이 그 사이트의 일로 이어진다 | 없음 | 결재 · `sites.login_needed_at` · `shots` |

## 2. 원칙

- **AI는 러너에서만 브라우저를 움직인다.** 서버 본체에는 AI가 없다 (원칙 6). 서버는 관리자가 콘솔에서 화면을 보고 누르는 중계와 사이트 세션 지우기로만 브라우저에 붙는다 (3장).
- **마지막 버튼은 결재 뒤에 믿는 코드가 누른다 (원칙 7, 2026-11-14).** AI는 제출 · 결제 · 게시 버튼 앞에서 멈추고 `browser-stop.json`을 남긴다. 결재는 AI가 아니라 러너(AI 없음)가 그 버튼의 지문과 화면을 붙잡아 올린다. 승인되면 붙잡은 러너가 같은 탭 · 같은 주소 · 같은 지문 · 가장 위 요소인지 다시 보고, 같을 때만 실제 마우스 이벤트로 누른다. 다르면 누르지 않고 관리자가 콘솔 화면에서 직접 한다. 많아야 한 번 누른다.
  누르기 전 내용 확인 (2026-11-24): AI가 `check`에 받는 사람 · 금액 · 제목 같은 화면의 글자를 적으면, 러너가 붙잡을 때와 누르기 직전에 그 글자가 화면(보이는 글 · 칸의 값)에 있는지도 본다. 없으면 붙잡지 않거나 누르지 않는다. 숫자는 숫자의 가운데와 맞추지 않는다 ("5,000원"은 "15,000원"에 맞지 않음). 승인 카드에 "확인한 내용"으로 보인다.
- **브라우저를 쓰는 에이전트도 비공개를 읽는다 (2026-11-21, 사용자 결정).** 팀을 없애고 모든 에이전트가 같은 권한(비공개 읽기 · 초안 · 브라우저 · 코드 · 만들기)을 갖는다. 예전에는 `browse`를 `read_all` · `write`와 함께 주지 못했고 비공개를 읽은 대표는 브라우저 일을 맡기지 못했다. 남은 위험: 비공개를 읽은 AI가 악성 페이지를 열면 주소나 입력으로 정보가 나갈 수 있다. 그래서 바깥을 바꾸는 클릭(제출 · 결제 · 게시)은 그대로 승인 뒤 러너가 누르고(아래), 둘러보기는 내부망을 막는다. 맡기기는 대표만 한다 (`DelegationPolicy`).
- **둘러보기는 로그인된 프로필을 건드리지 않는다.** 일마다 새 빈 컨텍스트(`--isolated`)라 쿠키가 없고, MCP가 끝나면 사라진다. 이 서버 · 내부망 · 메타데이터 주소는 러너의 프록시(`ExploreProxy`)가 막는다.
- **CDP는 서버 밖으로 열지 않는다. 화면은 관리자 확인 뒤에만 넘긴다.** 조종 중계(9223)는 서버와 브라우저만 붙는 망에 있고, 콘솔 화면 API는 관리자만 부른다. 밖으로 여는 포트 · 비밀번호가 없다 (neko의 실시간 영상은 2026-11-14에 지웠다).
- **브라우저 작업은 서버 러너만 받는다.** 내 컴퓨터 러너는 탭 읽기만 한다 (평소 쓰는 계정에 가까운 브라우저를 AI에게 맡기지 않는다).
- **비밀번호는 저장하지 않는다.** 관리자가 콘솔 화면에서 로그인하고(2단계 인증 포함) 브라우저는 로그인 상태만 기억한다. 브라우저의 비밀번호 저장은 정책으로 꺼져 있다.

## 3. 구성

```
관리자 브라우저 ─https─ 앞단 프록시 ─┬─ 웹 · 콘솔 (운영 › 브라우저: 화면 그림 · 클릭 · 입력, 세션 지우기, 결재 카드)
                                     └─ Moida 서버 (/api · /mcp)

Moida 서버 ── 전용 망(browser) ── 조종 중계 9223 ─┐   (콘솔 화면 · 세션 지우기: 관리자만)
서버 러너 ──MCP──▶ Moida 서버                     │
   │ CDP 127.0.0.1:9222 (브라우저와 같은 네트워크) ▼
   │                    브라우저 컨테이너 (Xorg + openbox + Chromium, 로그인 프로필 볼륨)
   ├─ Playwright MCP (사이트 일): 기본 컨텍스트, 허용 출처만 ──▶ 등록한 사이트
   ├─ Playwright MCP (둘러보기): 새 빈 컨텍스트 ─ ExploreProxy(127.0.0.1) ─▶ 공개 사이트 (내부 주소 막힘)
   └─ ClickRunner: 승인된 클릭을 CDP로 다시 확인하고 누른다
```

- 서버 브라우저는 선택 구성 `docker-compose.browser.yml`이다. 켜면 서버 러너가 브라우저의 네트워크를 함께 쓴다(`network_mode: service:browser`). 러너에게 브라우저는 127.0.0.1이라 Chrome의 Host 검사를 중계 없이 지나고, CDP가 컨테이너 밖으로 나가지 않는다.
- 이미지는 neko 3.2.0(amd64 · arm64, digest 고정)의 화면과 Chromium에 실행 옵션(`browser/chromium.conf`) · 정책(`browser/policies.json`) · 조종 중계(`browser/cdp-relay.py`)를 더한다. **neko 서버(영상 · 원격 입력 · 비밀번호)는 끈다** (supervisord `autostart=false`). 화면 크기는 neko가 아니라 Chromium 창(`--window-size=1280,720`, openbox 최대화 끔)으로 정한다. Chromium 로그는 치명적인 것만(`--log-level=3`), 10MB × 2. Chromium은 `moida-chromium`(이미지 안에서 만든 스크립트)으로 띄워 시작 전에 남은 프로필 잠금(`Singleton*`)을 지운다 (2026-11-18): 프로필은 볼륨이라 컨테이너를 다시 만들면 호스트 이름이 바뀌고, 잠금이 남아 있으면 Chrome이 "다른 컴퓨터가 쓰는 프로필"로 보고 조종 포트를 열지 않는다 (콘솔 화면의 `fetch failed`).
- **콘솔 화면 (2026-11-14):** 서버(`browser-tabs`의 `BrowserScreenGateway`)가 전용 망으로 조종 중계에 붙어 화면을 JPEG로 받고 클릭 · 스크롤 · 글자 · 키 · 이동 · 뒤로 · 앞으로 · 새로고침(2026-11-28: 캡차 · 만료된 양식을 다시 받기)을 보낸다. 지금 상태를 한 줄로 보인다(보는 중 · 멈춤(창이 가려짐) · 꺼짐: 이유). 꺼져 있으면 10초마다만 묻는다. HTTPS(443) 하나로 끝난다.
  - **흘려보내기 (2026-11-26, "브라우저가 끊기듯이 동작")**: 1초마다 새로 찍던 것을 바꿨다. 서버(`ScreenCastGateway`)가 보는 탭에 웹소켓 하나로 오래 붙어 Chrome이 화면이 바뀔 때마다 보내는 그림(`Page.startScreencast`, JPEG 60, 받았다고 알려야 다음 그림)을 메모리에 마지막 하나만 두고, 클릭 · 글자도 같은 연결로 보낸다. 콘솔은 `GET screen?tab=&after=<받은 마지막 번호>`로 묻고, 서버는 새 그림이 오면 바로 · 없으면 5초 기다렸다 그림 없이(`image: null`) 답한다. 콘솔은 답을 받으면 0.1초 뒤 다시 묻는다(움직이는 페이지에서 1초에 10장까지). 그림을 주지 않는 탭(가려진 탭)은 1.2초 뒤 한 번 찍는다. 30초 동안 아무도 묻지 않으면 떼고, 함께 붙는 탭은 3개까지. 실제 Chromium에서 클릭 → 바뀐 그림이 20ms 안팎(이 컴퓨터 안, 그 전에는 다음 1초 찍기까지 기다림).
  - 전용 망에는 브라우저(와 그 네트워크를 함께 쓰는 서버 러너)와 서버만 붙는다. 웹 · DB · 일꾼은 9223에 닿지 않는다.
  - Chrome은 Host가 이름이면 거절해서(`Host header is specified and is not an IP address or localhost`) 서버는 서비스 이름 `browser`를 IP로 풀어 붙는다.
  - 화면 API는 관리자만 부른다. 입력한 글자(로그인 비밀번호일 수 있다) · 주소 · 화면은 어디에도 남기지 않는다. 주소 이동은 http(s)만.
- 정책(`URLBlocklist`)은 `localhost` · `127.0.0.1` · `[::1]` · `0.0.0.0` · `169.254.169.254` · `metadata.google.internal`과 compose 서비스 이름(`moida-server` · `server` · `browser` · `db` · `web` · `worker` · `runner`)을 막는다. IP 대역은 정책에 적을 수 없어 둘러보기는 러너의 프록시가 막는다. 프록시를 거치지 않는 WebRTC UDP도 정책으로 막는다(`WebRtcIPHandling`).
- 내 컴퓨터에서는 러너 전용 Chrome 프로필을 `--remote-debugging-port`로 띄우고 `MOIDA_BROWSER_URL`을 주면 탭 읽기를 한다 (`apps/runner/.env.example`).

## 4. 흐름

### 탭 읽기

1. 관리자: `POST /api/p/browser-tabs/reads { url }` → `reads`에 `requested`. 일꾼: MCP `browser_read { request_id, urls }`(10개까지, 2026-11-24) → `reads`에 `agent_id`와 함께 `requested`. 자바스크립트로 그리는 페이지(`read_url`은 HTML만 받아 껍데기만 온다) · 여러 페이지 · 내리면 더 나오는 목록을 읽는 기본 길이다. 승인 없음(읽기만).
2. 러너의 `TabReader`(일과 따로 돎): `browser_tab_pending`으로 받는다 (`blank`: 일꾼의 읽기). 없으면 3초, 패키지가 꺼져 있으면 5분 뒤 다시 묻는다. 세 개씩 함께 읽는다.
3. `BrowserTabs`: 새 탭 → 다 뜨면(30초, 넘어도 그때까지 그린 것을 읽는다) 아래로 내리며 글자 수가 두 번 내리 그대로일 때까지(0.8초 간격, 10초까지) 기다린 뒤 제목과 `innerText` → 탭 닫기. 관리자의 읽기는 로그인된 프로필의 탭으로, 일꾼의 읽기(`blank`)는 쿠키 없는 새 빈 컨텍스트(CDP `Target.createBrowserContext`)에서 내부 주소를 막는 프록시(`ExploreProxy`, `<-loopback>`으로 localhost도 프록시로)로만 나가고 끝나면 컨텍스트째 지운다.
4. `browser_tab_save`로 남긴다. 페이지 문제(열지 못함)는 이유를 남기고, 브라우저에 닿지 못하면 남기지 않고 기다렸다 다시 한다. 로그에는 주소의 호스트만.
5. 일꾼은 `browser_read_result { ids, wait_seconds }`로 결과를 받는다 (맡긴 에이전트만, 주소마다 30,000자까지). `browser_read`에 `shot: true`면 러너가 넓은 화면(1280×900)의 첫 화면을 JPEG로 떠서(280KB까지, 화질 70 → 45) 함께 남기고, 결과 답 뒤에 MCP image로 붙인다 (글 JSON에는 `shot: true`만, 2026-11-25 앱의 디자인 조사). 관리자의 읽기 목록에는 그림을 싣지 않는다. 일꾼의 읽기는 7일 뒤 지운다. `read_url`이 글이 거의 없는 HTML을 받으면 답의 note가 `browser_read`를 알린다 (지시문 틀 `read-url-shell`).

### 사이트 일과 결재된 클릭

1. 관리자: 사이트를 등록하고(이름 · 시작 주소 · 허용 출처), 콘솔 화면에서 그 사이트에 로그인한다.
2. 관리자: 사이트에서 "맡기기" → 패키지가 `task.task.requested`(종류 `browse`, 대상 `browser_site` · 사이트 id · 판)를 남긴다. 담당을 비우면 `browse` 권한이 있는 에이전트가 맡는다. 대표(공개 읽기만)가 `delegate_task { kind: browse, target_kind: browser_site, … }`로 브라우저 담당에게 맡겨도 같다 (사이트는 `browser_sites`로 고른다).
3. 서버: `browse` 작업은 `next_jobs`에서 `browser: true`를 알린 러너에게만 빌려 준다. 러너는 사이트 일(대상이 있는 browse)이 도는 동안 `browser`를 알리지 않는다 (사이트 일은 러너마다 하나씩).
4. 서버 러너(`BrowseStage`): 브라우저에 닿는지 묻고(3초), 닿지 못하면 돌려주고 기다린다. `browser_job`으로 어디서 돌지 받는다(사이트 값 · 로그인 필요 · 붙잡았던 페이지). 브라우저 자리(`BrowserSlot`, 결재된 클릭과 나눈다)를 잡고 지금 탭을 기억한다. 사이트에 로그인 필요가 적혀 있으면 AI 없이 로그인 결재로 간다 (아래).
5. AI CLI에 moida MCP와 Playwright MCP(`--cdp-endpoint` · `--allowed-origins` · `--output-dir`)를 붙여 띄운다. 스킬은 `moida-browse`: 새 탭을 열고, 채우고, 단계마다 JPEG 화면을 찍고, 마지막 버튼 앞에서 작업 폴더에 `browser-stop.json { stop: "final_click", page_url, button: { role, name, nth }, note, check? }`을 쓰고 끝낸다. 결재는 올리지 않는다.
6. 러너: AI가 찍은 단계 화면을 올리고(`browser_shot_save`), AI가 새로 연 탭에서 그 주소를 찾아 접근성 트리에서 역할 + 이름으로 버튼을 다시 찾는다 (`BrowserPages.hold`). 보이고 · 켜져 있고 · 한가운데의 가장 위 요소여야 한다. 지문(주소(# 앞) · 역할 · 이름 · 순번 · 태그 · type · form action · method · 글자의 sha256)과 멈춘 화면을 만들어 `browser_click_hold`로 붙잡고(페이지는 허용 출처 안이어야 한다), 작업 토큰으로 `request_approval { action: browser.site.publish, target_kind: browser_click, target_id: 클릭, target_version }`을 올린다. 작업은 결재를 기다린다.
7. 관리자: 결재 카드에서 페이지 · 버튼 · 멈춘 화면(버튼 자리에 테두리)을 보고 "누르기"(승인). 고칠 게 있으면 수정 요청: 클릭은 닫히고 AI가 붙잡아 두었던 탭에서 고친 뒤 다시 멈춘다.
8. 패키지: `task.approval.granted`를 받아 클릭을 `approved`로 (판이 결재한 판과 같을 때만). 작업은 임대 없이 결과를 기다린다.
9. 러너의 `ClickRunner`(5초마다 `browser_click_next`, 붙잡은 러너만 받는다): 자리를 잡고 같은 탭 · 같은 주소 · 같은 지문 · 가장 위 요소인지 다시 본다. 같으면 실제 마우스 이벤트로 누르고, 새 페이지면 뜰 때까지(최대 10초) 기다려 결과 화면과 주소를 `browser_click_save { outcome: clicked }`로 남긴다 → 패키지가 `plugin.browser_tabs.click_done { approvalId, outcome: done }` → 코어가 작업을 끝낸다. 다르면 누르지 않고 `changed`와 그때의 화면 → 작업 실패("페이지가 바뀌어 누르지 않았어요 … 콘솔 화면에서 직접 눌러 주세요") → 관리자가 직접 누르고 클릭 목록에서 "직접 눌렀어요"로 기록한다.
   사람이 넣을 칸 (개인정보 규칙 ①, 2026-11-28): 결제 수단 · 본인 인증 번호 · 주민번호 칸은 AI가 채우지 않는다. AI는 나머지를 채운 뒤 마지막 버튼 앞에서 `final_click`의 `human`(칸 이름 5개까지)을 적고 멈추며, 러너가 `browser_click_hold`의 `human_fields`(`clicks.human_fields`)로 붙잡는다. 승인 카드에 그 탭의 서버 브라우저 화면이 열려 관리자가 직접 넣고 승인하면 러너(AI 없음)가 누른다. AI는 그 페이지로 돌아가지 않는다.
   화면 사진의 보관 기한 (개인정보 규칙 ④, 2026-11-28, `dropOldShots`): 단계 화면 30일, 로그인 · 누르기 전후 · 바뀐 화면 90일. 작업이 끝날 때(`TaskSettled`)와 단계 화면을 저장할 때 지운다.
   누른 뒤 확인 (L3, 2026-11-28, `ClickConfirm`): 누른 화면을 한 번 더 읽어 결제 · 본인 인증 화면이면 `confirm.state: auth`(승인 카드에 그 탭의 서버 브라우저 화면이 열려 관리자가 직접 마친다. 넣은 값은 AI를 거치지 않는다), 결과 화면이면 `done`과 예약 · 주문 번호(`reference`) · 페이지 제목을 `browser_click_save` · `browser_press_save`의 `confirm`으로 남긴다 (`clicks.confirm_state` · `confirm_ref` · `confirm_title`). 화면의 글은 보내지 않는다. 계획 안의 누르기는 `browser_press_result`의 `confirm`으로 AI가 보고, auth면 더 누르지 않고 끝낸다. 인증을 마친 뒤 결과를 다시 읽는 단계는 아직 없다 (관리자가 화면에서 확인한다)

### 누르기 계획: 일 하나에 승인 한 번 (F2, 2026-11-21)

같은 사이트에서 마지막 버튼을 여러 번 눌러야 하는 일(지도 목록에 12곳 저장, 상품 여러 개 등록)은 버튼마다 승인받지 않는다.

1. AI가 첫 마지막 버튼 앞에서 `browser-stop.json { stop: "click_plan", page_url, plan: { summary, count } }`(횟수 1~50)을 쓰고 끝낸다.
2. 러너(`StopHold.plan`)가 `browser_click_plan`으로 계획을 붙잡고(`click_plans`, held, 허용 출처 안의 페이지만) `request_approval { action: browser.site.publish, target_kind: browser_click_plan }`을 올린다. 메모는 `누르기 계획: <요약> (<횟수>번)`.
3. 관리자가 한 번 승인하면 패키지가 계획을 approved로 하고 결과 이벤트를 `outcome: continue`로 남긴다 → 코어가 같은 작업을 다시 대기열로 돌린다 (`Task.continueAfterApproval`, 플러그인 API 0.8). 수정 요청 · 반려면 계획은 dropped (수정 요청이면 그 메모로 같은 작업이 다시 돈다).
4. 다시 빌린 실행의 `browser_job`에 `click_plan { id, summary, max_clicks, used, left }`가 오고, 지시문 틀 site가 "승인된 누르기 계획"을 싣는다. 러너는 AI가 도는 동안 `PressLoop`를 함께 돌린다.
5. AI는 항목마다 채우기까지 하고, 마지막 버튼은 직접 누르지 않고 `browser_press { page_url, role, name, nth?, note? }`(작업 토큰)로 요청한다. 서버가 막는 것: 승인된 계획 없음 · 계획한 사이트(허용 출처) 밖 · 횟수를 다 씀 · 앞 누르기가 끝나지 않음(한 번에 하나). 요청은 클릭 줄 하나(`clicks.plan_id`, requested)다.
6. `PressLoop`가 1.5초마다 `browser_press_next`로 가져가면(clicking, 이때 계획의 횟수를 센다) 그 주소의 탭에서 역할 + 이름으로 버튼을 다시 찾아(`BrowserPages.hold`: 보임 · 켜짐 · 가장 위) 주소가 같을 때만 실제 마우스로 누르고, 다시 찾은 버튼(탭 · 자리 · 지문)과 누르기 전 · 뒤 화면을 `browser_press_save`로 남긴다. 찾지 못하거나 주소가 바뀌었으면 누르지 않고 changed와 까닭.
7. AI는 `browser_press_result { click_id }`(최대 20초 기다림)로 결과를 보고 다음 항목으로 간다. 실행이 끝나면 가져가지 않은 요청은 닫고(dropped), 작업이 끝나면 계획을 닫는다(closed).

누르는 것은 여전히 AI 없는 러너다 (원칙 7). 계획 하나의 승인은 "이 사이트에서 이 일로 N번까지"를 허락하는 것이라, AI가 계획과 다른 버튼을 요청해도 같은 사이트 안이면 횟수 안에서 눌릴 수 있다. 그래서 요약을 구체적으로 쓰게 하고(스킬), 누른 것은 모두 클릭 목록에 화면과 함께 남는다.

### 로그인 필요

1. AI가 사람이 해야 하는 화면(로그인 · 회원가입 · 본인 인증 · 캡차 · 새 기기 확인, 2026-11-17 넓힘)을 보면 아무것도 치지 않고 `browser-stop.json { stop: "login", page_url, reason? }`을 쓰고 끝낸다. `reason`은 로그인이 아닐 때의 까닭 한마디(30자, 러너가 한 줄 · 괄호 없이 다듬는다). 사이트에 이미 로그인 필요가 적혀 있으면 러너가 AI를 띄우지 않는다 (관리자가 로그인할 탭을 열어 둔다).
2. 러너가 그 탭을 찍어 `browser_login_needed`로 사이트에 표시(`login_needed_at`, 판은 올리지 않는다)와 화면을 남기고, `request_approval { action: browser.site.login, target_kind: browser_site, … }`을 올린다. 메모는 `로그인 필요: <사이트>` 또는 `확인 필요(<까닭>): <사이트>`로 시작한다 (승인 카드가 까닭을 읽어 제목으로 쓴다). 작업은 기다리고 결재 알림 · 푸시가 간다. 위임한 일이면 원래 대화의 답 아래에도 이 카드가 뜬다.
3. **로그인 카드 (2026-11-19, 원칙 8을 바꿈)**: AI는 로그인 화면이면 `browser-stop.json`의 `form`에 칸(`kind`: id · password · code, 접근성 `role` · `name`)과 로그인 단추(`submit`)를 적는다. 값은 적지 않는다. 러너(`BrowseLogin`)가 관리자가 로그인할 탭(유지 프로필)에서 그 칸을 다시 찾아(`LoginForm.check`: 하나뿐 · 보임 · 쓸 수 있음 · 비밀번호 칸은 `type=password`, https나 이 컴퓨터의 http) 확인한 것만 `browser_login_needed`의 `form`으로 보낸다. 패키지는 **믿는 출처**일 때만 사이트의 `login_form`에 적는다: 사이트와 같은 등록 도메인(nid.naver.com ↔ blog.naver.com)이고, 관리자가 등록했거나 화면에서 로그인한 사이트(`trusted_at`)이거나 관리자가 쓴 지시(`LeasedWork.ownerText`)에 그 도메인이 있을 때 (`LoginTrust`). 아니면 칸 없이 화면 로그인이다 (페이지에 심은 글이 AI를 가짜 로그인 화면으로 데려가도 칸이 뜨지 않게).
   카드에 칸이 있으면 관리자가 값을 넣는다 (`POST sites/:id/login { values }`, 관리자만). 값은 API 서버 메모리에만 두고(`LoginInbox`, 10분), 그 로그인 화면을 연 러너(`login_form.runner_id`)의 `LoginRunner`가 `browser_login_next`로 꺼내면 지운다. 러너(AI 없음)는 같은 출처의 탭(없으면 그 주소를 새로 연다)에서 칸을 다시 확인하고 `Input.insertText`로 넣은 뒤 로그인 단추를 실제 마우스 이벤트로 누르고, 주소가 바뀌거나 그려질 때까지 기다려 그 뒤 화면을 `browser_login_save`로 남긴다 (화면도 메모리에만 10분). 카드가 그 화면을 보이고 "로그인했어요"로 같은 작업을 잇는다. 값은 AI · 로그 · 실행 기록 · DB 어디에도 가지 않는다 (e2e가 본다). 로그인 요청(API)을 재현하지 않고 화면의 칸에 넣으므로 CSRF 토큰 · 스크립트 암호화를 사이트가 그대로 한다. 인증번호가 이어서 필요하면 같은 작업이 다시 그 화면에서 멈추고 인증번호 칸 카드가 뜬다.
   **간편 로그인 (2026-11-26, 사용자 결정)**: AI는 로그인 화면의 카카오 · 네이버 · 구글 · 애플 간편 로그인 단추를 `form.social`(회사 · 역할 · 이름, 회사마다 하나)에 적고 누르지 않는다. 칸 없이 간편 로그인만인 화면도 된다. 러너가 그 탭에서 다시 찾아 누를 수 있는 단추만 보내고, 카드에 "카카오로 로그인" 단추가 뜬다. 관리자가 누르면(`POST sites/:id/login { social }`) 그 러너(AI 없음)가 단추를 실제 마우스 이벤트로 누르고, **고정 목록**(`LOGIN_PROVIDERS` · 러너 `LoginFormRef.PROVIDERS`: accounts.kakao.com · kauth.kakao.com · nid.naver.com · accounts.google.com · appleid.apple.com, https만)의 호스트로 열린 탭(같은 탭이나 새 창)을 6초까지 찾는다. 찾으면 그 화면에서 보이는 비밀번호 칸이 꼭 하나 · 같은 폼의 글 칸이 꼭 하나 · 보내기 단추가 꼭 하나일 때만 셋을 접근성 역할 + 이름으로 적어(`ProviderLogin`, AI 없음) `browser_login_save { outcome: opened, provider_form }`로 남긴다 (서버도 고정 목록의 https 호스트만 받는다). 카드가 그 회사의 아이디 · 비밀번호 칸을 띄우고, 넣으면(`{ step: 'provider', values }`) 러너가 열려 있는 그 회사 화면의 칸에 넣고 누른다 (`submitted` → 같은 작업을 잇는다). 칸을 찾지 못하면(여러 단계 · 휴대폰 승인 · 캡차) 카드가 그 화면을 보이고 관리자가 휴대폰 승인이나 화면에서 마친 뒤 "로그인했어요". 그 회사의 칸 · 화면은 서버 메모리에만 10분(`LoginInbox`), 값은 지금과 같이 AI · 로그 · DB에 가지 않는다. 사이트의 로그인 요청(API)을 대신 부르지 않는다.
4. 칸이 없거나(믿지 않는 출처 · 캡차 · 보안 키패드) 관리자가 원하면 **대화의 승인 카드 안에서** 그 탭의 화면을 열어(2026-11-17) 직접 로그인 · 가입 · 인증하고 "로그인했어요"를 누른다 (= 정해진 말의 수정 요청). 카드의 화면은 콘솔 화면(`Screen.tsx`)을 `pin`으로 쓴 것이다: 로그인 주소와 같은 탭(없으면 같은 호스트의 탭)을 앞으로 가져와 그 탭에 묶이고, 탭 고르기 · 주소 칸은 없고, 페이지 전체를 카드 폭에 맞춰 보이며 "크게 보기"로 화면을 채운다. 쓰는 API는 콘솔 화면과 같다(`GET /screen` · `POST /screen/control`, 관리자만). 비밀번호는 진짜 사이트의 칸에만 들어간다. 패키지가 표시를 비우고, 코어가 같은 작업을 대기열로 돌린다(대상 `browser_site`). 위임 사슬(위 작업이 하위 작업을 기다리는 것)은 끊기지 않는다. 반려하면 작업이 취소된다. API로 승인하면 쓰지 않는 길이라 실패로 끝난다.

### 요청 기록 → API 도구 (B2 · B3, 2026-11-20)

"브라우저로 들어가도 분석하고 MCP로 변환" (2026-11-19 사용자 결정). 같은 사이트의 읽기를 다음부터는 화면이 아니라 그 화면이 쓰는 API로 한다.

1. 사이트 일이 시작되면(로그인 필요가 적혀 있지 않을 때) 러너의 `NetworkTap`(AI 없음)이 같은 브라우저의 탭들에 CDP로 함께 붙는다 (0.4초마다 새 탭을 찾음, 10탭까지). 듣기만 한다: 요청을 바꾸거나 막지 않는다.
2. 사이트의 허용 출처로 가는 XHR · fetch만 모양으로 바꿔 모은다 (`ApiShape`, 40개까지): 방법 · 출처 · 경로 틀(숫자 조각 `{n}`, id · 토큰처럼 생긴 조각 `{id}`) · 쿼리 이름 · 요청 본문의 모양(JSON이면 칸 이름과 종류, 폼이면 이름) · 상태 · JSON 답의 모양(512KB까지 읽고 깊이 4 · 칸 30개 · 목록은 첫 항목). 값 · 머리글 · 쿠키는 보지 않고, 이메일 · 긴 숫자 · 토큰처럼 생긴 칸 이름도 뺀다.
3. AI가 끝나면 러너가 `browser_requests_save { task_id, requests }`로 보낸다 (그 작업의 임대를 쥔 러너만, 사이트 일만). 패키지는 사이트의 허용 출처로 간 것만 `endpoints`에 남기고, 같은 모양(방법 · 출처 · 경로 틀)은 횟수(`seen`)만 올린다. 실패해도 일은 그대로 이어진다.
4. 그 사이트에 아직 사이트 도구가 없고, 읽을 만한 API(GET · 2xx · JSON 답)가 처음 생기면 패키지가 읽기 사이트 도구 하나(`api_<호스트 낱말>`, 제목 `<사이트> API`)를 만들고 굳히기 작업을 맡긴다 (사이트마다 한 번 `sites.api_build_at`, 설정 `autoApiTools`, 담당은 `browse` 권한이 있는 에이전트). 이번 일은 브라우저로 끝까지 한다 (기다리게 하지 않는다).
5. 굳히는 AI는 `browser_job`의 `build.endpoints`(읽을 만한 GET이 먼저, 20개)를 지시문 틀 `site-build`의 "이 사이트에서 기록한 API"로 받는다. 코드는 화면 대신 `site.api(경로, { query })`를 부르고, API로 안 되는 것만 `page`로 읽는다. 시험을 지나면 바로 켜지고(B0), 다음부터 에이전트는 브라우저 대신 `site_run`으로 한다.
6. 쓰기도 바로 제안한다 (2026-11-21): 승인한 누르기 계획이 있는 일(계획이 `approved` · `closed`, 그 계획으로 눌린 클릭이 하나 이상)의 기록에 쓰기 API(GET · HEAD · OPTIONS가 아닌 2xx)가 있으면, 되풀이 셋을 기다리지 않고 "도구로 만들 만한 일"에 바로 제안을 연다 (`suggestions.note`에 계획 이름과 `방법 경로` 목록, 열쇠는 되풀이와 같은 지시의 모양이라 하나로 합쳐진다). "도구로 만들기"는 폼을 쓰기 모드로 연다. 쓰기 도구는 검토자 짝 · 부를 때마다 승인(MCP 7장)이라 자동으로 만들지는 않는다.
7. 배정 단계에서 도구 먼저 (2026-11-21, 위임 지킴이 `GuardSiteDelegation`, 플러그인 API 0.9 `delegate:browser_site`): `browser_sites`는 사이트마다 켜진 도구(`tools`: 이름 · 제목 · 읽기/쓰기)를 함께 주고, 대표가 켜진 도구가 있는 사이트에 browse를 맡기면 코어가 하위 작업을 만들기 전에 패키지가 거절한다. 통과하는 길은 둘: 그 대표가 30분 안에 그 사이트의 도구를 불러 봤거나(`runs`), 지시에 그 도구 이름을 적었다(도구로 할 수 없는 일 · 그 까닭). 둘러보기(대상 없음)는 지나지 않는다.
8. 되풀이도 묻지 않고 도구로 (2026-11-24, 설정 `autoRepeatTools`, 기본 켬): 같은 사이트 · 같은 모양의 일이 14일 안에 세 번이면 제안을 띄우는 대신 바로 읽기 도구(`repeat_<호스트 낱말>`, 힌트는 횟수와 지시 예)를 만들고 굳히기를 맡긴다 (담당은 `browse` 권한이 있는 에이전트, 제안은 `made`). 시험을 지나면 바로 켜진다(B0). 필요 없는 도구는 관리자가 목록에서 지우고, 지운 도구는 제안이 `made`로 남아 다시 만들지 않는다. 그 사이트에 굳히는 중인 도구가 있으면 제안을 연 채로 두고 다음 되풀이에 다시 본다. 쓰기 API가 기록된 제안(`note`)은 6처럼 제안으로 둔다. 굳히기 작업이 실패 · 취소로 끝나면 제안은 `failed`(못 만듦)가 되어 까닭(작업의 실패 글)과 다시 해 볼 날이 "도구로 만들 만한 일"에 보이고, 30일 동안은 같은 일이 되풀이돼도 굳히지 않는다(그동안은 브라우저로). 30일이 지나 다시 되풀이되면 꺼 둔 같은 도구를 다시 굳힌다 (C4, 2026-11-28).
8. `site.api`: GET만 · 사이트의 허용 출처만 · 브라우저 컨텍스트의 요청(`context.request`)이라 로그인 쿠키는 브라우저가 붙이고 코드 · AI는 보지 못한다 · 리다이렉트를 따라가지 않는다 · 15초 · 답 2MB. 답은 `{ status, ok, json(), text() }`.

### 둘러보기

1. 관리자: `POST /api/p/browser-tabs/explore { requestId, instruction, agentId? }`, 또는 대표가 대상 없이 `kind: browse`로 맡긴다.
2. 러너: `browser_job`이 `explore`. 프록시(`ExploreProxy`, 127.0.0.1의 빈 포트)를 띄우고 Playwright MCP를 `--isolated --proxy-server`로 붙인다. 브라우저 자리를 쓰지 않아 여럿이 함께 돈다.
3. AI는 공개 사이트를 열어 조사하고 결과를 답에 쓴다. 단계 화면은 사이트 일과 같이 남는다. `browser-stop.json`의 `final_click`을 써도 러너는 누르지 않는다.
   로그인이 있어야 하는 일이면(등록 없이, 2026-11-19 사용자 결정) AI는 `browser-stop.json { stop: "login", page_url }`을 쓰고 끝낸다. 러너가 그 주소를 로그인이 남는 프로필(서버 브라우저)의 탭으로 열고 `browser_login_needed`를 부르면, 패키지가 그 출처를 가진 사이트를 찾고 없으면 만든다(`siteForPage`: 이름은 호스트, 시작 주소는 `<출처>/`, 출처 하나). 그 뒤는 로그인 필요와 같다: 결재의 대상이 그 사이트라 "로그인했어요"면 코어가 결재의 대상을 작업의 대상으로 옮기고 같은 작업이 그 사이트의 일(유지 프로필)로 다시 돈다. 관리자가 사이트를 미리 등록할 일이 없다.
4. MCP가 끝나면 그 컨텍스트도 사라진다 (CDP 연결이 끊기면 Chrome이 지운다, 시험으로 확인).

### 사이트 세션 지우기

`POST /api/p/browser-tabs/sites/:id/clear-session` (관리자): 서버가 조종 중계로 로그인된 프로필에 빈 탭을 열어, 그 사이트 출처의 호스트로 가는 쿠키만 지우고(`Network.deleteCookies`) 그 출처의 저장소(localStorage · IndexedDB · 캐시 저장소 · 서비스 워커 …)를 지운 뒤(`Storage.clearDataForOrigin`) 탭을 닫는다. 쿠키만 지우면 토큰을 저장소에 두는 사이트는 로그인이 남기 때문이다. 다른 사이트의 로그인은 그대로다. 그 사이트에서 기다리는 클릭이 있으면 409, 브라우저에 닿지 못하면 502. 로그인 필요 표시는 바꾸지 않는다 (다음 일이 로그인 화면을 만나면 적힌다).

## 5. 데이터와 입구

**표** (스키마 `browser_tabs`, 마이그레이션은 `plugins/browser-tabs/migrations/`. 코어 표는 바꾸지 않고 값으로만 가리킨다):

| 표 | 칸 | 규칙 |
|---|---|---|
| `reads` | `url`, `status`(`requested` · `done` · `failed`), `title`, `body`, `error`, `requested_at`, `read_at`, `version` | http(s)만. 러너가 한 번만 남긴다 |
| `sites` | `name`, `start_url`, `origins[]`, `login_needed_at`, `login_form`, `trusted_at`, `api_build_at`, `created_at`, `updated_at`, `version` | 출처는 1~10개, `http(s)://호스트[:포트]`(경로 없음). 시작 주소는 출처 안. 고치고 지울 때 판을 본다. 로그인 필요 표시 · 로그인 칸은 판을 올리지 않는다. `login_form`은 로그인 칸(종류 · 역할 · 이름 · 단추 · 주소 · 그 러너, 값 없음), `trusted_at`은 믿는 출처가 된 때(직접 등록 · "로그인했어요"), `api_build_at`은 기록으로 API 도구 굳히기를 시작한 때(사이트마다 한 번) |
| `endpoints` | `site_id`(→ `sites`, 지우면 함께), `method`, `origin`, `path`(틀), `query[]`(이름), `body` · `response`(모양 jsonb), `status`, `content_type`, `seen`, `last_task_id`(값), `created_at`, `updated_at` | 사이트 · 방법 · 출처 · 경로마다 한 줄 (같으면 횟수만 올리고 모양은 새것으로). 값은 없다. 사이트 일에서만 쌓인다 |
| `clicks` | `task_id` · `site_id` · `runner_id`(값), `tab_id`, `page_url`, `page_title`, `role`, `name`, `nth`, `box`, `fingerprint`, `note`, `status`, `approval_id`, `reason`, `after_url`, `created_at` · `decided_at` · `clicked_at`, `version` | `held → approved → clicking → clicked · changed · unknown`, `held → dropped`, `approved · changed · unknown → manual`. 작업 하나에 열린 클릭(`held` · `approved` · `clicking`)은 하나(부분 유일 인덱스). 붙잡은 러너만 누른다. 2분 넘게 `clicking`이면 `unknown`(다시 누르지 않는다) |
| `shots` | `task_id`, `click_id`(→ `clicks`), `kind`(`step` · `login` · `before` · `after` · `changed`), `seq`, `url`, `title`, `image`(bytea, 300KB), `mime`(JPEG · PNG) | 단계(`step`)는 작업마다 30장 · 30일(새로 저장할 때 지운다). 나머지는 남긴다. 목록은 그림 없이 |

코어 쪽은 `task.agents.scopes`의 `browse`, 일 종류 `browse`(위임 가능), 결재 동작 이름 `browser.site.publish` · `browser.site.login`(값)뿐이다 ([테이블설계](테이블설계.md) 6장).

**MCP** ([API설계](API설계.md) 4장): 러너(`run`) `browser_tab_pending` · `browser_tab_save`, 에이전트(작업 토큰) `browser_read` · `browser_read_result`(화면 읽기, 2026-11-24), 그 작업의 임대를 쥔 러너만 `browser_job` · `browser_shot_save` · `browser_login_needed` · `browser_click_hold` · `browser_requests_save`(요청 기록, 사이트 일만), 붙잡은 러너만 `browser_click_next` · `browser_click_save`, 로그인 화면을 연 러너만 `browser_login_next` · `browser_login_save` (로그인 카드). 에이전트(작업 토큰) `browser_sites`. `next_jobs`의 `browser`, `request_approval`의 `browser.site.publish`(대상 `browser_click`) · `browser.site.login`(대상 `browser_site`)은 러너가 작업 토큰으로 올린다.

**이벤트**: 패키지가 `task.task.requested`를 남긴다(`uses: task:request`). `task.approval.granted` · `revision_requested` · `rejected` · `cancelled`(클릭 결재 → `approved` · `dropped`, 로그인 결재의 수정 요청 → 표시 비우기)와 `task.task.changed`(실패 · 취소된 작업의 열린 클릭 닫기)를 받고, `plugin.browser_tabs.click_done { approvalId, outcome, error? }`를 남긴다.

결과 결재(2차 2단계)는 클릭 결재를 대화 회차의 결과 카드로 묶는다. 결재 줄의 모양(동작 · 대상 · 판)과 승인 이벤트가 같아 이 패키지는 그대로다. 로그인 필요는 결과가 아니라 바로 오는 결재로 남는다.

## 6. 안전장치와 남는 위험

| 막을 일 | 어디서 | 어떻게 |
|---|---|---|
| AI가 마지막 버튼을 누르는 것 | 스킬 · 러너 · 서버 | AI는 멈추고 `browser-stop.json`만 남긴다. 누르기는 결재 뒤 러너가 같은 탭 · 주소 · 지문 · 가장 위 요소일 때만 (`BrowserPages.press`). 다르면 누르지 않는다. 많아야 한 번 |
| 비공개가 바깥 사이트로 나가는 것 | 서버 · 러너 | 2026-11-21부터 브라우저 담당도 비공개를 읽는다 (사용자가 위험을 듣고 고름). 바깥을 바꾸는 클릭은 승인 뒤 러너가 누르고, 사람이 볼 수 없는 입력 · 주소로 새는 것은 막지 못한다 |
| 둘러보기가 로그인 · 내부망에 닿는 것 | 러너 · 정책 | 일마다 새 빈 컨텍스트(쿠키 없음), 이름을 풀어 본 뒤 내부 · 사설 · 메타데이터 · CGNAT 주소를 막는 프록시. 정책이 이름을 한 번 더 막는다 |
| 조종 포트가 밖에 열리는 것 | 배포 구성 | CDP는 러너와 브라우저가 함께 쓰는 네트워크의 127.0.0.1에만. 밖으로 여는 포트가 없다 |
| 남이 화면을 보는 것 | 서버 | 콘솔 화면 · 세션 지우기 · 클릭 · 화면 API는 관리자만 |
| 다른 컨테이너가 조종 중계에 닿는 것 | 배포 구성 | 중계(9223)는 서버와 브라우저만 붙는 망(`browser`)에만. 웹 · DB · 일꾼은 그 망에 없다 |
| 다른 사이트로 가는 것 | 러너 | 허용 출처(`--allowed-origins`): 바로 이동 · `fetch` · 이미지는 막는다. 붙잡을 때 페이지가 허용 출처 안인지 서버가 다시 본다 |
| AI가 셸 · 다른 MCP를 쓰는 것 | 러너 | 셸은 없고, 격리 검사가 그 작업에서만 `playwright`를 허락한다. 작업 토큰은 moida 설정에만 |
| AI가 페이지에서 스크립트를 돌리거나 파일을 올리는 것 | 러너 | Playwright MCP의 `browser_evaluate` · `browser_file_upload`를 막는다 (2026-11-24, `BrowserMcp.BLOCKED_TOOLS`: Claude는 `--disallowedTools`, Codex는 config.toml의 `disabled_tools`). 스크립트는 로그인된 페이지에서 마지막 버튼을 대신 누를 수 있고, 파일 올리기는 작업 폴더의 것을 사이트로 내보낸다 |
| 요청 기록에 값이 남는 것 | 러너 · 패키지 | 러너가 모양으로 바꾼 뒤에만 보낸다(값 · 머리글 · 쿠키 없음, 개인정보처럼 생긴 칸 이름은 뺌). 패키지는 허용 출처의 것만 받고 JSON이 아닌 모양은 거절. 둘러보기(빈 프로필)는 기록하지 않는다 |
| 굳힌 도구가 API로 쓰기를 하는 것 | 러너 | `site.api`는 GET만 · 허용 출처만 · 리다이렉트 없음. 쓰기 API는 기록만 하고 부르지 않는다 (쓰기 도구는 화면 + 부를 때마다 승인) |
| 브라우저가 서버를 잡아먹는 것 | 배포 구성 | `mem_limit: 1g` (넘치면 브라우저만 죽는다). 로그는 10MB × 2 |

**남는 위험**
- **허용 출처는 경계가 아니다.** 허용한 사이트에서 나가는 리다이렉트는 막지 못했다 (시험, Playwright MCP 문서에도 "보안 경계가 아님"). 진짜 경계는 사이트 일에도 나가는 프록시를 거는 것이다 (다음 단계).
- **AI가 버튼을 누를 수 있다.** 허용 출처 안에서는 그 계정으로 할 수 있는 일을 다 할 수 있고, 막는 것은 스킬 지시뿐이다. 결재된 클릭은 "멈춘 버튼을 대신 누르는 길"이지 AI의 클릭을 막는 장치가 아니다. 자동화용 계정을 따로 쓰길 권한다.
- **역할 + 이름이 Playwright와 Chrome에서 다를 수 있다.** 다르면 붙잡지 못하거나(작업 실패) 바뀐 것으로 보여 누르지 않는다 (안전한 쪽으로 실패한다).
- **사이트 일이 관리자 탭을 옮길 수 있다.** Playwright MCP는 붙을 때 맨 앞 탭을 지금 탭으로 고른다. 스킬이 새 탭부터 열게 하고, 옮겨진 탭은 지문 검사가 "바뀜"으로 잡는다.
- **프로필이 하나다.** 사이트마다 나누지 않아 쿠키가 한 브라우저에 함께 있다 (요청은 허용 출처로만 나간다). 세션 지우기는 그 사이트의 호스트로 가는 쿠키만 지운다 (`.example.com` 쿠키는 그 아래 다른 사이트와 함께 지워진다).
- **관리자 로그인이 뚫리면 로그인된 브라우저가 넘어간다.** 콘솔 화면은 관리자 세션 하나로 열린다.
- **서버가 뚫리면 브라우저도 넘어간다.** 서버는 전용 망으로 조종 중계에 닿는다. 서버에는 이미 모든 데이터와 열쇠가 있어 새로 생기는 길은 아니다.
- **러너가 죽어도 둘러보기 창은 남지 않는다.** 프록시는 러너와 같은 프로세스라 함께 사라지고, 컨텍스트는 CDP 연결이 끊기면 Chrome이 지운다 (SIGKILL로 시험).
