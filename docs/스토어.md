# 스토어와 앱

> 상태: **설계안 승인** (2026-11-18, [기획서](기획서.md) 결정 기록). **1단계 인터페이스(8장) 승인** (2026-11-18), 1-1 ~ 1-5 구현. **1-6은 "앱 코드"로 바꿔(2026-11-18) 인터페이스(9장) 승인, 1-6a 서버 · 1-6b 웹 · 1-6c 러너 · 보관 구현.** 테이블 · API · 보관 형식은 단계마다 함께 고치고, 객체 설계는 1-6에서.

"블로그 하나"를 "스토어 안의 여러 앱"으로 올린다. Cairn은 앱들을 만들고 운영하고, AI 팀이 앱마다 글을 쓰고 커뮤니티를 관리하고 새 앱을 개발한다. 사람은 목적을 말하고 승인만 한다.

## 1. 개념

| 말 | 뜻 | 예 |
|---|---|---|
| 스토어 | 만들 수 있는 앱 종류의 목록이자 만든 앱을 관리하는 콘솔 화면 | 콘솔 독의 "스토어" |
| 앱 종류 | 코드로 만든 앱의 틀. 저장소(코어 또는 기능 패키지)에 있다 | 블로그 · 매거진 · 페이지 앱 · 커뮤니티 |
| 앱 | 앱 종류로 만든 서비스 하나. DB의 데이터다 | 개발 블로그 · 여행 블로그 · 카페 매거진 · 커뮤니티 |

- 개발 블로그와 여행 블로그는 같은 "블로그" 종류의 앱 두 개다. 코드는 같고 이름 · 주소 · 메뉴 · 운영 팀이 다르다.
- 카페 매거진은 "매거진" 종류다. 지금 있는 호 발행을 그대로 쓴다.
- 페이지 앱은 AI가 만든 HTML · JS 묶음이다. 지금의 "AI가 만든 페이지"를 앱 종류로 올린 것이다. 페이지 없이도 만들 수 있고, 그때 화면은 앱 코드가 전부다 (일정표 · 계산기 · 지도 같은 도구 화면, 2-6). 블로그 · 매거진과 달리 블로그 틀(머리 · 메뉴 · 꼬리)이 없는 빈 시작 코드에서 앱이 하는 일에 맞게 화면을 처음부터 만들고, 화면은 `/<앱>/<이름>`으로 여럿 둘 수 있다. 앱 코드를 아직 공개하지 않았으면 앱의 공개 페이지가 그대로 화면이다 (페이지 앱 자유도 P1, 2026-11-20, 9.11.4).
- 커뮤니티는 방문자가 회원으로 가입해 글을 쓰는 첫 기능이라 따로 단계를 둔다.

## 2. 구조

```
Cairn (내 서버 하나)
├─ store 모듈 (새로)        앱 종류 목록 · 앱(이름 · 주소 · 공개 여부 · 운영 팀 · 편집 방침)
├─ blog 모듈 (그대로)       글 · 메뉴 · 호 · 페이지 · 사진: 블로그 · 매거진 · 페이지 앱이 쓰는 글 엔진
├─ community 모듈 (3단계)   회원 · 글 · 댓글 · 신고
└─ vault · task · account · platform (그대로)

조직도: 대표 → 앱마다 운영 팀장 (개발 블로그 팀 · 여행 블로그 팀 · 매거진 팀 · 커뮤니티 운영 팀)
```

- `store`는 앱의 머리(무엇 · 어디 · 누가 · 아이콘 · 순서)만 갖는다. 글 · 메뉴 · 호 · 페이지는 blog가 갖고 `app_id`를 값으로 들고 있다 (모듈 사이 외래키 없음, 객체설계 9장).
- blog는 store를 가져오지 않는다. 앱이 있는지 · 공개인지는 platform 등록부(`Lookups`)로 묻는다 (R3b와 같은 방식).

## 3. 정한 것

| 정한 것 | 까닭 | 고르지 않은 것 |
|---|---|---|
| 앱 종류는 저장소 코드, 앱은 데이터. 스토어의 "만들기" = 앱 하나 만들기 | 남이 만든 앱 코드를 내려받아 서버에서 돌리지 않는다 | 외부 마켓에서 앱 코드 설치 |
| 블로그 · 매거진 · 페이지 앱은 지금 blog 모듈을 글 엔진으로 쓴다 | 글 · 버전 · 발행 승인 · 호 · RSS · 페이지가 테스트까지 있다 | 종류마다 엔진 새로 만들기 |
| 스키마 · 모듈 이름 `blog`는 그대로, 화면 · 문서의 "블로그"를 "스토어 · 앱"으로 | 이름만 바꾸면 마이그레이션 · 보관 형식 · 테스트 비용만 크다 | 모듈 · 스키마 이름 바꾸기 |
| 주소는 도메인 하나에 경로로 (`/dev`, `/travel`). 앱 주소로 못 쓰는 이름(`admin` · `api` · `login` · `install` · `connect` · `pages` · `posts` · `m` · `graph` …)은 막는다 | 인증서 · 프록시 설정이 그대로다 | 앱마다 도메인 (4단계 선택) |
| 지금 글 · 메뉴 · 호 · 페이지는 기본 앱 하나로 옮기고, 옛 주소(`/posts/…`, `/m/…`)는 새 주소로 넘긴다 | 들어온 정보는 버리지 않는다. 바깥 링크가 깨지지 않는다 | 처음부터 다시 |
| 앱 만들기 · 고치기는 대화에서도 제안(`propose_setting`의 `app`) → 승인 | AI는 설정을 제안만 한다 (2026-11-15 C) | AI가 앱을 바로 만들기 |
| 서버 기능이 필요한 새 앱 종류는 기능 패키지로 개발한다 | 자기 스키마 · 적은 확장 지점만 쓰고, 켤 때 권한을 허락받는다. AI가 쓴 코드의 피해 범위가 좁다 | 코어에 바로 넣기 |
| 커뮤니티는 따로 설계안 · 보안 검토 뒤에 | 회원 계정 · 스팸 · 개인정보(개인정보보호법) · 신고가 함께 생긴다 | 1단계에 함께 |

## 4. "앱 하나 만들어줘"의 흐름

대표가 요청을 보고 셋 중 하나로 보낸다.

| 길 | 언제 | 하는 일 | 승인 |
|---|---|---|---|
| ① 앱 만들기 | 있는 종류로 된다 ("요리 블로그") | 대표가 `propose_setting { setting: app, op: create, fields: { …, agent_id 또는 new_team: true } }` → 결과 카드 → 승인하면 서버가 앱(비공개)과 운영 팀(새로 만들거나 고른 팀장)을 함께 만든다 → 이어서 회차에서 운영 팀장의 팀이 첫 글 초안 | 앱 만들기 1 + 글 공개 |
| ② 페이지 앱 | 화면만 있으면 된다 ("카페 지도", "경비 계산기") | 대표가 ①처럼 `kind: page`로 앱 만들기를 제안한다(페이지 없이) → 승인 → 이어서 회차에서 앱 디자이너가 앱 코드로 첫 화면을 만든다(비공개 앱이라 바로 보이고 앱 관리에서 미리 보기) → 관리자가 공개. 있는 페이지를 앱으로 올리는 것은 관리자가 만들기 시트에서 (2-6) | 앱 만들기 1 + 공개 |
| ③ 새 앱 종류 | 저장 · 회원 · 결제 같은 서버 기능이 필요하다 ("예약") | 코드 작업 열기 → 코드 러너가 기능 패키지로 개발 · 테스트 → PR → 머지 → 배포(사람) → 켤 때 권한 허락 → ①로 앱 만들기 | 3 + 배포 |

## 5. 화면

화면을 먼저 정하고, 화면이 필요로 하는 데이터에서 API · 표를 정한다. 구현 순서는 지금 규칙대로 표 → 서버 → 웹이다 (웹의 타입은 서버 View에서 온다, `.claude/rules/web.md`).

### 콘솔

독(DOCK)에 "스토어"를 더한다 (대화 · 팀 · **스토어** · 오피스 · 승인 · 보관함). 설정의 "블로그 › 블로그 메뉴"는 앱 관리 안으로 옮긴다.

| 화면 | 주소 | 내용 |
|---|---|---|
| 내 앱 | `/admin/store` | 만든 앱 카드: 종류 · 이름 · 주소 · 공개 여부 · 글 수 · 승인 대기 · 운영 팀. "열기"(공개 주소) · "관리". 위에 "앱 만들기" |
| 스토어 | `/admin/store/new` | 앱 종류 카드: 블로그 · 매거진 · 페이지 앱 · 커뮤니티(준비 중) · 기능 패키지가 더한 종류. "만들기" → 만들기 시트. "대화에서 만들기" 안내 |
| 만들기 시트 | (시트) | 아이콘(그림 올리기, 없으면 종류 아이콘) · 이름 · 주소(`/` 뒤, 못 쓰는 이름은 바로 알림) · 설명 · 운영 팀(템플릿으로 만들기 · 있는 팀 · 나중에) · 시작 메뉴(종류마다 기본 세트). 비공개로 만들어진다 |
| 앱 관리 | `/admin/store/<앱 id>?tab=` | 머리: 아이콘 · 이름 · 종류 · 주소 · 공개 전환. 탭: 개요(든 것의 수 · 최근 글. 승인 대기 · 운영 팀의 진행은 2단계) · 메뉴(옛 설정 › 블로그 메뉴, 호 관리는 `/admin/store/<앱 id>/m/<메뉴 id>`) · 글(이 앱의 글, 새 글은 이 앱에 넣어 편집기로) · 설정(이름 · 주소 · 설명 · 순서 · 아이콘 · 삭제). 운영 팀 탭은 2단계 |
| 대화의 제안 카드 | (대화) | 지금 설정 바꾸기 카드 그대로: "새 앱: 요리 블로그 (/cooking, 블로그)" · "새 에이전트 3" 줄, 승인 · 수정 요청 · 반려 |

보관함의 "글" · "페이지"는 그대로 두고 앱으로 거르는 칩을 더한다.

### 공개 화면 (방문자)

| 주소 | 내용 |
|---|---|
| `/` | 설정 › 사이트의 "첫 화면"을 따른다. 기본은 "자동": 공개 앱 0개면 사이트 이름 · 소개 · "공개한 앱 없음", 1개면 그 앱의 첫 화면, 2개 이상이면 앱 아이콘 목록(휴대폰 홈 화면처럼 아이콘 · 이름 · 종류, 누르면 그 앱으로). 앱 하나로 고정할 수도 있다 |
| `/<앱>` | 그 앱의 첫 화면: 앱 설명 · 글 목록 (매거진은 최신 호, 페이지 앱은 그 페이지 또는 앱 코드의 첫 화면) |
| `/<앱>/<이름>` | 페이지 앱의 다른 화면 (앱 코드의 `<이름>.html`, 또는 앱의 페이지가 화면이면 그 페이지의 파일, 9.11.4) |
| `/<앱>/posts/<글>` · `/<앱>/m/<메뉴>` · `/<앱>/rss.xml` | 지금 화면에 앱 주소가 앞에 붙는다 |
| `/posts/<글>` · `/m/<메뉴>` · `/rss.xml` | 기본 앱의 새 주소로 넘긴다 (308) |
| 비공개 앱의 모든 주소 | 없는 주소와 같은 404 ("없는 페이지"). 응답 · 문구가 같아 앱이 있다는 사실도 드러나지 않는다 (원칙 5) |

- 앱 아이콘은 앱마다 올린 그림, 없으면 종류의 선 아이콘. 순서는 내 앱 화면에서 끌어 정한다.
- 머리는 한 줄. 앱 목록(`/`)에서는 로그인만, 앱 안에서는 왼쪽 끝 "모든 앱" 버튼(앱 목록으로) · 앱 아이콘 · 앱 이름 · 그 앱의 메뉴 · 그래프 · 로그인. 공개 앱이 하나뿐이면 "모든 앱" 버튼이 없다.
- 아래쪽에 다른 공개 앱 링크와 그 앱의 RSS.
- 그래프는 사이트 하나 (공개 앱의 공개 글만). 공개 글이 없으면 링크를 숨긴다.
- 관리자가 로그인해 있어도 공개 화면은 방문자와 같다 (지금 규칙). 다른 점은 오른쪽 끝 "로그인" 대신 "콘솔". 비공개 앱은 앱 관리의 미리 보기로 본다.
- 오른쪽 끝 "로그인"은 관리자 로그인이다. 커뮤니티(3단계)에서 회원 로그인이 생기면 이 자리를 다시 정한다.

## 7. 바뀌는 원칙 · 문서

- 기획서 1장: "결과를 블로그로 내보낸다" → "결과를 스토어의 앱으로 내보낸다".
- 결정 기록: "블로그 → 스토어와 앱"(이 문서).
- 커뮤니티 단계에서 원칙 10을 더하고 원칙 2에 예외 하나를 둔다 (2026-11-19 승인, AGENTS.md): 회원은 콘솔 · 보관함 · 작업 · MCP에 닿지 않고 회원 글의 삭제 · 제재는 관리자 승인으로만. 탈퇴한 회원의 개인정보는 지운다 (개인정보보호법).
- 그대로: vault와 blog는 서로 의존하지 않는다, 비공개가 기본, 위험한 동작은 승인 뒤.
- 관련 문서: 테이블설계(store · blog의 `app_id`), API설계(`api/apps` · `api/app-types`), 객체설계 모듈 지도, 보관형식(앱 폴더), README(스토어).

## 8. 1단계 인터페이스 (승인 2026-11-18, 끝남)

### 8.0 설계안과 달라지는 점

| 설계안 | 바꾸자는 것 | 까닭 |
|---|---|---|
| 새 `store` 모듈이 `apps`를 갖고 blog는 `app_id`를 값으로, 공개 여부는 `Lookups`로 묻는다 | **`apps` 표를 blog 모듈(스키마 `blog`)에 둔다.** 코드 자리는 `blog/app/`, 화면 이름만 "스토어" | 글이 방문자에게 보이는가 = "글이 공개 **그리고** 앱이 공개"다. 같은 스키마면 SQL 조건 하나로 거른 뒤 개수 · 순서를 센다 (원칙 5). 다른 모듈이면 방문자 요청마다 `Lookups`로 묻고 결과로 다시 걸러야 해서 목록 · 개수 · 사진 · 호 · RSS 곳곳에 새는 틈이 생긴다. 3단계 커뮤니티 모듈은 blog가 `Lookups`로 내주는 `app`을 묻는다 |
| `/rss.xml`은 기본 앱으로 넘긴다 | `/rss.xml`은 **사이트 전체**(공개 앱의 공개 글)로 둔다. 앱마다는 `/<앱>/rss.xml` | "기본 앱"을 따로 정하지 않아도 되고, 구독자의 주소가 그대로 산다 |
| 1단계에 운영 팀 고르기 · 첫 화면 고정 | 2단계로 (6장의 2단계와 맞춤). 1단계 만들기 시트에서 "운영 팀" 칸을 뺀다 | 1단계는 앱의 뼈대와 공개 범위만. 메뉴의 운영 팀은 지금처럼 메뉴마다 |

### 8.1 표 (마이그레이션 하나 `blog_apps`)

```sql
CREATE TABLE blog.apps (
  id uuid PRIMARY KEY,                       -- UUIDv7
  space_id uuid NOT NULL,
  kind text NOT NULL CHECK (kind IN ('blog', 'magazine', 'page')),   -- 만들 때만
  name text NOT NULL,                        -- 1~40자
  slug text NOT NULL,                        -- 영어 소문자 · 숫자 · 하이픈 2~30자, 못 쓰는 이름 제외 (App.RESERVED)
  description text NOT NULL DEFAULT '',      -- 200자, 앱 목록 · 앱 첫 화면
  visibility text NOT NULL DEFAULT 'private' CHECK (visibility IN ('private', 'public')),
  sort integer NOT NULL DEFAULT 0,
  icon_blob_hash text,                       -- BlobStore.registerUse에 등록
  version integer NOT NULL DEFAULT 1,
  created_at timestamptz NOT NULL, updated_at timestamptz NOT NULL,
  UNIQUE (space_id, slug)
);
ALTER TABLE blog.menus ADD COLUMN app_id uuid REFERENCES blog.apps(id);   -- 옮긴 뒤 NOT NULL
ALTER TABLE blog.posts ADD COLUMN app_id uuid REFERENCES blog.apps(id);   -- NULL = 아직 앱에 없는 글
ALTER TABLE blog.pages ADD COLUMN app_id uuid REFERENCES blog.apps(id);   -- NULL = 앱 밖의 페이지 (지금처럼 /pages/<이름>/)
-- 메뉴 주소는 공간에서 하나 → 앱 안에서 하나: UNIQUE (space_id, slug) → UNIQUE (app_id, slug)
```

- **옮기기** (같은 마이그레이션): 글 · 메뉴 · 페이지가 있는 공간마다 기본 앱 하나 (블로그, 주소 `blog`, 이름 "블로그", **공개** — 지금 블로그가 공개라서). 모든 메뉴 · 글과 메뉴에 올린 페이지를 그 앱으로. 새로 설치한 곳은 앱이 없다.
- 글의 주소 · 페이지 이름은 지금처럼 공간에서 하나다 (`/posts/<글>`이 어느 앱인지 찾아 넘길 수 있게).
- 앞뒤가 맞아야 하는 것 (엔티티가 지킨다): 글을 메뉴 · 호에 올리면 글의 앱 = 그 메뉴의 앱. 앱에 없는 글은 공개 · 링크만으로 바꿀 수 없다.

### 8.2 방문자에게 보이는 것 (한 곳의 규칙)

| 대상 | 보이는 조건 |
|---|---|
| 앱 | `visibility = 'public'` |
| 글 | 지금 조건 **그리고** 앱이 공개 (앱 없는 글은 안 보임) |
| 메뉴 · 호 | 그 앱이 공개 (호는 지금처럼 발행한 것만) |
| 페이지 | 지금 조건 **그리고** (앱 밖이거나 앱이 공개) |
| 사진 | 방문자에게 보이는 글에 붙어 있음 |
| 앱 아이콘 | 앱이 공개 |
| 그래프의 글 | vault의 글 자리 사본에 앱 공개 여부를 더해 거른다 (8.5) |

조건은 같은 SQL 한 줄(`a.visibility = 'public'`)을 각 방문자 읽기(글 · 메뉴 · 호 · 페이지 · 사진 · 아이콘)에 걸고, 보이지 않는 것은 없는 것과 같은 404다. DB도 앱 없는 글의 공개와 메뉴 · 앱이 어긋나는 것을 막는다 (CHECK · 외래키). 테스트가 비공개 앱의 것을 하나씩 확인한다 (`app.api.test`).

### 8.3 REST

새 `api/apps` (묶음 `blog/app/`: `App` · `AppService` · `AppQuery` · `AppRepository` · `AppEdit` · Input · View):

| 요청 | 누가 | 하는 일 | 오류 |
|---|---|---|---|
| `GET api/apps` | 누구나 | 방문자: 공개 앱 `[{ slug, name, kind, description, iconUrl }]` 순서대로 (id는 내보내지 않는다). 관리자: 모든 앱 + `id · visibility · sort · version · counts { published, drafts, menus, pages }` | |
| `GET api/apps/by-slug/:slug` | 누구나 | 앱 머리 하나 (방문자는 공개 앱만) | 404 |
| `POST api/apps` | 관리자 | `{ requestId, kind, name, slug?, description?, menus?: string[], pageId? }` → 앱(비공개) + 시작 메뉴(블로그: 글, 매거진: 호, `menus`를 주면 그 이름들의 글 목록 메뉴, 5개까지). 페이지 앱은 `pageId`를 주면 그 페이지를 앱에 넣는다 (없으면 화면은 앱 코드, 2-6에서 바꿈) | 422 주소 형식 · 못 쓰는 이름 · 페이지 앱의 메뉴, 409 주소 겹침, 404 페이지 |
| `PATCH api/apps/:id` | 관리자 | `{ version, name?, slug?, description?, visibility?, sort? }` (종류는 못 바꿈) | 409 버전 · 주소 겹침, 422 |
| `POST api/apps/:id/delete` | 관리자 | `{ version }`. 글 · 페이지가 없을 때만, 빈 메뉴는 함께 지운다 | 409 "글 N개 · 페이지 N개가 있어요" |
| `PUT api/apps/:id/icon?version=` · `POST api/apps/:id/icon/delete` | 관리자 | 사이트 로고와 같은 모양 · 한도 (PNG · JPEG · WebP, SVG는 받지 않음) | 413 · 415 · 409 |
| `GET api/apps/by-slug/:slug/icon` | 누구나 | 공개 앱의 아이콘 (관리자는 비공개도) | 404 |

바뀌는 것:

| 요청 | 바뀌는 점 |
|---|---|
| `GET api/posts` | `?app=<앱 주소>` 거르기. `?menu=`는 `app`과 함께 (메뉴 주소가 앱 안에서 하나가 되어서) |
| `GET api/posts/by-slug/:slug` | 답에 `app: { slug, name } \| null`. 웹이 다른 앱 주소로 온 요청을 맞는 주소로 넘긴다 |
| `POST api/posts` | 새 글을 앱에 넣을 때 `appId?` (고쳐 쓰기 `PUT`이 아니라 올리기 API로 앱을 바꾼다: 앱 · 메뉴를 한 곳에서) |
| `POST api/posts/:id/menu` | `{ version, menuId \| null, appId? }`: 메뉴를 주면 앱은 그 메뉴의 앱, 메뉴 없이 앱만 주면 메뉴에서 빼고 그 앱으로 |
| `POST api/posts/:id/status` · 승인한 발행 | 앱에 없는 글이면 422 "앱에 넣은 뒤 공개해요" (승인한 발행은 `publish_failed`). 결과 카드 전의 확인(`PostQuery.publishProblem`)도 같은 말을 먼저 짚는다 |
| `GET api/menus` · `POST api/menus` | 목록은 `?app=` (방문자는 꼭), 만들기는 `appId`가 꼭. View에 `appId` |
| `GET api/issues/by-number/:menu/:number` | `by-number/:app/:menu/:number` |
| `PATCH api/pages/:id` | `appId?`(페이지를 앱에 넣기 · 빼기). 페이지 앱의 페이지는 앱을 지우기 전에는 뺄 수 없다 |
| `GET api/pages/site/*path` | 앱이 비공개면 방문자에게 404 |

### 8.4 대화 (설정 바꾸기)

`BlogSettings`에 하나 더 등록한다 (메뉴와 같은 모양):

```ts
AppEdit.SETTING = {
  setting: 'app', list: 'apps', ops: ['create', 'edit'],
  fields: ['name', 'slug', 'kind', 'description', 'sort', 'menus'],   // kind · menus는 만들 때만
  target: 'id', versioned: true, grants: [],
}
```

- `get_settings apps`: 앱 목록 (공개 여부는 읽기만).
- **AI는 공개 여부를 제안하지 못한다**: 페이지와 같은 규칙 (AI · 기기가 공개하는 길은 없다). 공개는 앱 관리의 전환 하나.
- 결과는 지금처럼 `blog.setting.changed`. 만들기의 `requestId`는 결재 키.

### 8.5 이벤트와 vault

- 새 이벤트 `blog.app.changed { appId, visibility, appVersion, deleted? }`: 공개 여부가 바뀌거나 앱을 지울 때.
- `blog.post.*`에 `appId`(없으면 null)를 더한다.
- vault: 글 자리 사본(`vault.post_marks`)에 `app_id`, 새 표 `vault.app_marks(app_id, space_id, public, app_version)`. `appVersion`이 더 큰 이벤트만 받는다 (글 자리 사본과 같은 규칙). 그래프의 방문자 읽기가 둘을 이어 SQL에서 거른다. 앱을 비공개로 바꾸면 행 하나만 바뀐다.

### 8.6 보관 형식 (번호 그대로, "있으면"만 더함)

- 새 파일 `blog/apps/<주소>.yml` (앱 하나에 파일 하나): `cairn_id · kind · name · slug · description · visibility · sort · icon?`. 아이콘은 사진처럼 `assets/<해시>.<확장자>`.
  앱마다 파일을 나눈 까닭: 공개 여부가 파일 단위라, 목록 파일 하나면 비공개 앱의 이름이 공개 저장소로 나간다.
- 글 앞부분에 있으면 `cairn_app`(앱 id).
- 공개 저장소에는 공개 앱의 파일과, 공개 앱에 든 공개 글 · 그 사진 · 공개 앱의 아이콘만 보낸다.
- 복원: 앱 파일이 있으면 앱부터 만든다 (id · 종류 · 공개 여부 · 아이콘 그대로, 버전은 1부터). 글이 없는 앱을 가리키거나, 공개 · 링크 공개 글이 앱 밖에 있으면 어느 글인지 알리고 멈춘다.
- 옛 백업: 앱 파일이 하나도 없는데 공개 · 링크 공개 글이 있으면 앱이 생기기 전의 백업으로 보고, 마이그레이션과 같은 기본 앱(블로그, `/blog`, 공개) 하나에 모든 글을 넣는다. **기본 앱의 id는 공간 id**라는 형식 규칙을 두어, blog와 vault가 서로를 모른 채 같은 앱을 가리킨다 (vault는 그 id로 그래프 사본을 만든다). 임시 글만 있으면 앱 없이 들어온다 (앱이 없는 Cairn을 왕복해도 앱이 생기지 않게).
- 메뉴 · 호 · 페이지는 지금처럼 싣지 않는다. 페이지 앱은 페이지 없이 들어오고 복원 결과에 알린다.

### 8.7 웹

| 자리 | 하는 일 |
|---|---|
| `/` | `GET api/apps` → 0개 "공개한 앱 없음", 1개 그 앱의 첫 화면, 2개 이상 앱 아이콘 목록 (시안 6 · 7 · 8번) |
| `app/(blog)/[app]/…` | 앱 첫 화면(블로그: 글 목록, 매거진: 최신 호, 페이지 앱: 그 페이지를 틀로) · `posts/[slug]` · `m/[menu]` · `m/[menu]/[number]` · `rss.xml` |
| 옛 주소 | `/posts/<글>` → 그 글의 앱 주소로 **307** (계속 두는 고정 주소: 그래프 · 편집기 · 보관함 링크는 그대로). `/m/<메뉴>` · `/m/<메뉴>/<번호>` · `/m/<메뉴>/rss.xml` → 그 주소의 메뉴가 있는 첫 공개 앱으로 307. 308이 아닌 까닭: 글은 다른 앱으로 옮길 수 있고 앱은 비공개가 될 수 있어 넘길 곳이 바뀐다 (308은 브라우저가 기억해 옛 자리로 계속 보낸다). 방문자에게 안 보이는 글(초안 · 비공개 앱 · 앱 밖)은 관리자에게만 고정 주소에서 미리 보기로 그린다 |
| `app/not-found.tsx` | 한국어 404 "없는 페이지" · "첫 화면으로". 비공개 앱과 없는 앱은 `[app]/layout`이 같은 공개 앱 목록으로 판단해 같은 응답 · 같은 일이다 |
| 콘솔 | 독에 스토어(`/admin/store`: 탭 내 앱 · 스토어) · 스토어(`/admin/store/new`: 종류 카드 · 만들기 시트, 아이콘은 만든 뒤 올림) · 앱 관리(`/admin/store/[id]`: 개요 · 메뉴 · 글 · 설정). 설정의 "블로그 메뉴"는 앱 관리 › 메뉴로 옮기고 지운다. 글 편집기의 발행 창에 앱 고르기(저장한 글은 바로 옮기고, 새 글은 첫 저장에 함께, 앱 관리 › 글의 "새 글"은 `?app=`). 보관함의 메뉴 고르기는 "앱 › 메뉴". 비공개 앱의 미리 보기는 1-6(앱 코드)에서 |

앱 주소로 못 쓰는 이름(`App.RESERVED`): `admin · api · apps · assets · connect · files · graph · install · login · m · mcp · oauth · pages · posts · rss · share · store` (점 · 밑줄이 든 `_next` · `.well-known` · `sw.js`는 주소 모양에서 이미 막힌다). 구조 검사가 웹의 최상위 경로 폴더와 이 목록을 맞춰 본다.

### 8.9 나중에 생길 일에 버티는 법 · 고르지 않은 것

| 나중에 | 지금 모양이 버티는 법 |
|---|---|
| 커뮤니티 모듈 (3단계) | blog가 `Lookups`에 `app`을 내주고, 커뮤니티는 `app_id`를 값으로 갖는다 |
| 기능 패키지가 새 앱 종류 (4단계) | 그때 `kind`의 CHECK를 목록 표로 바꾸고 `api/app-types`를 연다 (테이블설계 0장: 자주 늘어날 종류는 목록 표). 지금은 셋뿐이라 CHECK |
| 앱마다 도메인 (4단계) | `apps`에 칸 하나 (`domain`). 주소 규칙은 그대로 |
| 앱마다 운영 팀 · 편집 방침 · 첫 화면 고정 (2단계) | `apps`에 칸을 더한다. 메뉴의 운영 팀 규칙(`AgentDirectory`)을 그대로 쓴다 |

고르지 않은 것: 별도 `store` 모듈(8.0) · 글이 꼭 앱에 들게(`app_id NOT NULL`: AI 초안마다 "어느 앱"을 짐작해야 한다. NULL = 앱에 없는 글이 분명하고 안전하다) · 글 주소를 앱 안에서 하나로(`/posts/<글>`로 찾아 넘기는 길이 없어진다) · 앱 휴지통(비어 있을 때만 지우면 충분하다) · 앱 순서를 한 번에 바꾸는 API(`PATCH`의 `sort`로 충분하다).

## 9. 1-6 앱 코드 인터페이스 (승인 2026-11-18)

시안: https://claude.ai/artifact/SAj3KxEguDUErcJXVdTh9P 의 넷째 줄 (코드 탭 · 미리 보기 · 대화 카드 · 시작 코드로 만든 앱 · 직접 쓴 코드의 앱). 2026-11-18 결정(기획서)으로 1-6 "앱 테마"를 "앱 코드"로 바꾼다.

### 9.0 한 장 요약

- **앱 = 자기 코드 묶음(HTML · CSS · JS · 그림) + Cairn의 데이터(글 · 메뉴 · 호).** 앱끼리 코드를 나누지 않는다. 공통 템플릿 · 테마 값이 없다.
- 코드는 **버전으로 쌓는다** (추가만). 공개 앱의 새 버전은 확인 대기로 두고, 관리자가 미리 보고 "이 버전 공개"를 누를 때 바뀐다 (페이지와 같은 규칙, 원칙 7).
- 앱 코드는 **우리 서버에서 실행되지 않는다.** 로직 없는 템플릿(Mustache)에 데이터를 채운 HTML을 브라우저로 보낼 뿐이다.
- 앱 화면은 **격리해서 연다** (CSP `sandbox`). 앱의 JS는 다른 출처로 취급되어 로그인 · 콘솔 API에 닿지 못한다. 바깥 주소는 그 버전의 `cairn.json`에 적은 호스트만.
- 코드가 없는 앱은 **종류의 시작 코드**로 보인다. 처음 고칠 때(AI 작업 · zip 올리기) 시작 코드 위에 버전 1이 생긴다.
- 1-4의 공개 화면 컴포넌트는 시작 코드(템플릿)로 옮기고 지운다. 앱 화면을 그리는 길은 하나다.

### 9.1 표 (마이그레이션 하나 `blog_app_code`)

```sql
CREATE TABLE blog.app_code_versions (
  id         uuid PRIMARY KEY DEFAULT platform.uuid_v7(),
  app_id     uuid NOT NULL,              -- blog.apps의 id (값). 앱을 지워도 버전은 남는다 (원칙 2)
  space_id   uuid NOT NULL,
  seq        int  NOT NULL CHECK (seq >= 1),
  files      jsonb NOT NULL CHECK (jsonb_typeof(files) = 'array'),   -- [{ name, blobHash, mime, sizeBytes }] 페이지 버전과 같은 모양
  source     text NOT NULL CHECK (source IN ('starter', 'upload', 'task', 'restore')),
  task_id    uuid,                       -- source = 'task'일 때만 (task의 것, 값)
  run_id     uuid,
  note       text NOT NULL DEFAULT '' CHECK (char_length(note) <= 2000),   -- 요청 글 · 올린 파일 이름
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT app_code_versions_seq UNIQUE (app_id, seq),
  CONSTRAINT app_code_versions_run UNIQUE (app_id, run_id),             -- 같은 이벤트를 두 번 받아도 버전은 하나
  CONSTRAINT app_code_versions_task CHECK ((source = 'task') = (task_id IS NOT NULL AND run_id IS NOT NULL))
);
-- 추가만: BEFORE UPDATE OR DELETE 트리거 platform.forbid_update_delete()

ALTER TABLE blog.apps
  ADD COLUMN code_seq         int,                          -- 방문자에게 보이는 버전. NULL = 시작 코드
  ADD COLUMN code_pending_seq int,                          -- 확인 대기 버전 (공개 앱만)
  ADD COLUMN code_versions    int NOT NULL DEFAULT 0,       -- 쌓인 버전 수
  ADD CONSTRAINT apps_code_seq CHECK (code_seq IS NULL OR code_seq BETWEEN 1 AND code_versions),
  ADD CONSTRAINT apps_code_pending CHECK (code_pending_seq IS NULL OR code_pending_seq BETWEEN 1 AND code_versions);
```

- 파일 내용은 지금처럼 BlobStore에 두고 버전마다 `registerUse`로 등록한다.
- 지금 있는 앱은 옮길 것이 없다 (`code_seq` NULL = 시작 코드).
- 버전을 바꾸면 `apps.version`이 오른다 (낙관적 잠금은 앱 하나로).

### 9.2 코드 묶음 규칙

| 규칙 | 값 |
|---|---|
| 파일 | 100개까지, 폴더 없는 이름, 형식 표는 페이지와 같다 (`PageFiles`를 그대로 쓴다). `index.html`이 꼭 있다 |
| 크기 | 버전 하나 20MB, 템플릿(`.html`)은 합쳐 1MB |
| 화면 → 템플릿 | 첫 화면 `index.html` · 글 `post.html` · 메뉴 목록 `list.html` · 호 `issue.html` · 앱 안의 없는 주소 `404.html`. 없으면 `index.html` (404는 Cairn의 404). 페이지 앱은 `/<앱>/<이름>` → `<이름>.html` (없으면 앱 안의 없는 주소, 9.11.4) |
| 부분 템플릿 | `{{> header}}` → 같은 묶음의 `header.html` |
| 정적 파일 | `{{files}}/style.css` → `/<앱>/files/style.css` |
| `cairn.json` (있으면) | `{ "cairn": 1, "hosts": ["fonts.googleapis.com", "fonts.gstatic.com"] }`. 호스트 10개까지, 정확한 이름만 (와일드카드 · IP · 포트 없음, https로만 연다) |

AI 작업의 결과는 바꾼 파일만 앞 버전 위에 얹는다 (`PageFiles.overlay`). 파일을 지우는 것은 zip 올리기(묶음 전체)로 한다.

위는 템플릿 앱의 규칙이다. 페이지 앱은 `cairn.json`에 `"render": "static"`을 넣어 템플릿 없는 정적 앱이 될 수 있고, 그때는 폴더를 쓴다 (9.13).

### 9.3 데이터 약속 (`cairn: 1`)

템플릿에는 아래 데이터가 들어가고, 같은 값이 `<script type="application/json" id="cairn-data">`로 `</head>` 앞에 실린다 (앱 JS가 읽을 수 있게). 약속의 원본은 스킬 `cairn-make/references/app-code.md` 하나이고, AI와 사람이 같은 글을 본다.

| 이름 | 화면 | 값 |
|---|---|---|
| `cairn` · `screen` | 모두 | `1` · `'home' \| 'post' \| 'menu' \| 'issue'`, 섹션용 `isHome` · `isPost` · `isMenu` · `isIssue` |
| `base` · `files` | 모두 | 앱 주소 `/travel` (미리 보기는 `/travel/~<토큰>`) · 파일 주소 `/travel/files` |
| `title` | 모두 | 화면 제목 (앱 이름, 글이면 `글 제목 · 앱 이름`) |
| `site` | 모두 | `{ home: '/', loginUrl: '/login', graphUrl }` (공개 글이 없으면 `graphUrl` null). 웹이 `name`(사이트 이름)을 더한다 |
| `app` | 모두 | `{ name, description, kind, url, iconUrl, rssUrl }` |
| `apps` · `others` | 모두 | 공개 앱 `[{ name, url, iconUrl, current }]`, `others`는 이 앱을 뺀 것 (다른 앱으로 가는 줄, `{{#others.length}}`로 있을 때만) |
| `menus` | 모두 | `[{ name, url, kind, active }]` |
| `menu` | menu · issue · home(매거진: 첫 호 메뉴) | `{ name, url, kind, isPosts, isIssues, isPages, isPage, rssUrl }` |
| `posts` · `more` | home · menu | `[{ title, excerpt, url, date, tags }]` 20개씩 · 다음 쪽 `{ url } \| null` (`?cursor=`) |
| `post` | post | `{ title, excerpt, url, date, tags, body, html, center, listed, back }` (`body`는 md, 웹이 `html`로 그린다. `listed`가 거짓이면 링크 공개 글, `back`은 올린 메뉴 · 앱 첫 화면) |
| `issues` | home(매거진) · menu(호 메뉴) | `[{ number, title, intro, url, date }]` |
| `issue` | issue · home(매거진: 최신 호) | `{ number, title, intro, url, date, posts: [{ title, excerpt, url }] }` |
| `pages` | home(페이지 앱) · menu(페이지 메뉴) | 공개 페이지 `[{ title, url, date }]` |

- `html`이 붙은 값만 HTML(본문 md를 웹이 그려 거른 것)이라 `{{{ }}}`로 쓴다. 나머지는 `{{ }}`(이스케이프). 웹은 `date`가 있는 곳마다 `dateText`(예: `2026. 11. 16.`)를 더한다.
- 표지 그림(`coverUrl`)은 1-6a에 없다 (글에 대표 그림 칸이 아직 없다). 약속은 더하기만 하므로 나중에 더한다.
- 약속은 이름을 더하기만 한다. 빼거나 이름을 바꿀 때는 `cairn: 2`를 만들고 한동안 둘을 함께 받는다.

### 9.4 주소와 그리기 (웹)

| 주소 | 하는 일 |
|---|---|
| `/<앱>` · `/<앱>/posts/<글>` · `/<앱>/m/<메뉴>` · `/<앱>/m/<메뉴>/<번호>` (끝에 `/`를 붙이지 않는다: Next가 308로 한 번 더 보낸다) | route handler 하나(`app/(blog)/[app]/[[...path]]/route.ts`)가 ① 서버에서 화면 묶음을 받고(9.5) ② 본문 md를 HTML로 ③ 템플릿을 고르고 Mustache로 채우고 ④ 데이터 블록을 넣어 격리 머리글과 함께 보낸다 |
| `/<앱>/files/<이름>` | 서버의 파일을 그대로 흘려보낸다 (같은 격리 머리글) |
| `/<앱>/<이름>` (페이지 앱) | 앱 코드의 `<이름>.html`. 앱의 페이지가 화면이면(9.11.4) `/<앱>`은 `/<앱>/index.html`로 넘기고(307), `/<앱>/<파일>`은 그 페이지의 파일(`/api/pages/site/<페이지>/<파일>`)을 서버의 머리글(페이지의 격리 CSP) 그대로 흘려보낸다 |
| `/<앱>/~<토큰>/…` | 미리 보기. 같은 경로들을 그 토큰의 버전으로. `base`에 토큰이 들어 있어 링크를 눌러도 미리 보기 안에 머문다. 글 본문의 사진(`/api/files/<해시>`)에는 웹이 `?ticket=<토큰>`을 붙인다 (격리된 화면에는 쿠키가 실리지 않아 비공개 앱 글의 사진을 토큰으로 연다, 9.5) |
| `/<앱>/rss.xml` · `/<앱>/m/<메뉴>/rss.xml` | 지금 그대로 (앱 코드와 상관없는 Cairn의 RSS) |
| `/` | 공개 앱 0개 "공개한 앱 없음", **1개는 `/<앱>`로 307** (1-4는 그 자리에서 그렸다. 이제 앱 화면은 앱 코드가 그린다), 2개 이상 앱 아이콘 목록 (Cairn의 화면) |
| 없는 앱 · 비공개 앱 | 같은 Cairn 404 (앱 코드를 거치지 않으니 응답이 같다). 공개 앱 안의 없는 글은 그 앱의 `404.html`(상태 404), 없으면 Cairn 404 |
| 그리기 실패 (템플릿 문법) | 500 "앱 화면을 그리지 못했어요". 미리 보기에서는 파일 · 줄을 보인다. 공개 앱은 미리 보기 뒤에 공개하므로 방문자에게 가기 전에 보인다 |

격리 머리글 (앱 화면 · 앱 파일):

```
Content-Security-Policy: sandbox allow-scripts allow-forms allow-modals allow-popups allow-popups-to-escape-sandbox allow-downloads;
  default-src <사이트> <hosts>; script-src <사이트> 'unsafe-inline' <hosts>; style-src <사이트> 'unsafe-inline' <hosts>;
  img-src <사이트> <hosts> data: blob: https:; font-src <사이트> <hosts> data:; connect-src <hosts>; form-action <hosts>;
  base-uri 'none'; frame-ancestors 'self'
```

- `sandbox`에 `allow-same-origin`이 없어서 앱 화면은 출처 없는 문서다: 우리 쿠키가 실리지 않고, 쓰기 요청은 `ActorGuard`의 출처 확인에서 막히고, 앱 JS가 콘솔 API의 답을 읽지 못한다. 대신 앱 JS는 자기 저장소(localStorage · 쿠키)도 못 쓴다 (4단계 앱별 도메인에서 풀린다).
- `<사이트>`는 사이트 주소(`CAIRN_WEB_URL`)를 그대로 적는다 (출처 없는 문서에서 `'self'`가 맞지 않는 브라우저가 있어서). 그림은 글 본문이 바깥 그림을 쓰므로 https 어디서나.
- 웹의 화면 머리글(`frame-ancestors 'none'` · `X-Frame-Options`)은 `/`와 웹의 최상위 경로에만 붙인다. 목록 `WEB_ROUTES`는 `next.config.ts`에 두고 구조 검사가 웹의 최상위 폴더 · `App.RESERVED`와 맞춰 본다. 앱 주소의 머리글은 route handler만 붙인다 (두 CSP가 겹치거나 콘솔의 미리 보기 창이 막히지 않게).

### 9.5 REST (묶음 `blog/app-code/`)

`AppCode`(버전 · 확인 대기 규칙) · `AppCodeService` · `AppCodeQuery` · `AppSiteQuery`(화면 묶음) · `AppCodeRepository` · `AppTicket`(미리 보기 토큰: `PageTicket`과 같은 모양, 서버 키로 봉인, 용도 `app-view`, 30분, 앱 하나 · 버전 하나에 묶임) · 시작 코드 `blog/app-code/starters/<종류>/`.

| 요청 | 누가 | 하는 일 | 오류 |
|---|---|---|---|
| `GET api/apps/site/:slug/screen?path=&cursor=&ticket=` | 누구나 | 화면 하나에 필요한 것 `{ status, seq, template, templates: { 이름: 글 }, hosts, data, redirect: null, page: null }` 또는 페이지가 화면인 페이지 앱이면 `{ redirect: null, page: { name, file, base } }` (9.11.4) (`seq` 0은 시작 코드, 앱 안의 없는 주소는 `status` 404). 토큰이 없으면 공개 앱의 보이는 버전. 토큰이 있으면 그 앱 · 그 버전을 **공개된 것처럼** (그 앱의 공개 · 링크 공개 글만, 초안은 아님). 관리자가 토큰 없이 비공개 앱에 오면 `{ redirect }`(토큰 주소). 보는 사람이 누구든 데이터는 방문자 데이터다 | 404 (없는 앱 · 비공개 앱 · 틀린 토큰 모두 같은 404) |
| `GET api/apps/site/:slug/files/:name?ticket=` | 누구나 | 파일 하나. `ETag` = 해시, 공개는 짧은 캐시, 토큰은 `no-store` | 404 |
| `GET api/files/:hash?ticket=` (1-6b에 더함) | 누구나 | 글 사진. 지금 규칙(공개 앱의 공개 · 링크 공개 글 → 누구나, 나머지 → 관리자)에 더해, 미리 보기 토큰이 있으면 **그 토큰의 앱**에 든 공개 · 링크 공개 글의 사진도 (`no-store`). 앱 화면의 데이터와 같은 범위 | 404 (초안 · 다른 앱 · 틀린 토큰 모두 없는 파일과 같다) |
| `GET api/apps/:id/code` | 관리자 | `{ current, pending, versions: [{ seq, source, note, taskId, createdAt, fileCount, bytes }], files: [{ name, mime, sizeBytes }], hosts }` (`files`는 보이는 버전, 없으면 시작 코드) | 404 |
| `GET api/apps/:id/code/versions/:seq/changes` | 관리자 | 앞 버전과 비교 `{ added, changed, removed, hostsAdded, hostsRemoved, bytes }` (카드 · 코드 탭의 바뀐 점 줄) | 404 |
| `POST api/apps/:id/code/preview` | 관리자 | `{ seq? }` → `{ url }` (토큰 주소. 미리 보기 창 · 새 창) | 404 |
| `POST api/apps/:id/code/current` | 관리자 | `{ version, seq }` 이 버전 공개 (앞 버전으로 되돌리기도 같은 요청). 확인 대기를 비운다 | 409 버전, 404 |
| `POST api/apps/:id/code/versions?version=&note=` | 관리자 | zip 본문(20MB) → 201 새 버전(`upload`). 공개 앱은 확인 대기, 비공개 앱은 바로 보이는 버전 | 413, 415 zip 아님, 422 묶음 규칙(폴더 · 이름 · 개수 · `index.html` · `cairn.json`), 409 |
| `GET api/apps/:id/code/versions/:seq/zip` | 관리자 | 그 버전 zip (`seq` 0 = 시작 코드). zip은 `platform/base`의 `ZipFile` · `ZipReader` | 404 |
| `POST api/apps/:id/code/starter` | 관리자 | `{ version }` 시작 코드를 새 버전으로 (처음으로 되돌리기, 기록은 남음) | 409 |

- 공개 · 되돌리기 · 올리기 · 시작 코드는 **관리자 로그인만** (기기 토큰 · AI는 못 한다. 페이지와 같은 규칙).
- 앱 지우기(`POST api/apps/:id/delete`)는 지금 규칙 그대로. 코드 버전은 남는다.

### 9.6 AI로 고치기

1. 코드 탭의 "AI에게 맡기기" → 만들기 작업(`POST api/tasks`, kind `make`, payload `appCode: { appId }`, task의 `AppCodeOrder`, `PageOrder`와 같은 모양). 대화에서는 대표가 make 팀원에게 `delegate_task`의 하위 작업 `app_id`로 맡긴다 (9.11.2).
2. 러너: MCP `app_code_base { task_id }` → `{ app_id, name, kind, slug, seq, files: [{ name, size, text }], hosts }` (가장 새 버전, 없으면 시작 코드 `seq` 0. 글 파일은 내용까지 300KB)를 `inputs/app/`에 두고 지시문 틀 `make`의 `# 고칠 앱` 단락을 채운다(`AppCodeBase`). AI는 `cairn-make`의 앱 코드 지시(`references/app-code.md`)를 따라 바뀐 파일만 낸다. 러너가 받은 코드 위에 낸 파일을 얹어 검사하고(`AppCodeCheck`: 묶음 규칙 · 템플릿 문법 · 데이터 이름) `submit_result`의 checks로 올린다. 떨어지면 AI에게 한 번 더 맡기고(검증 고리 V), 묶음 · 문법이 그래도 틀리면 새 버전 없이 실패로 끝낸다 (9.11.3).
3. 작업이 끝나면 task가 `task.app_code.built { taskId, runId, appId, note, files }` → blog `AppCodeBuiltHandler` → 새 버전(`task`).
4. 공개 앱: 확인 대기 + `blog.app_code.added`(pending) → 알림 "앱 코드 확인 대기"(코드 탭으로, 공개하면 읽음). 코드 탭 · 미리 보기의 "이 버전 공개" = `POST …/code/current`. 공개하지 않아도 버전은 남는다. 비공개 앱: 바로 보이는 버전. 대화의 일이 낸 확인 대기 버전은 그 대화의 결과 카드에 공개 승인(`blog.app_code.show`)으로 실려, 고르면 공개된다 (9.11.2).
5. 이벤트: `blog.app_code.added { appId, name, seq, source, pending, taskId }`(`taskId`는 AI 작업이 만든 버전이면 그 작업, 아니면 null) · `blog.app_code.shown { appId, seq, settled }` · `blog.app_code.refused { appId, name, taskId, error }`(AI 결과가 묶음 규칙에 맞지 않아 버전을 만들지 못함 → 알림, 작업은 이미 끝났다) (`blog.events.json`에 등록).

### 9.7 콘솔

- 앱 관리에 탭 **코드** (시안): 버전 목록(확인 대기 · 공개 중 · 출처: 시작 코드 · zip 올림 · AI 작업 · 복원), 버전마다 미리 보기 · 이 버전 공개 · 되돌리기, zip 올리기 · 내려받기, 지금 버전의 파일, 바깥 주소(읽기만, 바꾸려면 `cairn.json`을 고친 새 버전), "AI에게 맡기기" 입력.
- 미리 보기 화면 `/admin/store/[id]/code/[seq]` (`seq`는 버전 번호 · `0` 시작 코드 · `live` 지금 보이는 코드): 데스크톱 · 폰(390px) 너비, 새 창, 앞 버전과 바뀐 파일 · 새 바깥 주소 한 줄, 이 버전 공개. 미리 보기 창(iframe)은 토큰 주소를 열고, 틀에도 같은 `sandbox`를 한 번 더 건다.
- "AI에게 맡기기" 입력은 보관함 › 페이지의 입력과 같은 부품(`_ui/InstructionForm`)이고, 고치는 중인 작업(`useAppCodeTasks`)을 그 아래에 보인다.
- 1-5에서 미룬 **비공개 앱 미리 보기**도 이것 (개요 탭의 "미리 보기").

### 9.8 보관 형식

- `blog/apps/<주소>/code/<파일>`: 보이는 버전의 파일, 이름 순서 (시작 코드면 쓰지 않는다). 공개 저장소에는 공개 앱의 코드만. 1-6c ✅ (`PostArchiveQuery.appCode`)
- 복원: 파일이 있으면 버전 1(`restore`)로 바로 보인다 (`RestoredAppCode`: 저장할 때와 같은 묶음 규칙, 들어오지 않는 앱의 코드면 멈춘다). 버전 기록과 확인 대기 버전은 싣지 않는다 (코드는 지금 모양이 곧 앱이다).

### 9.9 1-4에서 바뀌는 것

- `app/(blog)/[app]/`의 화면들(layout · page · posts · m)을 지우고 route handler 하나로. `_blog/`의 앱 화면 컴포넌트(AppShell · AppHeader · AppFooter · AppHome · PostList · IssueBody · PageFrame)는 시작 코드 셋(블로그 · 매거진 · 페이지 앱)의 템플릿으로 옮기고 지웠다 (1-6b). 지금 모습 그대로 옮겨서 있는 앱의 화면은 바뀌지 않는다. `PostArticle`은 관리자의 앱 밖 · 초안 글 미리 보기(`/posts/<글>`)가 계속 쓴다.
- `_lib/markdown`은 그대로 (편집기 미리 보기와 route handler가 쓴다).
- 고정 주소 `/posts/<글>` 307과 관리자의 앱 밖 · 초안 글 미리 보기는 Cairn 화면 그대로.
- 글 화면의 플러그인 자리(`Slot`, comments-giscus)는 앱 코드 데이터에 없다. 플러그인 계약을 바꾸는 일이라 따로 결재한다 (그 전에는 앱 코드에 giscus 스크립트를 넣고 `hosts`에 `giscus.app`).

### 9.11.1 1-6a에서 정한 것 · 1-6b로 넘기는 것

- 서버의 화면 데이터는 `AppScreenQuery`가 앱을 먼저 정한 뒤(공개 앱 또는 토큰의 앱) 그 앱 안만 읽는다: 앱 공개 조건을 다른 Query마다 넓히지 않고, 토큰 미리 보기도 같은 길로 비공개 앱의 공개 글을 본다.
- AI 결과가 묶음 규칙에 맞지 않으면 버전 없이 `blog.app_code.refused` 알림 (작업은 이미 끝나 되풀이하지 않는다). 그사이 다른 버전이 생겼으면 409로 일꾼이 다시 받아 새 바탕 위에 얹는다.
- 시작 코드는 `apps/server/starters/`(base + 종류)이고 서버 이미지에 함께 든다. 템플릿 파일(Mustache)은 HTML로 읽히지 않아 Biome 검사에서 뺀다.
- 1-6b로: 비공개 앱 미리 보기의 글 사진(`/api/files/<해시>`)은 격리된 화면에 쿠키가 없어 보이지 않는다 → 1-6b에서 둘 다 했다 (웹이 토큰을 싣고 파일 API가 받는다, 9.11.2). 페이지 앱의 시작 코드는 페이지를 틀로 넣지 않고 링크로 보인다 (출처 없는 화면 안에서는 `frame-ancestors 'self'`가 맞지 않는다). → 2026-11-20 틀로 넣지 않고 페이지가 화면 자체가 되게 했다 (9.11.4).

### 9.11.2 1-6b에서 정한 것 · 미룬 것

- 앱 주소의 끝 `/`를 없앴다 (`/dev`, `/dev/~<토큰>`): Next가 끝 `/`를 308로 한 번 더 보내서 토큰 주소 · 미리 보기 창이 두 번 오갔다. 서버의 `base` · 앱 주소 · 미리 보기 주소 · 시작 코드의 링크가 모두 끝 `/` 없이.
- 미리 보기의 글 사진: 웹이 미리 보기에서만 본문 HTML의 `/api/files/<해시>`에 토큰을 붙이고, 파일 API가 토큰의 앱 · 공개 범위를 본다 (9.5). 토큰은 이미 주소에 있으므로 새로 드러나는 값은 없고, 미리 보기 화면은 `Referrer-Policy: no-referrer`다.
- 앱 JS가 콘솔 API에 닿지 못하는 까닭은 세 겹이다: ① `connect-src`에 사이트가 없다 ② 출처 없는 문서라 SameSite=Lax 쿠키가 실리지 않는다 ③ 응답에 CORS 허락이 없다. 관리자가 `cairn.json`의 `hosts`에 사이트 주소를 적어도 ②③이 남는다.
- **대화에서 앱 코드를 맡기는 길과 결과 카드 (1-6b 나머지, 2026-11-18).**
  - 맡기기: `delegate_task`의 하위 작업에 `app_id`를 적으면 그 make 일의 `payload.appCode { appId }`가 된다. make가 아닌 일에 적으면 `rule_violation`(`MakeOrder`). 주인이 고른 주문(`payload.make` · `page`)은 여전히 물려주지 않는다: `app_id`는 위 작업에서 물려받는 값이 아니라 대표가 적는 값이고, 그 결과는 공개 앱이면 확인 대기라 사람이 공개해야 방문자에게 보인다 (비공개 앱은 바로 보이지만 방문자에게는 없는 앱이다). 앱이 있는지는 위임 때 보지 않는다: 코드 탭의 `appCode`와 같이 러너의 `app_code_base`가 404, blog가 없는 앱의 결과를 버린다.
  - 결과 카드: `blog.app_code.added`에 `taskId`를 실었다. task의 `AppCodeCardHandler`가 그 작업이 대화의 일 아래이고 버전이 확인 대기(`pending`)일 때만 그 대화에 작업에 묶이지 않은 결재(`Approval.forAppCode`: 동작 `blog.app_code.show`, 대상 `app` · 판 = 버전 번호, 메모 "<앱> 버전 <n>")를 올린다. 같은 버전은 결재 하나 (`Idempotency`, 키 `<앱>:<버전>`). 결재에 `chat_id`가 있어 그 대화의 카드에 실린다.
  - 앱 코드 일의 결과물(파일)은 카드에 싣지 않는다 (`OutputRepository.uncardedInChat`가 `payload.appCode` 작업을 뺀다): 파일은 이미 버전이 되었고, 고르지 않은 결과물을 휴지통으로 보내는 카드 규칙이 버전과 어긋난다.
  - 승인하면 blog `AppCodeShowHandler`(`task.approval.granted` 중 `blog.app_code.show`) → `AppCodeService.showApproved`(`ApprovedActor`의 동작이 `blog.app_code.show`일 때만) → `AppCode.showApproved`: 그 버전이 아직 보이지 않을 때만 보인다. 그사이 관리자가 같은 버전이나 더 새 버전을 공개했으면 되돌리지 않고, 없는 버전 · 지운 앱이면 아무것도 하지 않는다. 작업에 묶이지 않은 결재라 결과를 task에 돌려주지 않는다. 고르지 않으면 반려되고 버전은 확인 대기로 남는다 (코드 탭에서 공개할 수 있다).
  - 카드 항목에 `targetVersion`을 실었다: 웹은 이 동작에 "미리 보기"(콘솔의 그 버전 미리 보기 `/admin/store/<앱>/code/<버전>`)를 붙인다.
- 미룸(그대로): 글 화면의 플러그인 자리(giscus, 9.9), 페이지 앱의 페이지를 틀로 넣기(9.11.1, → 9.11.4에서 페이지가 화면).

### 9.11.3 1-6c에서 정한 것

- **검사는 러너가 한다 (스킬의 검사 스크립트 대신).** 서버가 보내는 스킬 판은 `SKILL.md`와 `references/*.md`만 싣는다 (task `SkillFiles`): 스킬에 스크립트를 두면 콘솔에서 고친 판으로 돌 때 빠진다. 러너에는 런타임 의존 패키지가 없어(Dockerfile) Mustache 라이브러리 대신 태그만 훑는 `AppCodeCheck.scan`을 두었다: 여닫는 짝 · 없는 조각 · `{{{ }}}`/`{{& }}`는 `html` 값에만 · 구분자 바꾸기 금지 · 닫히지 않은 태그. 시작 코드 셋이 이 검사를 지나는지 러너 테스트가 본다.
- 검사 셋: `앱 코드 묶음`(받은 코드 위에 얹어 100개 · 합 20MB · 템플릿 합 1MB · `index.html`, 낸 `cairn.json`의 모양 — 서버 `AppCodeBundle`과 같은 한도) · `템플릿 문법` · `데이터 이름`. 묶음 · 문법은 일을 실패로 끝낸다(서버는 Mustache를 읽지 않아 틀린 템플릿도 버전이 되고, 비공개 앱은 바로 보인다). 이름은 알리기만 한다(없는 이름은 빈 칸으로 그려질 뿐이다).
- 데이터 이름 목록은 러너의 `AppCodeCheck.NAMES`다. 약속은 이름을 더하기만 하므로, 서버 테스트(`app-screen.view.test`)가 모든 화면의 데이터 이름(+ 웹이 더하는 `html` · `dateText` · `name`)이 그 목록에 있는지 본다. 약속에 이름을 더하면 그 목록에도 더한다.
- AI가 낸 템플릿 · `cairn.json`은 러너가 agent 권한으로 읽는다(`AgentUser.readFile`): AI가 둔 링크를 러너가 따라가지 않게.

### 9.11.4 페이지 앱 자유도 P1 (2026-11-20, 사용자 결정 "넵 진행")

페이지 앱이 블로그 · 매거진과 같은 모양(머리 · 메뉴 · 꼬리)으로 나오던 까닭은 시작 코드가 base(블로그 틀) 위에 얹혔고, 화면이 첫 화면 하나뿐이었고, 앱의 페이지를 링크로만 보였기 때문이다. 넷을 바꿨다.

| 무엇 | 바꾼 것 |
|---|---|
| ① 빈 시작 코드 | `starters/page/`는 base 없이 자기 셋만(`index.html` · `style.css` · `icon.svg`, `AppStarterGateway.ALONE`): 앱 이름 · 설명과 "모든 앱" 링크(다른 공개 앱이 있을 때)만 있는 빈 화면, 밝은 · 어두운 화면 모두. 다른 종류는 그대로 base + 종류 |
| ② 화면마다 템플릿 | 페이지 앱의 `/<앱>/<이름>`(한 단계, `^[a-z0-9][a-z0-9-]{0,59}$`, `index` · `404` 빼고)은 화면 `view` → 템플릿 `<이름>.html`. 데이터는 첫 화면과 같고 `isView` · `view`(이름)를 더한다. 그 템플릿이 없거나 더 깊은 주소면 앱 안의 없는 주소(404). 블로그 · 매거진의 주소 규칙은 그대로 |
| ③ 페이지가 화면 | 토큰 없이 연 공개 페이지 앱이 앱 코드를 아직 공개하지 않았고(`code_seq` 없음) 앱에 공개 페이지(버전 1 이상)가 있으면, 화면 API가 `{ redirect: null, page: { name, file, base } }`를 준다. 웹은 `/<앱>` → `/<앱>/index.html`(307), `/<앱>/<파일>` → 그 페이지의 파일을 서버의 머리글(페이지의 격리 CSP · `frame-ancestors 'self'`) 그대로. 페이지 안의 상대 경로(`style.css` · `data.json`)가 그대로 맞는다. 두 단계 이상은 404. 앱 코드를 한 번 공개하면 앱 코드가 화면이다 (확인 대기 버전은 아직 아니다). 미리 보기(토큰)는 늘 앱 코드다 |
| ④ AI 안내 | `cairn-make/references/app-code.md`의 "페이지 앱" 단락(빈 시작 코드에서 처음부터 · 흔한 템플릿 모양 피하기 · `<이름>.html` 화면), 앱 디자이너 역할 설명, 대표가 페이지 앱을 맡길 때 누가 · 무엇을 · 어떤 느낌인지를 지시에 적기, 검수의 "흔한 템플릿 모양이면 고칠 것" |

- 있는 공개 페이지 앱 중 앱 코드를 공개하지 않은 것은 화면이 바뀐다: 시작 코드(머리 · 메뉴 · 페이지 링크) → 페이지 자체(②③). 페이지가 없거나 비공개면 새 빈 시작 코드.
- 고르지 않은 것: 페이지를 앱 화면 안에 틀(iframe)로 넣기 — 출처 없는 화면 안에서는 `frame-ancestors 'self'`가 맞지 않고(9.11.1), 틀 안팎으로 화면이 둘이 된다. 페이지 파일을 앱 코드로 복사하기 — 자라는 페이지(`data.json` 갱신)와 버전이 둘로 갈린다.
- 남은 것: P2 페이지 앱의 `data.json`을 앱 코드에서 읽기, P3 앱이 방문자 데이터를 저장하기(원칙을 바꾸는 일이라 따로 정한다).

### 9.12 나중에 생길 일에 버티는 법 · 고르지 않은 것

| 나중에 | 지금 모양이 버티는 법 |
|---|---|
| 앱마다 도메인 (4단계) | 그 도메인에서는 진짜 다른 출처라 `sandbox`를 풀고 저장소 · 쿠키를 쓸 수 있다. 코드 묶음 · 데이터 약속은 그대로 |
| 커뮤니티 (3단계) | ~~방문자 로그인 · 글쓰기는 앱 JS가 부르는 공개 API(CORS, 앱별 토큰)로~~ → 바뀜 (11장, 2026-11-19): 로그인 · 글쓰기 · 댓글 · 신고는 Cairn이 그리는 고정 화면(같은 출처 쿠키 + CSRF). 격리된 앱 화면은 출처가 없어(`null`) 쿠키 · CORS를 열어 줘야 해서. 읽기 화면은 앱 코드 그대로, 데이터 약속에 이름을 더한다 (`cairn: 1` 그대로) |
| 폴더가 있는 앱 | 파일 이름 규칙(`PageFiles`)만 넓히면 된다 (`css/a.css`, `..` 금지) → 정적 앱에서 했다 (9.13, 2026-11-21) |
| 기능 패키지의 새 앱 종류 | 시작 코드 폴더 하나를 더한다 |

고르지 않은 것:

- **`blog.pages`를 앱 코드로 다시 쓰기**: 페이지 목록 · `/pages/` 주소 · 보관함 · 공개 여부마다 "앱 코드는 빼고"를 걸어야 하고 공개 여부가 페이지와 앱 둘로 갈린다. 파일 규칙(`PageFiles`) · 미리 보기 표 · 확인 대기 방식만 다시 쓴다.
- **앱 JS가 JSON API로만 그리기 (빈 HTML)**: JS 없이는 글이 안 보이고 검색에 안 잡히며, 출처 없는 문서에서 API를 부르려면 CORS를 열어야 한다.
- **Handlebars · Liquid**: 템플릿 안에 로직(helper · filter)이 들어온다. Mustache로 충분하다.
- **앱 코드를 서버에서 실행 (React · Node)**: 남이 만든 코드를 서버에서 돌리지 않는다 (2026-11-18 결정).
- **`sandbox`에 `allow-same-origin`**: 앱 JS가 우리 쿠키 · API에 닿는다.
- **앱마다 하위 도메인을 지금**: DNS · 인증서가 앱마다 필요하다. 4단계로.
- **1-4 화면을 두고 코드가 있는 앱만 템플릿으로**: 그리는 길이 둘이 되고, 기본 앱의 모양을 바꾸려면 Cairn 코드를 고쳐야 한다.
- **버전 표에 앱 외래키**: 버전이 추가만이라 코드를 고친 앱은 지울 수 없게 된다.

### 9.13 정적 앱: 템플릿 없는 앱 (2026-11-21, 사용자 결정 "템플릿이 없는 앱 · 패키지가 자유롭게")

페이지 앱은 Mustache 템플릿을 거치지 않고 **묶음의 파일을 그대로** 내보낼 수 있다. 스크립트가 화면을 그리는 앱(도구 · 지도 · 대시보드)과 빌드한 결과(`dist/`)를 그대로 쓴다. 버전 · 공개 전 확인 · 격리는 템플릿 앱과 같다.

| 항목 | 정한 것 |
|---|---|
| 켜는 법 | `cairn.json`의 `"render": "static"` (없으면 `"template"`). 버전마다 그 버전의 `cairn.json`으로 정한다: 표 · 마이그레이션 없음 |
| 되는 앱 | 페이지 앱만 (`AppCodeBundle.assertFits`). 블로그 · 매거진 · 커뮤니티는 글 · 메뉴 화면이 템플릿이라 422 |
| 묶음 규칙 | 폴더 있는 이름 (`PageFiles.of(raw, true)`): 파일 500개 · 합쳐 20MB · HTML 하나 1MB · 경로는 파일까지 여섯 마디 · 300자 · 점으로 시작하는 마디 없음. `index.html`이 꼭 있다. 템플릿 앱에 폴더가 있으면 422 (`"render": "static"`을 알려 준다) |
| 주소 → 파일 | `AppSiteQuery.staticFile`: 그 이름의 파일 → 폴더면 그 안의 `index.html` → 마지막 마디에 확장자가 없으면 `index.html`(앱 안의 화면 전환) → 확장자가 있으면 404 |
| 화면 API | `{ status, seq, static: { file, text }, hosts, data, redirect: null, page: null }` (`AppScreenStaticView`). HTML이면 `text`(글)와 `data`(첫 화면의 데이터 약속)를 싣고, 그 밖의 파일은 `text` · `data`가 null이고 웹이 파일 주소에서 받아 넘긴다 |
| 파일 API | `GET api/apps/site/:slug/files/*path`: 폴더가 든 이름. `Access-Control-Allow-Origin: *`(격리된 문서가 모듈 스크립트 · 글꼴 · fetch로 자기 파일을 읽는다. 답은 쿠키와 상관없다: 공개 앱이거나 토큰 주소). HTML은 화면으로만 나간다 (404) |
| 웹 | HTML에 `<base>`(그 파일이 있는 폴더의 주소)와 `cairn-data` 블록만 더한다 (`renderStaticScreen`). 격리 머리글은 템플릿 앱과 같고 둘만 다르다: `base-uri <사이트>`, `connect-src`에 그 앱의 주소(`<사이트>/<앱>/`)를 더한다. 사이트의 다른 주소(api)는 여전히 부르지 못한다 |
| AI로 고치기 | 폴더가 없으면 지금처럼 바꾼 파일만 얹는다. 폴더가 있으면 결과물에 `app.zip` 하나(결과물은 폴더를 올리지 못한다): zip 안이 묶음 전체다 (`AppCodeService.BUILD_ZIP`). AI가 내용을 받지 못한 앞 버전의 파일(그림 · 큰 파일, `AppCodeQuery.givenOf`의 밖)은 zip에 없어도 남긴다. 러너는 zip의 목록과 `cairn.json`을 읽어 묶음 규칙을 본다 (`ZipIndex` · `AppCodeCheck.packed`). 정적 앱은 템플릿 문법 · 데이터 이름 검사가 없다 |
| 관리자 zip 올리기 | 그대로다: zip 안이 묶음 전체. 폴더가 든 zip은 `cairn.json`에 `"render": "static"`이 있어야 한다 |
| 보관 형식 | `blog/apps/<주소>/code/<경로>`에 폴더째 싣고 폴더째 복원한다 |

브라우저로 확인한 것 (Chromium, 격리된 문서): 모듈 스크립트와 그 안의 `import`, 폴더 안의 CSS · 그림, 같은 묶음 파일의 `fetch`, `history.pushState`(앱 안의 화면 전환), 미리 보기 토큰 주소. 막힌 것: 이 서버의 API(`connect-src`), `localStorage` · 쿠키(출처 없는 문서).

정적 앱이 지켜야 하는 것: 주소는 모두 상대 주소 (`/`로 시작하면 앱 밖을 가리킨다. Vite는 `base: './'`).

아직 안 되는 것 (격리 때문에, 앱마다 도메인에서 `sandbox`를 푸는 단계의 일): `localStorage` · 쿠키 · 워커 · 서비스 워커 · 위치 정보(`Permissions-Policy: geolocation=()`).

고르지 않은 것:

- **앱 종류를 하나 더 (static)**: 종류는 만들 때만 정해 기존 페이지 앱을 바꿀 수 없다. 그리는 법은 코드의 일이라 `cairn.json`에 둔다 (버전마다 되돌릴 수 있다).
- **`app.zip`을 앞 버전 위에 얹기**: 빌드 결과는 파일 이름에 해시가 붙어 옛 파일이 버전마다 쌓인다. zip은 묶음 전체로 하고, AI가 받지 못한 파일만 남긴다.
- **러너가 폴더를 zip으로 묶어 올리기**: 결과물 폴더는 바로 아래 파일만 올린다는 규칙(링크 · 폴더를 러너가 따라가지 않는다)을 지킨다. zip은 AI가 만든다.
- **템플릿 앱에도 폴더**: 조각(`{{> 이름}}`)과 화면 템플릿이 이름으로 정해져 있어 폴더가 뜻이 없다.

## 10. 2단계 앱별 운영 (설계안 승인 2026-11-18)

> 2026-11-21: 앱 운영 팀(운영 팀장 `apps.agent_id` · 메뉴의 `menus.agent_id` · 팀 안인지 보기 `AppTeam` · platform `AgentDirectory`의 카드 · `new_team`)은 없앴다 (기획서 결정 "팀을 없애고 대표 하나 + 모두 같은 일꾼으로"). 모든 에이전트가 어느 앱 · 메뉴에나 초안을 놓고, 남는 것은 편집 방침 · 첫 화면 고정 · 대화의 앱이다. 아래는 만들 때의 기록이다.

### 10.0 한 장 요약

관리자는 대표와만 대화하고, 대표가 앱의 일을 그 앱의 운영 팀에 맡긴다. 결과는 지금처럼 결과 카드로 승인한다.

| # | 정한 것 |
|---|---|
| 1 | 앱마다 운영 팀장(`apps.agent_id`)과 편집 방침(`apps.policy`, 4000자). 메뉴의 같은 칸과 같은 모양. 팀장은 맨 위 에이전트(대표가 맡길 수 있는 층)이고 비공개를 읽지 않는 에이전트만. 한 팀장이 여러 앱을 맡아도 된다. 편집 방침의 "## 문체" · "## 배운 규칙" 단락은 피드백에서 배우기(2026-11-20, 기획서 결정)가 대표의 설정 바꾸기 제안으로 채우고 관리자가 승인한다. 검수도 이 단락을 완료 조건으로 본다 |
| 2 | 운영 팀 = 팀장과 그 아래 팀 전체. 앱 · 메뉴에 글을 놓는 에이전트는 비공개를 읽지 않고, 운영 팀이 정해져 있으면 그 팀 안이어야 한다. 메뉴에도 운영 팀이 있으면 메뉴가 정한다. 메뉴의 운영 팀도 "그 에이전트 하나"에서 "그 에이전트와 그 아래 팀"으로 넓힌다 (팀장이 팀원에게 나눠 맡기므로) |
| 3 | 팀 확인은 platform `AgentDirectory` 카드의 `chain`(보고 대상을 위로 따라간 id). blog는 task를 가져오지 않는다 |
| 4 | 대표는 `get_settings apps`의 `agent_id` · `policy`를 읽고 앱의 일을 그 팀장에게 맡긴다. 운영 팀이 없는 앱이면 `propose_setting app edit { agent_id }`를 `continue`와 함께 제안 |
| 5 | 대화에 앱: `task.chats.app_id` (앱 관리의 "맡기기"로 연 대화만, 확인 · 이름은 platform `Lookups`의 `app`). 회차마다 대표에게 앱이 가고, 그 대화에 묶인 자동화도 같다. `GET api/chats?app=`로 앱의 대화와 수 |
| 6 | MCP: `blog_menus { app_id? }`가 앱(방침 · 운영 팀)을 함께 내고, `blog_save_draft`에 `app_id`(메뉴 없이 앱에만) |
| 7 | 방문자 첫 화면 고정: `apps.home`(공간마다 하나, 공개 앱만, 비공개로 바꾸면 풀림), `PUT api/apps/home`(관리자만, 대화 제안 없음). `/`는 고정 앱이 있으면 그 앱으로, 없으면 지금처럼 자동 |
| 8 | 팀 템플릿 "앱 운영 팀": 편집장(팀장) · 작가(write) · 검토자 · 앱 디자이너(make) |

이미 된 것: 앱마다 RSS(1-4), 받을 것 넓히기(O-3: `blog` = 글 · 호 발행, `app_code` = 앱 코드. 값은 그대로, 화면 이름만 "글 발행").

단계: 2-1 서버 blog → 2-2 서버 task → 2-3 지시문 · 러너 · 스킬 → 2-4 웹 → 2-5 문서 · 전체 테스트 · 화면 확인 · main.

고르지 않은 것: 앱 운영 팀 표 따로(팀은 이미 조직도), 팀원 줄에 "운영하는 앱" 싣기(task가 blog를 읽는 길이 하나 더), 첫 화면을 사이트 설정(account)에(account가 blog의 앱 id를 들고 이벤트로 맞춰야 함), 작업 토큰에 앱을 넣어 대화의 앱 밖에 못 쓰게(운영 팀 규칙이 막는다), 앱 코드 일(make)도 운영 팀만(task가 blog의 팀을 읽어야 해서 뒤로. 공개 앱의 코드는 이미 승인을 거친다).

### 10.1 2-1 인터페이스: 서버 blog (승인 2026-11-18, 끝남)

설계안과 달라지는 점 두 가지:

- **편집 방침은 백업 파일에 넣지 않는다.** 공개 앱의 앱 파일은 공개 저장소로 갈 수 있는데 방침은 방문자에게 보이는 것이 아니다. 메뉴의 방침도 아직 파일에 없다 (보관형식 "아직 파일에 없는 것"). `home`만 넣는다.
- **`blog_menus`의 모양을 바꾸지 않고 더한다.** 지금 `{ menus }`를 두고 `apps`를 더한다 (깨지는 변경은 새 도구 이름이라는 API설계 2장 규칙).

표 (마이그레이션 하나 `blog_app_team`):

```sql
ALTER TABLE blog.apps
  ADD COLUMN agent_id uuid,                        -- 운영 팀장 (task 에이전트 id, 모듈 사이라 외래키 없음)
  ADD COLUMN policy text NOT NULL DEFAULT '',      -- 편집 방침
  ADD COLUMN home boolean NOT NULL DEFAULT false,  -- 방문자 첫 화면으로 고정
  ADD CONSTRAINT apps_policy_length CHECK (char_length(policy) <= 4000),
  ADD CONSTRAINT apps_home_public CHECK (NOT home OR visibility = 'public');
CREATE UNIQUE INDEX apps_one_home ON blog.apps (space_id) WHERE home;  -- 공간마다 하나
```

규칙 (`blog/app/app-team.policy.ts` `AppTeam`, 앱 · 메뉴가 함께 쓴다):

| 메서드 | 하는 일 |
|---|---|
| `AppTeam.ranks(actor, card)` | 에이전트면 `[자기 id, ...card.chain]`, 아니면 `[]` |
| `AppTeam.assertWriter(by, ranks, menuTeam, appTeam, where)` | 관리자 · 기기는 통과. 에이전트는 비공개를 읽으면 403, 운영 팀(`menuTeam ?? appTeam`)이 있는데 `ranks`에 없으면 403 "<where>의 운영 팀이 아니에요" |
| `AppTeam.allows(by, ranks, team)` | 위와 같은 판단의 참 · 거짓 (`blog_menus`의 `can_write`) |
| `AppTeam.assertLeader(card, forApp)` | 없으면 404, 비공개를 읽으면 422, 앱이면 맨 위(`chain` 비었음)가 아니면 422 "맨 위 에이전트만 앱의 운영 팀장이 될 수 있어요" |

- `Menu.assertWriter`는 지우고 `Post.placeIn(app, menu, by, ranks, now)` · `PostService.intoIssue`가 `AppTeam.assertWriter`를 부른다. `ranks`는 Service가 트랜잭션 전에 `AgentDirectory`로 읽는다 (놓는 요청이 있을 때만).
- platform `AgentCard`에 `chain: readonly string[]`(보고 대상, 가까운 순). task `AgentQuery.card`는 에이전트 자신도 읽는다 (`actor.id === id`).
- 지운 팀장은 카드가 없어 팀 밖과 같다 (관리자 · 기기만 놓는다). 휴지통에서 되살리면 그대로 돌아오게 값은 비우지 않는다 (메뉴와 같다).

REST (관리자만, 모양은 더하기만):

| 경로 | 바뀌는 것 |
|---|---|
| `POST api/apps` · `PATCH api/apps/:id` | 본문에 `agentId: uuid \| null` · `policy: string` (보내지 않으면 그대로). 팀장은 트랜잭션 전에 `AppTeam.assertLeader` |
| `PUT api/apps/home` (새로) | `{ appId: uuid \| null }` → 204 (화면이 목록을 다시 읽는다). 공간의 앱을 모두 잠그고 다른 앱의 고정을 푼 뒤 이 앱을 고정. 비공개 앱이면 422. 같은 값이면 그대로 (requestId · version 없음: 결과가 늘 같다) |
| `AppView` (관리자) | `agentId` · `policy` · `home` |
| `PublicAppView` (방문자) | `home` (웹 `/`가 본다) |

- `App.edit`이 공개 → 비공개면 `home`도 푼다 (DB CHECK도 막는다).

MCP (`blog.tools.ko.json`의 설명 함께):

| 도구 | 바뀌는 것 |
|---|---|
| `blog_menus { app_id? }` | 응답에 `apps: [{ id, name, slug, kind, policy, agent_id, can_write }]`(페이지 앱 빼고)를 더하고, `menus`의 줄마다 `app_id` · `can_write`. `app_id`를 주면 그 앱과 그 앱의 메뉴만 (없으면 not_found) |
| `blog_save_draft` | `app_id: uuid \| null` (메뉴 없이 그 앱에 넣기). `menu_id`와 함께 보내면 같은 앱이어야 한다 (아니면 422) |
| `get_settings apps` | 줄마다 `agent_id` · `policy` · `home`(읽기만) |
| `propose_setting app` | `fields`에 `agent_id` · `policy`. 미리 해 보기 · 적용도 `AppTeam.assertLeader`. `home`은 받지 않는다 (422, 공개 여부와 같은 규칙) |

메뉴: `MenuService`의 팀장 확인도 `AppTeam.assertLeader(card, false)` (깊이는 보지 않음).

보관 형식: 앱 파일에 `home: true`(고정일 때만). 복원은 공개 앱만, 둘 이상이면 멈춘다. `agent_id` · `policy`는 넣지 않는다 (위).

테스트: `app.api.test`(팀장 고르기: 맨 위 · 아래 · 비공개 읽기 · 지운 에이전트, 방침 길이, 첫 화면 고정 · 옮기기 · 비공개면 풀림 · 방문자 응답, 방문자 · 기기는 못 바꿈), `post-tool.api.test`(팀 안의 작가는 놓기, 팀 밖은 403, 메뉴 팀이 앱 팀보다 먼저, `app_id` · 메뉴와 앱이 다르면 422, `blog_menus`의 `apps` · `can_write`), 설정 바꾸기(`agent_id` · `policy` 제안 → 승인 → 적용), 복원(`home`).

줄 수: `post.ts`가 300줄이라 판단을 `AppTeam`으로 옮기며 늘리지 않는다.

2-1에서 정한 것: 놓는 요청자의 운영 팀 확인은 `Post.placeIn`이 아니라 `PostService`가 `AppTeam`으로 한다 (`intoIssue`와 같은 자리, 보고 대상을 트랜잭션 전에 읽어서 · `post.ts` 300줄). `PUT api/apps/home`은 204 (진입 계층은 메서드 하나만 부른다, 화면이 목록을 다시 읽는다). 방침이 4000자를 넘으면 입력 모양에서 400. 같은 앱의 `app_id`만 보내면 메뉴를 두고 그대로.

### 10.4 2-4 인터페이스: 웹 (승인 2026-11-19, 끝남)

서버 API는 2-1 · 2-2 그대로 쓰고 새로 만들지 않는다. 타입은 서버 View에서 `import type`.

| 화면 | 바뀌는 것 |
|---|---|
| 앱 관리 › **운영 팀** 탭 (새로, `?tab=team`, `AppTeamTab.tsx`) | 운영 팀장 고르기(맨 위의, 비공개를 읽지 않는 에이전트 · 없음, `PATCH api/apps/:id { agentId }`) · 팀원 목록(조직도에서 팀장 아래) · 운영 팀이 없으면 "앱 운영 팀 만들기"(템플릿 `app`을 만들고 편집장을 팀장으로) · 편집 방침(`policy`) · "이 앱에 맡기기" 입력(`POST api/chats { appId }` → 그 대화로) |
| 앱 관리 › 개요 | "이 앱의 대화"(`GET api/chats?app=`: 제목 · 상태 · 승인 대기 표시, 5개 · 모두 보기는 대화 목록) |
| 내 앱 카드 | 운영 팀장 이름(없으면 "운영 팀 없음") · 승인 대기 수(대화 목록의 `appId` · `waiting_approval`) |
| 만들기 시트 | 운영 팀: 나중에 · 있는 팀장 · 앱 운영 팀 새로 만들기 (새로면 팀을 먼저 만들고 앱을 만든다) |
| 설정 › 사이트 | "첫 화면": 자동 · 공개 앱 하나 (`PUT api/apps/home`) |
| 대화 머리 | 앱 칩 (앱 이름, 누르면 앱 관리) |
| 공개 `/` | 고정 앱이 있으면 그 앱으로 307, 없으면 지금처럼 자동 |

확인: 화면 테스트(웹 단위), 브라우저로 데스크톱 · 폰 (운영 팀 탭 · 맡기기 → 대화의 앱 칩 · 내 앱 카드 · 만들기 시트 · 첫 화면 고정 → `/`).

2-4에서 정한 것: 같은 템플릿으로 만든 팀장은 이름이 같아서(편집장) 고르기 칸에 이미 운영하는 앱을 붙인다(`leaderLabel`: "편집장 · 개발 블로그 운영"). 만들기 시트의 "앱 운영 팀 새로 만들기"는 앱과 같은 requestId로 팀을 먼저 만든다 (다시 눌러도 팀은 하나). 내 앱 카드의 승인 대기 수는 대화 목록(최근 100개)에서 센다. 화면 확인: 내 앱 카드 · 운영 팀 탭(팀장 · 방침 · 팀원) · 운영 팀 없음 → 앱 운영 팀 만들기 · 맡기기 → 대화의 앱 칩 · 개요의 이 앱의 대화 · 만들기 시트의 운영 팀 칸 · 설정 › 사이트 첫 화면(고정 → 방문자 `/`가 그 앱으로 307, 자동으로 되돌림) · 폰.

### 10.6 2-6 인터페이스: 대화로 앱 만들기 (승인 2026-11-19, 끝남)

목적: "여행 계획 사이트 하나 만들어 줘" 한마디로 대표가 앱 종류를 고르고, **승인 한 번에 앱과 운영 팀을 함께 만들고**, 이어서 첫 결과(첫 글 · 첫 화면)까지 낸다. 마이그레이션은 없다.

2-5 뒤에 코드를 보고 찾은 빈 곳:

1. 대표 지시문에 앱 만들기의 갈래(4장)가 없다. 같은 말에 블로그로 갈지 화면으로 갈지 정해져 있지 않다.
2. 대화로는 운영 팀 템플릿을 쓰지 못한다 (에이전트를 하나씩 제안해야 한다).
3. 대화의 "페이지" 결과(받을 것 `html`)는 결과물 파일(`.html`)이지 페이지(`blog.pages`)가 아니다. 페이지 앱은 페이지가 꼭 있어야 해서 대화로 끝까지 만들지 못한다. (그래서 처음 말한 "`page_id`를 받기"는 대화에서 쓸 수 없다.)
4. 새로 만든 앱은 비공개라 앱 코드의 새 버전이 승인 없이 바로 보인다. 받을 것이 `app_code`면 서버가 공개 승인(`blog.app_code.show`)을 찾지 못해 같은 일을 두 번 다시 맡긴다.

| 바뀌는 곳 | 모양 |
|---|---|
| blog `AppEdit.create` | 페이지 앱은 **페이지 없이도** 만든다 (`pageId` 선택). 화면은 앱 코드다. 페이지를 주면 지금처럼 그 페이지를 앱에 넣는다. 복원은 이미 페이지 없는 페이지 앱을 받는다 |
| blog `AppEdit.SETTING` (`propose_setting app`) | fields에 `new_team`(true, 만들 때만, 굵은 줄). `agent_id`와 함께 주면 422 "운영 팀장을 고르거나 새로 만들거나 하나만 해요", 고치기에 주면 422 "운영 팀 새로 만들기는 앱을 만들 때만 해요" |
| platform `AgentDirectory` | `registerTeamMaker(make)` · `teamFor(actor): Promise<string>`(팀장 id)를 더한다. 에이전트를 가진 모듈(task)이 등록하고, 승인한 설정 바꾸기가 부른 팀을 만든다. platform · blog는 템플릿 이름 · 구성원을 모른다 (platform에 업무 말을 두지 않으려고 이름을 일반으로) |
| task (등록하는 함수, `AgentService.createAppTeam`) | `ApprovedActor`(동작 `task.setting.change`)만 받는다. 그 결재를 읽어(`ApprovalQuery.asksAppTeam`) 승인됨 · `setting: app` · `op: create` · `new_team: true`인지 보고 아니면 Forbidden. 템플릿 `app`, requestId = 결재 id (결재마다 팀 하나, 다시 와도 같은 팀). 도구는 엔진 목록 첫 줄 (웹의 팀 만들기와 같다) |
| blog `AppService.applySetting` | `new_team`이면 트랜잭션 전에 `AgentDirectory.teamFor` → 팀장 id를 `agent_id`로 넣어 앱을 만든다 (앱 저장과 결과 `blog.setting.changed`는 지금처럼 한 트랜잭션). 팀 만들기가 규칙에 막히면 그 까닭으로 결재를 실패로 끝낸다. 이미 적용한 결재면 팀을 다시 찾지 않는다 |
| task `ChatResult.NEEDS`의 `app_code` | 공개 승인(`blog.app_code.show`) **또는** 이번 회차에서 끝난 앱 코드 만들기 일(`payload.appCode`, done, `ChatRepository.madeAppCode`). 비공개 앱은 승인 없이 바로 보이기 때문이다. 공개 앱은 지금처럼 카드에 공개 승인이 실린다 |
| 지시문 틀 `lead` | 새 앱 만들기 단락 (아래) |
| 도구 설명 `propose_setting` (`task.tools.ko.json`) | 앱 fields에 `new_team`(true면 앱 운영 팀(편집장 · 작가 · 자료 조사 · 앱 디자이너)을 새로 만들어 운영 팀장으로, `agent_id`와 함께 쓰지 않음, 만들 때만). `kind: page`는 "페이지 없이 만들고 화면은 앱 코드(make의 `app_id`)로" |
| 웹 만들기 시트 | 페이지 앱의 "앱이 될 페이지"에 "없음 · 앱 코드로 화면 만들기" |
| 웹 승인 줄 이름 (`_task/setting-labels.ts`) | `new_team: '앱 운영 팀 새로 만들기'` |
| 시작 코드 `starters/page` | 페이지가 없으면 앱 설명과 "준비 중" 한 줄 (공개 전에는 관리자만 본다) |

대표 지시문의 새 단락 (요지):

- 새 앱을 만들어 달라면 **방문자가 무엇을 하는지**로 종류를 고른다: 글을 읽는다 → `blog` (호로 묶어 낸다 → `magazine`) · 화면을 쓴다(일정표 · 계산기 · 지도) → `page` (페이지 없이, 화면은 앱 코드) · 가입 · 저장 · 결제가 필요하다 → 지금은 못 한다. 까닭과 가장 가까운 대안(앞의 둘 중 하나)을 짧은 답(`answer`)으로 낸다.
- 받을 것은 `setting`이 아니라 **앱의 첫 결과**로 정한다: `blog`면 `blog`(첫 글 발행), `page`면 `app_code`(첫 화면). 앱 만들기 승인은 `continue: true`로 올려 같은 대화에서 이어 간다.
- `propose_setting app create`(kind · name · slug · description · menus · policy)에 운영 팀: 맡을 팀장(맨 위, 비공개를 읽지 않음, 다른 앱을 맡지 않음)이 있으면 `agent_id`, 없으면 `new_team: true`.
- 승인 뒤 이어서 회차: `get_settings apps`로 새 앱의 id · `agent_id`를 읽고 그 운영 팀장에게 첫 결과를 맡긴다 (화면은 편집장이 앱 디자이너에게 kind make · `app_id`).

흐름 예 ("여행 계획 사이트 하나 만들어 줘", 화면 앱으로 판단한 경우):

1. 대표: `set_deliver app_code` → `propose_setting app create { kind: page, name: 여행 계획, slug: trip, new_team: true }`, `continue: true` → 결과 카드 (**승인 ①**: 앱 + 운영 팀)
2. 적용: task가 앱 운영 팀을 만들고 blog가 앱(비공개)을 그 편집장과 함께 만든다
3. 이어서 회차: 대표 → 편집장 → 앱 디자이너(make, `app_id`) → 앱 코드 버전 1 (비공개라 바로 보임) → 받을 것 충족 → 답 "앱 관리 › 코드에서 미리 보기"
4. 공개는 관리자가 앱 관리에서 한다 (AI는 공개하지 못한다). 공개 뒤 화면을 고치면 카드의 공개 승인 (1-6b)

글 앱이면 3에서 작가가 첫 글 초안을 앱의 메뉴에 놓고 카드에 발행 승인이 실린다 (**승인 ②**).

오류 경우:

| 경우 | 결과 |
|---|---|
| `new_team`과 `agent_id`를 함께 | 제안에서 422 rule_violation |
| 고치기(`op: edit`)에 `new_team` | 제안에서 422 rule_violation |
| 같은 결재가 두 번 옴 | 팀 하나 · 앱 하나 (requestId = 결재 id, `SettingOutcome`) |
| 팀은 만들었는데 앱이 막힘 (승인 사이에 다른 앱이 그 주소를 씀) | 결재 실패 "이미 쓰는 앱 주소예요". 팀은 남는다 (팀 화면에서 휴지통으로 · 앱 관리에서 팀장으로 고를 수 있다) |
| 그 결재가 아닌 요청자(관리자 REST · 제안의 미리 해 보기 · 다른 결재)가 `teamFor`를 부름 | Forbidden |

나중에 버티는 법:

- 템플릿을 고르는 칸이 필요해지면 `new_team: true`를 템플릿 키로 넓힌다 (true = `app`). 템플릿은 task 안에만 있어 blog는 바뀌지 않는다.
- 새 앱 종류(커뮤니티 등)가 생기면 지시문의 갈래 한 줄과 kind 값만 더한다.
- 페이지로 페이지 앱 만들기(`page_id`)는 대화에서 페이지가 생기는 길이 생길 때 더한다.

고르지 않은 것:

- **대화로 `page_id` 받기**: 대화의 결과는 결과물 파일이라 페이지가 없다. 결과물 → 페이지 바꾸기를 따로 만들어야 하고, 페이지 앱의 첫 화면은 페이지를 링크로만 보인다(9.11.1). 앱 코드는 이미 버전 · 미리 보기 · 카드의 공개 승인이 있다.
- **승인 두 번** (task의 팀 만들기 설정 + blog의 앱 만들기 설정): 바뀌는 곳은 적지만 관리자가 두 번 누르고 대표가 회차를 한 번 더 돈다.
- **이벤트로 잇기** (blog가 앱을 만들고 팀을 이벤트로 부탁 → task가 만들고 → blog가 팀장을 넣음): 그사이 이어서 회차가 먼저 열려 운영 팀장 없는 앱을 볼 수 있고, 실패가 두 곳에 생긴다.
- **이어서 회차에서 받을 것 바꾸기 허용**: 검사를 피하는 길이 된다. 첫 회차에 최종 결과로 정하게 한다.

테스트: blog 설정 제안(`new_team` → 승인 → 앱 + 팀, 앱의 `agent_id` = 편집장 · 같은 결재 두 번 → 하나 · `new_team` + `agent_id` 422 · 고치기 422), 페이지 없는 페이지 앱(관리자 REST · 제안), task `teamFor`의 요청자 확인(관리자 · `SettingActor` · 다른 결재는 Forbidden), 결과 검사(비공개 앱의 앱 코드 일이 끝나면 다시 맡기지 않음), 지시문 틀 검사, 웹 만들기 시트, 화면 확인(카드의 "앱 운영 팀 새로 만들기" 줄).

순서: 2-6a 서버(platform · blog · task) → 2-6b 지시문 · 도구 설명 → 2-6c 웹 · 문서(1장 페이지 앱 · 4장 흐름 · API설계 · 기획서 결정 기록) · 확인 → main.

2-6b에서 정한 것: 대표는 팀장의 팀원에게 직접 맡기지 않으므로, 화면을 만드는 첫 결과는 운영 팀장(편집장)에게 맡기고 지시에 "앱 디자이너에게 kind: make, app_id로"를 적게 했다. 앱 코드 참고(`cairn-make/references/app-code.md`)에 "페이지 앱은 페이지 없이도: `pages`는 빈 목록, 화면은 코드가 전부"를 더했다. 확인: 러너 단위(새 단락이 늘 들어감) · 지시문 틀 · 도구 설명 테스트.

2-6c에서 정한 것: 만들기 시트의 페이지 앱은 "앱이 될 페이지"를 비울 수 있다 ("없음 · 앱 코드로 화면 만들기"). 승인 줄은 설정 이름 "앱", `new_team`은 "운영 팀: 없음 → 앱 운영 팀 새로 만들기 (편집장 · 작가 · 자료 조사 · 앱 디자이너)"로 읽고 굵은 표시는 "에이전트 추가"다 (켜고 끔으로 읽으면 뜻이 틀려서 칸마다 따로 읽는 값을 둔다, `setting-labels.ts`). `menus`는 "시작 메뉴"로. 화면 확인에서 찾아 고친 것: 앱 만들기 카드(받을 것 앱 코드 + `continue` 설정 바꾸기)가 "검사에 떨어짐 (결과에 없음)"으로 보였다. 받을 것은 승인 뒤 이어서 내는 것이라 카드에 `continues`를 더해 "승인하면 이어서 만듦"으로 보인다 (`ChatResult.continuesAfter`). 확인: 결과 카드(앱 · 종류 페이지 앱 · 운영 팀 줄 · 에이전트 추가) → 승인 → 앱(비공개) · 편집장과 팀원 셋 · 승인 뒤 이어서 회차(받을 것 앱 코드) · 만들기 시트에서 페이지 없이 페이지 앱 · 폰.

## 11. 3단계 커뮤니티 (설계안 승인 2026-11-19)

방문자가 회원으로 가입해 글 · 댓글을 쓰는 첫 기능. 회원 계정 · 스팸 · 개인정보 · 신고가 함께 생겨 설계안과 보안 검토를 먼저 했다. 단계마다 인터페이스를 따로 승인받고 만든다.

### 11.0 한 장 요약

목표: 스토어에 "커뮤니티" 앱 종류를 더한다. 회원이 글 · 댓글을 쓰고, AI 운영 팀이 관리를 돕고, 지우기 · 제재는 관리자가 승인한다.

| 항목 | 정한 것 | 고르지 않은 것 |
|---|---|---|
| 회원 로그인 | 아이디 · 비밀번호로 간단히 가입한다 (2026-11-19 바꿈, 처음 설계는 카카오 소셜 로그인). 비밀번호는 해시만, 이메일은 받지 않는다. 틀린 시도 · 가입 수 제한, 실패 문구 하나 (11.5) | 소셜 로그인(카카오 앱 등록 · 키 관리가 필요해 "간단히"가 아니다), 이메일 + 비밀번호 (인증 · 재설정 메일 서비스 · 늘어나는 개인정보) |
| 회원 데이터 | 새 모듈 `community`(스키마 `community`): 회원 · 회원 로그인(세션) · 글 · 댓글 · 신고. 관리자 계정(account)과 표 · 쿠키 · 권한을 나눈다. 앱은 blog가 `Lookups`로 내주는 `app`을 묻고 `app_id`는 값으로 (8.9) | account 모듈에 회원 섞기 |
| 화면 | 읽기(목록 · 글 보기)는 앱 코드 템플릿(지금처럼 격리). 로그인 · 글쓰기 · 댓글 · 신고 · 내 정보는 Cairn이 그리는 고정 화면 (같은 출처 쿠키 + CSRF 토큰) | 격리된 앱 JS가 CORS로 API 부르기 (출처 없는 문서라 쿠키 · CORS `null`을 열어야 한다, 9.12를 바꿈) |
| 글 형식 | 글자 · 마크다운(지금의 정화기). 회원 글의 링크는 `rel="nofollow ugc"`. 1차는 사진 올리기 없음 | 사진 올리기 (불법 촬영물 · 저작권 · 저장 공간: 2차에 필터와 함께) |
| 스팸 | 회원마다 속도 제한(시간당 글 · 댓글 수), 가입 직후 잠깐 대기, 링크 수 제한, 같은 글 반복 막기, 관리자의 차단 | 캡차 (1차 생략, 필요해지면) |
| 신고 · 관리 | 신고가 3건이면 시스템이 임시로 가린다 (되돌릴 수 있음, 정보통신망법의 임시조치). AI 운영 팀이 검토 의견을 내고, 지우기 · 회원 제재는 관리자 승인으로만 | AI가 직접 지우기 (원칙 7) |
| 개인정보 | 탈퇴하면 회원 정보를 지우고 글은 "탈퇴한 회원"으로 남긴다. 만 14세 이상만 가입. 로그 · 보관 형식에 회원 정보를 남기지 않거나 가린다 | — |
| 약관 | 이용약관 · 개인정보처리방침: AI가 초안, 관리자가 확인한 뒤 공개. 가입할 때 동의를 기록한다 | — |
| AI 운영 팀 | 팀 템플릿 "커뮤니티 운영 팀": 공지 · 주제 글(운영자로 표시), 신고 검토 의견, 주간 요약. 비공개를 읽지 않는 팀만 (브라우저 담당과 같은 규칙) | AI가 회원인 척 쓰기 (속이는 일) |
| 주소 | 앱마다 자기 도메인을 붙일 수 있다 (3-0, 모든 앱에). 콘솔과 관리 API는 기본 도메인에서만, 앱 도메인에서는 그 앱의 공개 화면과 회원 화면만. 회원 쿠키는 그 앱 도메인에만. 등록하지 않은 Host는 404 | 커뮤니티를 별도 도커 이미지로 떼기 (아래 11.2) |

### 11.1 보안 검토에서 볼 것

| 위협 | 막는 법 |
|---|---|
| 회원이 관리 기능에 닿는다 | 회원 전용 Actor. 관리 API는 `assertOwner` 그대로, 회원 쿠키는 관리 경로에서 통하지 않는다. 콘솔은 기본 도메인에서만 |
| 세션 탈취 · CSRF | HttpOnly · Secure · SameSite=Lax 쿠키(그 앱 도메인에만), 쓰기마다 CSRF 토큰 |
| 회원 글의 스크립트(XSS) | 정화기와 앱 화면 격리 그대로 |
| 도배 · 스팸 | 속도 제한 · 차단 |
| 개인정보 유출 | 최소 수집, 로그에 남기지 않음, 보관 형식에서 가림 |
| 비공개 누출 | 신고 검토 일의 작업 토큰은 커뮤니티 도구 · 결정 제안만 본다 (2026-11-24, 11.7: 팀이 없어져 모든 일꾼이 비공개를 읽으므로 일마다 도구를 좁힘) |
| 불법 · 권리침해 글 | 신고 · 임시 가림 · 관리자 결정 기록 |
| Host 머리글 속이기 | 등록한 앱 도메인과 기본 도메인만 받고 나머지는 404 |

### 11.2 별도 이미지로 떼지 않는 까닭 · 나중에 떼는 길

주소(도메인)와 배포 단위는 따로 정할 수 있다: 앞단 프록시(Caddy)에 도메인 블록 하나를 더해 같은 웹 · 서버로 보내면 된다. 별도 이미지는 회원 로그인 · 세션 · 마이그레이션 · 배포가 두 벌이 되고, 관리자 승인 · AI 운영 팀 · 이벤트를 서비스 사이 API로 다시 이어야 하며 보안 검토도 두 벌이다. 떼는 것이 이득인 때(접속이 많아 따로 늘릴 때, 다른 서버로 옮기거나 넘길 때, 회원 쪽 코드가 뚫려도 비공개에 닿지 못하게 DB 권한까지 나눌 때)를 위해 지금 지킨다: 커뮤니티는 자기 스키마만 쓰고 다른 모듈과는 `index.ts` · 이벤트로만, 회원 Actor를 따로, 커뮤니티 API는 `/api/community/…` 한 줄기. 그러면 같은 코드에서 진입점만 다른 컨테이너 + 그 스키마만 쓰는 DB 계정으로 뗄 수 있다.

미리 할 일 (관리자): 커뮤니티 앱의 도메인을 DNS와 Caddyfile에 더한다 (회원 로그인 · 쓰기는 앱 도메인에서만).

### 11.4 3-0 앱마다 도메인 인터페이스 (승인 2026-11-19)

**표** (마이그레이션 `blog_app_domains`): `blog.apps.domain`(소문자 · 국제 도메인은 `xn--` 꼴, 모든 공간에서 하나 `apps_domain_key`, 모양 CHECK `apps_domain_format`) · `domain_checked_at`(연결을 확인한 때, 도메인을 바꾸면 비운다, 도메인 없이 있을 수 없다 `apps_domain_checked`).

**도메인 규칙** (`App.checkDomain` · `setDomain` · `confirmDomain`): 도메인만 받는다 (https:// · 포트 · 경로 422), IP 주소 · localhost · 이름 하나 422, 사이트 주소의 도메인 422, 다른 앱이 쓰면 409. 관리자의 `PATCH /api/apps/:id { version, domain }`에서만 바뀐다 (null · ""은 빼기). 대화의 `propose_setting app`은 `domain`을 받지 않는다 (공개 여부와 같다).

**앱 도메인으로 온 요청** (platform `HostGate`): 요청의 `Host`와 앞단 프록시의 `X-Forwarded-Host` 가운데 하나라도 앱 도메인(확인 전 것까지)이면 앱 도메인 요청이다.
- 지나는 경로는 모듈이 등록한 것뿐: blog의 GET · HEAD 셋(`/api/files/<해시>`(글의 사진), `/api/apps/by-slug/<앱>/icon`, `/.well-known/cairn-domain`)과 community의 `/api/community/…`(관리자 경로 `admin/` 빼고 쓰기까지, 3-1). 나머지(콘솔 · 관리 API · MCP · OAuth)는 없는 주소와 같은 404.
- 요청자는 늘 방문자다 (`ActorGuard`가 쿠키 · 토큰을 보지 않는다). 로그인 쿠키는 기본 도메인에만 있지만, 두 겹으로 막는다.
- 사이트 주소의 호스트는 앱 도메인으로 치지 않는다: 같은 값이 들어가도 콘솔이 잠기지 않게. 모르는 호스트(개발 · 서버끼리의 이름)는 기본 도메인처럼 다룬다.
- platform은 무엇이 도메인을 갖는지 모른다: blog가 앱 도메인 목록과 열 경로를, account가 사이트 주소를 등록한다 (`Lookups`와 같은 방식). 목록은 30초 기억하고, 도메인 · 사이트 주소를 바꾸면 바로 다시 읽는다.

**연결 확인**: 서버는 밖으로 요청하지 않는다 (내부망으로 요청을 보내는 길을 만들지 않게).
1. 앱 도메인의 `GET /.well-known/cairn-domain` → `{ token }`. 값은 서버 키에서 `app-domain`으로 나눈 열쇠로 "앱 id:도메인"을 서명한 것(`AppDomainProof`)이라 누구에게 보여도 되고, 다른 앱 · 도메인의 값은 서버 키 없이 만들 수 없다. 사이트 주소의 출처만 읽게 한다 (CORS). 기본 도메인 · 모르는 도메인은 404. 비공개 앱의 도메인도 답한다 (공개 전에 확인하게).
2. 관리자의 브라우저(앱 설정 화면)가 그 값을 읽어 `POST /api/apps/:id/domain/check { version, token }` → 맞으면 `domainCheckedAt`을 적은 앱, 틀리면 422 "연결되지 않은 도메인이에요".

**주소**:
- `AppView`에 `domain` · `domainCheckedAt` · `url`(확인한 도메인이면 `https://<도메인>/`, 아니면 `/<slug>`), `PublicAppView`에 `url`.
- `GET /api/apps/domains`(누구나) → `{ domains: [{ domain, slug }] }`: 공개 앱의 확인한 도메인만. 웹이 Host로 앱을 고른다.
- 화면 `GET /api/apps/site/:slug/screen?…&host=<방문자가 연 호스트>`: 그 앱의 도메인이면 도메인의 뿌리가 앱 주소(`base` `/`, `files` `/files`, RSS `/rss.xml`)이고 기본 도메인에 있는 것(사이트 첫 화면 · 로그인 · 그래프 · 페이지)은 사이트 주소로 적는다. 다른 호스트인데 확인한 도메인이 있으면 `{ redirect: https://<도메인>/<경로>, permanent: true }`(웹이 308). 미리 보기 토큰은 보내지 않는다. `host`가 없으면 지금처럼. 확인한 도메인이 있는 다른 앱의 링크는 어디서든 그 도메인으로.
- 보관 형식에는 넣지 않는다: 도메인과 확인은 배포마다의 값이다 (다른 서버에 복원하면 그 도메인이 아직 옛 서버를 가리킨다). 복원한 뒤 앱 설정에서 다시 정한다.

**웹 (3-0b)**: `proxy.ts`가 연결을 확인한 앱 도메인의 요청을 `/<slug>/…`로 바꿔 넘긴다(`/.well-known` · `/api` · `/_next`는 그대로, 앱 도메인의 `/admin` · `/login` · `/mcp` · `/oauth`는 그 앱 안의 없는 주소). 앱 화면은 방문자가 연 호스트를 `host`로 넘기고 서버의 308을 그대로 보내며, 앱 도메인에서는 격리 머리글의 출처를 그 도메인으로 적는다. `next.config`의 화면 머리글은 들어온 경로로 붙어 앱 화면의 격리 머리글(sandbox CSP)을 덮으므로 `/` · `/posts` · `/m`의 화면 머리글은 `proxy.ts`가 기본 도메인에서만 붙인다. RSS · 공개 앱 목록 · 콘솔의 앱 링크는 확인한 도메인으로. 앱 설정 › 도메인(저장 · 빼기 · 연결 확인 · 설정 방법), README에 DNS · Caddy 예시.

**고르지 않은 것**: 서버가 직접 그 도메인에 요청해 확인하기(서버가 밖 · 내부망으로 요청하는 길이 생긴다), DNS TXT 확인(DNS 조회 라이브러리 · 대기 시간, 관리자가 레코드를 하나 더 만든다), 도메인마다 쿠키 · 콘솔(회원 세션은 3-1에서 앱 도메인에만 따로 둔다).

### 11.5 3-1 커뮤니티 서버 인터페이스 (승인 2026-11-19)

**새로 정한 것**: ① 회원 로그인 · 쓰기는 앱 도메인에서만 (기본 도메인의 `/<slug>`에서는 읽기만: 관리자 쿠키와 같은 출처에 회원 쿠키를 두지 않는다. 3-2에서 공개 커뮤니티는 늘 확인한 도메인이 있게 바꿔, 기본 도메인 주소는 그 도메인으로 308이고 기본 도메인에서 읽는 것은 관리자의 미리 보기뿐이다: 11.6) ② 회원은 앱마다 따로 (같은 사람도 앱이 다르면 다른 회원) ③ 가입은 아이디 · 비밀번호로 간단히 (2026-11-19 사용자 결정으로 소셜 로그인에서 바꿈, 아래 "가입 · 로그인") ④ 이메일은 받지 않아 비밀번호를 잊으면 관리자가 초기화한다 (3-1c) ⑤ IP는 저장하지 않고 (시도 제한은 서버 메모리에서만 센다), 커뮤니티 앱은 지우지 않으며(비공개로 둔다), 관리자의 "내리기"는 숨김이고 내용은 남는다 (원칙 2).

**모듈**: `community`(스키마 `community`, `dependsOn: [platform]`). 다른 모듈과는 Lookups `community-app`(blog가 준다: 공개된 커뮤니티 앱인지, 관리자는 공간의 커뮤니티 앱)과 이벤트로만 잇는다. 폴더(데이터 묶음): `member/`(회원 · 회원 로그인 · 회원 세션), `topic/`(글 + 버전), `comment/`, `report/`, `moderation/`(가림 상태 · 결정 기록 · 차단, `ModerationService`만 글 · 댓글 · 회원 · 신고의 Repository를 함께 쓴다), `guard/member.guard.ts`. 글 클래스는 blog의 `Post`와 겹치지 않게 `Topic`.

**표**: `members`(app_id 값 · 닉네임(앱 안에서 하나, `nickname_key`) · `age_confirmed_at` · `blocked_until`(무기한은 9999-12-31) · `renamed_at` · `last_seen_at` · `login_id`(앱 안에서 하나, 바꾸지 않음) · `password_hash`(scrypt) · `password_changed_at`) · `member_sessions`(token_hash, 마지막 사용부터 30일) — 3-1a. `topics` + `topic_revisions`(추가만) · `comments`(고치기 없음) — 3-1b. `reports`(한 회원이 같은 대상에 한 번) · `decisions`(추가만, 관리자 결정 기록) — 3-1c. 상태는 `shown` · `hidden`(가림, 되돌림) · `removed`(관리자가 내림) · `deleted`(쓴 회원이 지움), 어느 상태든 내용 · 버전은 남는다. `decided_at` 앞의 신고는 임시 가림에 세지 않는다.

**요청자**: platform `MemberActor(appId, memberId)` — 권한 없음, 공간 없음(다른 모듈의 읽기에는 방문자와 같다), `MemberActor.require(actor, appId)`는 아니면 401. `MemberGuard`(커뮤니티 컨트롤러에만)가 앱 도메인 요청(HostGate의 `appId`)에서만 `cairn_member` 쿠키(HttpOnly · SameSite=Lax · https면 Secure, Domain 없이 그 도메인에만)를 읽는다. 관리자 쿠키는 앱 도메인에서 읽지 않는다(ActorGuard). 쓰기는 cross-site 403 · Origin이 있으면 그 앱 도메인의 출처 · 회원 쿠키를 실었으면 `X-Cairn-CSRF`가 그 쿠키의 확인 값(서버 키 `member-csrf` HMAC, `GET /api/community/me`가 준다).

**가입 · 로그인** (해킹 대비): 아이디는 영문 소문자로 시작하는 4~20자(영문 소문자 · 숫자 · `_`, 받은 값을 소문자로, 운영자로 보이는 아이디 막기, `LoginId`). 비밀번호는 관리자와 같이 10~200자에 조합 규칙 없음, 아이디 · 닉네임과 같은 값 · 한 글자 되풀이 · 유출 목록 맨 위의 흔한 값은 막는다(`MemberPassword`). 해시는 platform `PasswordHasher`(scrypt)이고 트랜잭션 밖에서 만들고 확인한다. 로그인 실패 문구는 "아이디나 비밀번호가 맞지 않아요" 하나이고, 없는 아이디도 같은 시간을 들여 확인한다(아이디가 있는지 알 수 없게). 틀린 로그인은 아이디마다 15분에 5번 · 곳(IP, IPv6는 /64)마다 15분에 20번까지, 가입은 곳마다 1시간에 3번까지(규칙을 지난 시도를 세어 겹친 아이디로 찔러보기도 막힌다) — 앱마다 서버 메모리에서만 센다(429). 가입 · 로그인할 때마다 새 세션 토큰, 비밀번호를 바꾸면 지금 브라우저 말고 다른 로그인은 모두 끝난다. 가입 · 로그인은 쿠키 없이 오므로 cross-site · 다른 Origin이면 403으로 막는다(다른 사이트가 남의 브라우저를 자기 계정으로 로그인시키지 못하게), 본문은 JSON만. 막힌 요청(401 · 403 · 429)은 지금처럼 관리자 보안 기록에 남는다(90일).

**API (회원 쪽, 앱 도메인에서만, 공개된 커뮤니티 앱이 아니면 404)**: `GET me` → `{ member: { id, loginId, nickname, joinedAt, writableAt, blockedUntil, version } | null, csrf }`(csrf는 회원 쿠키가 있으면 로그인이 끝났어도 그 쿠키의 값: 쿠키를 실은 쓰기는 이 값이 있어야 해서, 끝난 로그인의 쿠키가 남은 브라우저도 다시 로그인 · 가입한다. 3-2에서 고침) · `POST join { loginId, password, nickname, ageConfirmed }` → 201 회원(바로 로그인) · `POST login { loginId, password }` → 회원 · `POST logout` → 204 · `PATCH me { version, nickname }` · `PATCH me/password { current, next }` → 204 (3-1a). `GET topics?cursor=` · `GET topics/:id` · `POST topics { requestId, title, body }` · `PATCH topics/:id { version, title, body }` · `DELETE topics/:id { version }` · `POST topics/:id/comments { requestId, body }` · `DELETE comments/:id { version }` (3-1b) · `POST reports { topicId | commentId, reason, note? }` (3-1c). 작성자는 `{ nickname }`만, `version`은 내 글에만.

**API (관리자 쪽, 기본 도메인에서만, `assertOwner`, 3-1c)**: 모든 경로가 `/api/community/admin/:appId/` 아래다 (쓰기 경로에도 앱 id를 둔다: 앱을 먼저 확인하고 대상을 그 앱 안에서 찾게, 3-1c를 만들며 정함). 공간의 커뮤니티 앱이 아니면 404. 읽기 `GET topics?state=&cursor=`(모든 상태) · `topics/:id`(본문 전체 + 모든 댓글) · `reports?state=`(기본 open, 대상의 제목 · 앞부분 · 상태 · version과 함께) · `members` · `decisions` → `{ items, nextCursor }`(최근부터 30개, 쓴 회원은 `{ id, nickname, loginId }`). 쓰기는 200: `POST topics/:id/decide · comments/:id/decide { version, action: hide · show · remove, note? }`(show는 가린 것 · 내린 것을 되돌리고 열린 신고를 기각, hide · remove는 인정. 쓴 회원이 지운 것 · 이미 내린 것 409, 낡은 버전 409, 다른 action 422) · `POST members/:id/block { version, until?, note? }`(until이 없으면 무기한, 지난 때면 422) · `unblock { version, note? }`(차단 중이 아니면 409) · `reset-password { version, note? }` → `{ id, loginId, password, version }`(임시 비밀번호 16자는 이 응답에만, 해시만 저장하고 그 회원의 모든 로그인을 끝낸다. 관리자가 회원에게 직접 전한다). 결정마다 `decisions`에 한 줄.

**쓰기 규칙** (`WriteLimits`, 3-1b): 가입 뒤 5분 대기(422) · 글 시간당 5 · 하루 20 · 댓글 시간당 30 · 신고 시간당 10(429) · 링크 글 5 · 댓글 2(422) · 같은 본문 24시간(409) · 차단(403) · 닉네임 2~20자 · 7일에 한 번 · 운영자로 보이는 이름 막기(`Nickname`, 3-1a) · 길이 제목 100 · 본문 20,000 · 댓글 2,000 · 신고 메모 500. 셀 때는 쓰기 트랜잭션에서 회원 행을 잠그고 DB에서 센다 (재시작에도 그대로, 서버가 여럿이어도 같다). 값은 1차에 상수.

**신고 · 임시 가림** (3-1c): 신고(`POST reports` → 201 `{ id, createdAt }`, 보이는 글 · 보이는 글의 보이는 댓글만 404, 내 것 422, 같은 대상 두 번 409, 시간당 10개 429, 차단 403) → `community.report.added` → 일꾼이 `ModerationService.hideByReports`(대상을 잠그고 `decided_at` 뒤 서로 다른 회원의 열린 신고 3건이면 `hidden`(`hidden_by: reports`) + 결정 기록(`by: system`) + `community.content.hidden` → 관리자 즉시 알림 "신고로 가린 글", 관리자가 그 대상을 정하면 읽음). 새 신고는 앱마다 묶어서 알린다. 가려진 글 고치기 409 · 가려진 글에 댓글 404. 가림 규칙은 `Moderation` 한 곳(글 · 댓글이 같다). 3-3에서 AI 운영 팀은 같은 이벤트로 의견을 내고 승인 뒤 `ApprovedActor`로 같은 서비스를 부른다.

**바꾼 기존 코드** (3-1a): platform `HostGate`(`registerApps(읽기)`가 도메인 → 앱 id를 주어 `request.appId`, 앱 도메인에서 열 경로는 모듈이 `openPaths(경로, writes)`로: blog는 사진 · 아이콘 · 연결 확인 값의 GET, community는 `/api/community` 아래에서 `admin/`을 뺀 경로를 쓰기까지). blog: 앱 종류 `community`(마이그레이션 `blog_app_community`, 메뉴 · 블로그 글 없음 422, 지우기 422, RSS 없음, 시작 코드 `starters/community`), Lookups `community-app`. 마이그레이션 `community_members`(회원 · 세션) → `community_member_passwords`(아이디 · 비밀번호로 바꿈, 소셜 로그인 표 지움).

**나눠 만들기**: 3-1a 회원 · 가입 · 로그인 · 세션 · MemberGuard (끝, 2026-11-19) → 3-1b 글 · 버전 · 댓글 · 쓰기 규칙 (끝, 2026-11-19, 마이그레이션 `community_topics`) → 3-1c 신고 · 임시 가림 · 관리자 결정 · 차단 · 비밀번호 초기화 · 이벤트 · 알림 (끝, 2026-11-19, 마이그레이션 `community_moderation`). 3-2 웹은 11.6.

**고르지 않은 것**: 기본 도메인에서도 회원 로그인(관리자 쿠키와 같은 출처), 사이트 전체에 회원 하나(앱 사이 활동이 이어진다), 소셜 로그인(카카오 앱 등록 · 키 관리), 이메일 가입(인증 · 재설정 메일 서비스), 글 · 댓글 한도를 메모리에서 세기(재시작에 비고 회원 단위가 아니다. 로그인 · 가입의 시도 제한만 메모리: IP를 저장하지 않으려고), 신고와 가림을 한 트랜잭션에(신고 묶음이 글까지 쓰게 된다), 관리자 완전 삭제(원칙 2, 정말 지워야 하는 글은 3-4에서 예외로 따로), 댓글 고치기 · 답글(1차 범위 밖).

### 11.6 3-2 커뮤니티 웹 (승인 2026-11-19, 끝남)

**한 장 요약**: 읽기 화면(목록 · 글)은 지금처럼 앱 코드의 템플릿(격리)으로 그리고, 웹의 route handler가 블로그 화면 API(틀)와 이미 있는 회원 API(`GET topics` · `topics/:id` · `me`)를 함께 불러 데이터를 채운다. 쓰기는 Cairn이 그리는 고정 화면(React)을 앱 도메인의 `/_/…`에 둔다 (격리된 앱 화면은 출처가 없어 쿠키 · 확인 값이 통하지 않는다, 11.0). 관리자는 앱 관리의 커뮤니티 탭에서 정한다. 서버에 "앱 화면 데이터" 등록부를 새로 두지 않았다 (blog → community 연결이 하나 더 생긴다).

**공개 조건 (11.5 ①을 바꿈)**: 커뮤니티 앱은 연결을 확인한 도메인이 있어야 공개된다 (`App.edit`, 공개로 바꿀 때만 422 "커뮤니티는 도메인 연결을 확인한 뒤에 공개할 수 있어요"). 공개 중에는 확인한 도메인을 바꾸거나 빼지 않는다 (`App.setDomain` 422, 비공개로 바꾼 뒤에). 도메인은 백업에 없어 복원한 공개 커뮤니티는 도메인을 그대로 정하고 확인한다. 콘솔은 확인 전에 공개 단추를 막고 설정으로 안내한다.

**주소 (앱 도메인 기준)**:

| 주소 | 화면 | 누가 그림 |
|---|---|---|
| `/` · `/?cursor=` | 글 목록 (`index.html`) | 템플릿 |
| `/t/<글 id>` | 글 하나 + 댓글 (`topic.html`, 없으면 `index.html`). 없거나 가린 글은 그 앱의 `404.html`을 404로 | 템플릿 |
| `/_/join` · `/_/login?return=` | 가입(아이디 · 비밀번호 · 확인 · 닉네임 · 만 14세) · 로그인. 이미 회원이면 돌아갈 곳으로 | 고정 |
| `/_/me` | 내 정보: 아이디 · 가입일, 닉네임 · 비밀번호 바꾸기, 로그아웃, 가입 대기 · 차단 안내 | 고정 |
| `/_/write` · `/_/write/<글>` | 새 글 / 내 글 고치기 · 삭제 | 고정 |
| `/_/comment/<글>` | 댓글 달기 + 이 글의 내 댓글 삭제 | 고정 |
| `/_/report?topic=` · `?comment=&topic=` | 신고: 까닭 다섯 + 메모 | 고정 |

- 고정 화면은 그 앱의 도메인으로 온 요청에서만 열린다 (`_community/member-page.ts`: 기본 도메인의 `/<앱>/_/…`와 커뮤니티가 아닌 앱의 도메인은 404). 로그인하지 않고 회원 화면에 오면 `/_/login?return=<그 화면>`으로. 돌아갈 곳은 그 도메인 안의 경로만 (`memberReturn`: `safeReturnPath` + 가입 · 로그인 화면은 첫 화면으로).
- 폴더는 `app/(blog)/[app]/%5F/…` (Next에서 `_`로 시작하는 폴더는 주소가 되지 않아 `%5F`). `proxy.ts`가 앱 도메인의 `/_/…`에 화면 머리글(`frame-ancestors 'none'` · `X-Frame-Options` 등)을 붙인다: 로그인 폼을 다른 사이트가 겹쳐 놓지 못하게.
- 회원 쓰기는 화면을 그릴 때 서버에서 읽은 `me.csrf`를 `X-Cairn-CSRF`로 싣는다 (`_community/member-api.ts`). 로그인 · 가입 뒤에는 화면을 새로 열어(`location.replace`) 새 값을 받는다. 만들기의 `requestId`는 `getRandomValues`로 만든다 (`crypto.randomUUID`는 https에서만 있어 http로 연 시험용 도메인에서 깨졌다).

**템플릿 데이터 (약속 `cairn: 1`에 이름만 더함, `skills/cairn-make/references/app-code.md`)**: `screen` `'topic'` · `isTopic`, 모든 커뮤니티 화면의 `community: { open, member: { nickname } | null, joinUrl, loginUrl, meUrl, writeUrl }`(앱 도메인이 아닌 미리 보기는 `open: false` · 링크 null), 첫 화면의 `topics: [{ title, excerpt, url, date, dateText, author: { nickname }, comments }]` · `more: { url } | null`, 글 화면의 `topic: { title, html, url, date, dateText, edited, author, mine, editUrl, commentUrl, reportUrl, comments: [{ body, date, dateText, author, mine, reportUrl }] }`. 회원 정보는 닉네임과 내 것인지(`mine`)만 싣는다 (아이디 · 회원 id · 확인 값은 앱 JS가 읽을 수 있어 싣지 않는다). 글 본문은 마크다운 정화기로 그리고 바깥 링크에 `rel="nofollow ugc noopener noreferrer"`, 댓글은 글자 그대로(이스케이프). 미리 보기는 그 앱의 확인한 도메인으로 쿠키 없이 읽는다 (비공개 커뮤니티는 빈 목록).

**서버에서 바꾼 것 (3-2a)**: blog 화면 API가 커뮤니티 앱의 `t/<uuid>`를 `topic` 틀로 받고 그 밖은 `missing`. 시작 코드 `starters/community`(`index.html` · `topic.html` · 회원 링크가 든 `header.html` · `community.css`). community view의 응답 모양을 웹이 타입으로 쓰게 (`toJSON(): object` 지움). `me`의 csrf (11.5).

**관리자 (3-2c)**: 스토어의 커뮤니티 카드("회원 가입 · 글 · 댓글 · 신고. 도메인을 연결해야 공개"). 앱 관리 탭이 종류마다 다르다: 커뮤니티는 개요 · 커뮤니티 · 운영 팀 · 코드 · 설정. 커뮤니티 탭은 신고(열린 신고 · 인정 · 기각) · 글(상태로 거르기, 본문 · 모든 댓글 펼치기) · 회원(차단 1일 · 7일 · 30일 · 기한 없음, 풀기, 비밀번호 초기화: 임시 비밀번호를 한 번만 보이고 복사) · 기록. 결정 단추는 상태마다 서버 규칙과 같다 (보임: 신고 기각 · 가림 · 내림, 가림: 되돌림 · 내림, 내림: 되돌림, 지움: 없음), 메모는 결정 기록에만. `community.*` 변경 신호로 다시 읽는다 (회원의 글 · 댓글 자체는 신호가 없어 다시 연결될 때 · 결정한 뒤에 읽는다).

**확인 (3-2d)**: 운영 빌드의 웹 + 로컬 서버를 띄우고 Playwright로 시험용 도메인을 127.0.0.1에 묶어 관리자 공개 → 가입(폰 크기) → 가입 대기 안내 → 글 → 다른 회원의 로그인 화면 보내기 · 가입 · 댓글 · 신고 → 신고 3건으로 임시 가림(그 앱의 404) → 관리자 되돌림 → 다시 보임 · 비밀번호 초기화 · 기록까지 돌렸다. 웹은 앱 도메인 목록을 30초 기억해, 막 공개한 커뮤니티의 도메인은 그 뒤에 열린다.

**고르지 않은 것**: 서버에 앱 화면 데이터 등록부를 두고 blog가 community 데이터를 받기(모듈 연결이 늘고 기본 도메인에서 회원을 알아보는 길이 따로 필요), 템플릿 안의 폼 · 앱 JS로 쓰기(격리 문서에는 쿠키가 없다), 앞에 붙는 것 없는 `/join` 같은 주소(나중에 앱 코드 주소와 겹친다), 독에 커뮤니티 화면 따로(커뮤니티는 앱마다라 앱 관리 안).

### 11.7 3-3 AI 신고 검토 (2026-11-24, 끝)

사용자 결정 (2026-11-24): 3-3을 추천안대로 진행. 2026-11-19 계획(팀 템플릿 · 비공개를 읽지 않는 팀)은 2026-11-21 팀을 없애며 맞지 않게 되어, 팀 대신 **일마다 도구를 좁힌 작업 토큰**으로 바꿨다.

**흐름**: 회원의 신고 → `ModerationService.hideByReports`(일꾼)가 임시 가림을 보면서 검토 일을 요청한다 (`ReviewRequest`: `task.task.requested`, kind `community_review`, 담당 없음 = 대표가 아닌 일꾼 누구나, requestId는 대상 · 관리자가 마지막으로 정한 때마다 하나: 신고가 더 와도 같은 검토, 관리자가 정한 뒤의 신고는 새 검토). 지시는 대상 id뿐이다 (회원 글을 지시문에 싣지 않는다). 일꾼은 스킬 `cairn-moderate`대로 `community_case`로 읽고 결정 하나를 `propose_setting`(setting `moderation`)으로 올린다 → 관리자가 앱 관리 › 커뮤니티 › 신고 줄의 **AI 의견**(바뀔 줄 · 근거)이나 승인 화면에서 승인 · 반려 → 승인하면 관리자 결정과 같은 줄(`contentIn` · `memberIn`)로 반영, 결정 기록은 `approved`(by_id는 승인한 관리자). 관리자가 먼저 직접 정했으면 제안은 낡은 버전이라 적용에서 실패로 끝난다.

**막는 것**:
- 작업 토큰의 도구 목록 (`task-kinds.json`의 `tools`, `AgentActor`에 봉인, MCP 입구가 목록 · 부르기에서 거름): `community_case` · `propose_setting`만. 보관함 · 위키 · 주소 읽기 · 브라우저 · 사이트 도구는 보이지도 불리지도 않는다. 회원 글에 숨은 지시가 있어도 비공개에 닿거나 밖으로 보내지 못한다.
- 제안할 설정 (`settings`): `moderation`만 (그 일꾼은 승인 동작 없이도 이 설정만 올린다).
- 실행은 늘 관리자 승인 뒤 (원칙 7 · 10). AI가 가리거나 지우거나 차단하는 길은 없다. 시스템의 임시 가림(3명)은 그대로.
- 일꾼이 보는 것: 글 · 댓글의 본문 · 상태 · 버전, 쓴 회원의 닉네임 · 가입일 · 지난 가림 · 내림 · 차단 수, 신고의 까닭 · 메모. 회원 아이디 · 신고한 회원은 싣지 않는다.

**제안 모양** (`ModerationChange`): 글 · 댓글 `{ app_id, target: topic · comment, state: shown(기각) · hidden(가림) · removed(내림) }` + 서버가 `open_reports: 0`을 더해 기각도 바뀐 줄이 생긴다. 회원 `{ app_id, target: member, blocked_until: forever · ISO 시각 · null(풀기) }`. 대상 id · version은 `community_case`의 값. 일 하나에 기다리는 승인은 하나라 결정도 하나: 내림과 차단이 함께 필요하면 내림을 올리고 차단은 근거에 적는다.

**고르지 않은 것**: AI 의견을 커뮤니티 표에 따로 남기기(승인 대기와 두 군데가 되어 어긋난다: 의견 = 기다리는 승인의 근거 · 바뀔 줄), 대표에게 맡기기(대표의 지시문 · 위임 도구가 섞이고 대화 일과 자리를 다툰다), 비공개 읽기를 권한으로만 막기(모든 일꾼이 같은 권한이라 일마다 갈라야 한다), 검토를 켜고 끄는 설정(검토는 의견만 내고 비용은 대상마다 일 하나라 1차에는 두지 않음).

### 11.8 3-4 약관 · 탈퇴 · 보관 (2026-11-24, 끝)

사용자 결정 (2026-11-24): "3-4 진행해줘". 추천안대로 만들었다.

**약관** (`community/terms/`, 표 `community.terms`): 앱마다 이용약관(`terms`) · 개인정보처리방침(`privacy`) 두 장. 추가만 하는 버전이다 (트리거가 UPDATE · DELETE를 막는다): 지난 버전에 동의한 회원이 있어 덮지 않고 새 버전을 쌓고, 공개된 것은 늘 마지막 버전이다.
- 관리자: 앱 관리 › 커뮤니티 › 약관 (페이지 앱은 회원 탭 위). `POST api/community/admin/:appId/terms/:kind { version, body }`, version은 본 버전(처음이면 0). 그사이 다른 버전이 올라왔으면 409.
- 처음 쓸 때는 초안이 채워진다 (`apps/server/starters/terms/*.md`, `{{app}}`은 앱 이름). 초안의 `[ ]` 칸(운영자 · 연락처 · 보관 기간 등)은 관리자가 채운다: 법률 문서라 Cairn이 대신 정하지 않는다.
- 일꾼은 설정 바꾸기 제안 `terms`(`{ app_id, kind, body }`)로만 고친다. 승인하면 새 버전(`by_kind` approved). 제안한 뒤 관리자가 고쳤으면 적용이 실패로 끝난다 (본문 비교, 원칙 3).
- 회원 화면: 앱 도메인의 `/_/terms` · `/_/privacy`(`GET api/community/terms/:kind`, 없으면 404). 모든 회원 화면 아래에 두 링크.

**가입 동의**: 둘 다 공개돼야 가입을 받는다 (아니면 409 "아직 약관이 공개되지 않아"). 가입 화면은 두 약관을 접어 보이고 동의 체크를 받아 본 버전(`termsVersion` · `privacyVersion`)을 보낸다. 그사이 바뀌었으면 409 "약관이 바뀌었어요"로 다시 읽게 한다. 회원 행에 동의한 버전을 남긴다 (`terms_version` · `privacy_version`). 약관이 바뀌어도 이미 가입한 회원에게 다시 묻지는 않는다 (1차: 바뀐 뒤 다시 동의 받기는 법이 요구하는 경우가 생기면).

**탈퇴** (`POST api/community/me/leave { password }`, 내 정보 화면 아래): 지금 비밀번호를 확인하고(틀리면 400, 시도 제한에 센다), 한 번 더 묻고, 개인정보를 바로 지운다: 아이디 · 비밀번호 해시 · 닉네임(→ "탈퇴한 회원") · 겹침 열쇠 · 차단 메모 · 마지막 접근. `left_at`을 남기고 모든 로그인을 끝낸다. 글 · 댓글은 "탈퇴한 회원"으로 남는다 (원칙 2, 남기고 싶지 않은 글은 먼저 지우라고 화면에 적는다). 같은 아이디 · 닉네임은 다시 쓸 수 있다. "탈퇴"가 든 닉네임은 막는다. 관리 화면의 아이디 칸은 "탈퇴".

**IP를 남기지 않는다**: 앱 도메인 요청의 거절은 보안 기록(`security_events`, IP를 담는다)에 남기지 않는다 (회원 IP를 저장하지 않는다는 개인정보처리방침과 맞추려고). 시도 제한은 지금처럼 서버 메모리에서만 센다.

**보관**: md 보관 형식(GitHub 동기화 · 백업 zip)에는 넣지 않는다. 회원 · 글 · 약관은 앱의 것이라 앱 내보내기(`api/community/admin/:appId/export`, 12.5)에 담는다: `members.json`에 동의한 약관 버전 · 탈퇴한 때, `terms/<종류>-v<버전>.md`에 약관의 모든 버전. 전체 백업은 DB 백업이다.

**고르지 않은 것**: 약관을 md 보관 형식에 넣기(플랫폼 경로 규칙 · 공개 저장소 거르기가 blog의 앱 공개 여부를 알아야 하고, 복원에 약관만 있고 회원이 없는 앱이 생긴다), 탈퇴 유예 기간(지운 정보를 그동안 들고 있어야 한다. 실수는 한 번 더 묻기와 비밀번호로 막는다), 탈퇴하면 글도 지우기(원칙 2와 다른 회원의 댓글 흐름이 깨진다. 글마다 지우기는 이미 있다), AI가 약관을 바로 고치기(회원에게 보이는 약속이라 원칙 7대로 승인 뒤).

## 12. 앱 플랫폼: 앱은 화면, 기능은 Cairn (승인 2026-11-22)

사용자 결정 (2026-11-22): "앱 단위로 자유도가 있으면 좋겠다 (카페24 · 워드프레스처럼)" · "영어 공부 앱도 만든다" · "Supabase처럼" · "1단계부터 5단계까지 한번에 진행하고 그 다음에 검증".
앱마다 서버를 따로 두지 않는다. 앱은 화면 묶음(9장 · 9.13)과 선언서(`cairn.json`)만 갖고, 회원 · 데이터 · 버전 · 승인 · 백업 · 도메인은 Cairn이 준다. 설계는 오픈소스를 그대로 붙이지 않고 참고해서 우리 구조 안에 만든다: 데이터는 Supabase(실제 Postgres 표 · 행 수준 보안 · 표에서 생기는 API), 규칙의 단순함과 앱 하나가 통째로 나오는 것은 PocketBase, 화면은 앱 · 기능은 플랫폼이라는 나눔은 카페24.

### 12.0 한 장 요약

| 단계 | 만드는 것 | 끝나면 |
|---|---|---|
| P1 | 자기 도메인에서 격리 풀기, 선언서의 권한 | 저장소 · 마이크 · 위치 · 홈 화면 설치 |
| P2 | 회원을 모든 앱에, 로그인 화면에 앱 테마 | 페이지 앱에 로그인 |
| P3 | 앱 데이터: 앱마다 스키마 · 표 선언 · 규칙 · 조회 API · `cairn.js` | 학습 기록 · 순위표 같은 저장이 되는 앱 |
| P4 | 앱 내보내기, 배포 도구 | 큰 앱을 계속 고치고, 떼어 간다 |
| P5 | 커뮤니티 화면 자유화 | 글쓰기 · 댓글까지 앱 코드가 그린다 |

**바뀌는 결정**: 2026-11-18 "앱 화면에 같은 출처를 주지 않는다(`sandbox`에 `allow-same-origin` 없음)"는 기본 도메인의 `/<앱>`과 미리 보기에 남고, **연결을 확인한 자기 도메인으로 연 공개 화면은 격리를 푼다** (9.12에서 미뤄 둔 길). 자기 도메인은 콘솔과 다른 출처라 앱 JS가 관리자 로그인 · 콘솔 API에 닿지 못한다 (쿠키는 Domain 없이 그 호스트에만, `HttpOnly`).

**새 위험과 남는 방어**: 앱 코드가 그 앱 회원의 이름으로 그 앱의 데이터 · 글을 읽고 쓸 수 있다 (카페24 스킨과 같은 조건). 방어: 공개 앱의 새 버전은 관리자가 확인해야 보인다(원칙 7) · 바깥으로의 요청은 `cairn.json`의 `hosts`뿐(CSP) · 비밀번호는 Cairn의 고정 화면에서만 받는다(앱 코드를 거치지 않는다) · 회원 쿠키는 JS가 읽지 못한다 · 콘솔 · 보관함은 다른 출처.

### 12.1 선언서 (`cairn.json`, blog의 `AppManifest`)

```json
{
  "cairn": 1,
  "render": "static",
  "hosts": [],
  "members": true,
  "permissions": ["microphone"],
  "theme": { "accent": "#3b6cff", "background": "#ffffff", "text": "#1c1c1e", "logo": "icon.svg" },
  "tables": {
    "lessons":  { "columns": { "title": "text", "level": "int", "body": "json" }, "read": "anyone", "write": "admin" },
    "progress": { "columns": { "lesson": "int", "score": "int" }, "read": "owner", "write": "owner" }
  }
}
```

| 이름 | 규칙 |
|---|---|
| `members` | 참이면 이 앱에 가입 · 로그인이 열린다 (커뮤니티 앱은 늘 열려 있다). 도메인을 연결한 공개 앱에서만 |
| `permissions` | `microphone` · `camera` · `geolocation` 가운데. 격리를 푼 화면의 `Permissions-Policy`에만 열린다 |
| `theme` | 고정 화면(가입 · 로그인 · 내 정보 …)에 입히는 색(`#rrggbb`) `accent` · `background` · `text`와 `logo`(묶음의 파일 이름) |
| `tables` | 표 20개까지. 이름 · 칸 이름은 영문 소문자로 시작하는 소문자 · 숫자 · `_` 40자까지. 칸 30개까지, 타입은 `text` · `int` · `number` · `bool` · `time` · `json`. `id` · `owner` · `created_at` · `updated_at`은 Cairn이 붙이는 칸이라 선언하지 않는다 |
| `read` | `anyone`(누구나) · `member`(로그인한 회원) · `owner`(쓴 회원만) · `admin`(관리자 · 승인받은 일꾼만) |
| `write` | `member`(회원이 자기 행을 만든다) · `owner`(만들고 자기 행을 고치고 지운다) · `admin`. `member` · `owner` 규칙은 회원이 있는 앱에서만 |

- 보이는 버전의 선언서(정리한 모양)는 `blog.apps.code_manifest`에 둔다: 버전을 보일 때(`AppCode.add` · `show`) 함께 바뀐다. 미리 보기는 그 버전의 파일에서 읽는다.
- 칸의 타입은 바꾸지 못한다 (앞 버전과 다르면 422: 새 이름으로 더한다). 선언에서 뺀 표 · 칸은 API에서 사라지지만 DB에는 남는다 (원칙 2).
- `blog.app_code.shown` 이벤트에 `members` · `tables`를 싣는다: community가 받아 표를 맞춘다 (12.4).

### 12.2 P1 격리 풀기

- 서버(`AppSiteQuery.screen`)가 화면마다 `open`을 답한다: 그 앱의 도메인으로 왔고 미리 보기 토큰이 없을 때만 참. `permissions`도 함께.
- 웹(`appHeaders`): `open`이면 CSP에서 `sandbox`를 빼고(`script-src` · `connect-src` · `form-action`은 그 출처와 `hosts`만) `Permissions-Policy`에 선언한 권한을 연다. 앱 파일도 같은 머리글로 내보낸다 (서비스 워커 · 웹 앱 매니페스트가 돌게).
- 기본 도메인의 `/<앱>` · 미리 보기(`/~<토큰>`)는 지금처럼 격리한다: 저장소 · 회원 · 데이터를 쓰는 앱은 도메인을 연결하고 공개한 뒤에 온전히 돈다 (`cairn.js`의 `cairn.open`이 거짓이면 앱이 안내를 그린다).

### 12.3 P2 앱 회원

- 회원은 community 모듈이 그대로 맡는다 (모듈을 새로 떼지 않는다: 글 · 신고가 회원 행을 함께 잠그고, 11.2의 "회원 쪽을 다른 컨테이너로" 길도 이 모듈 단위다). 모듈의 뜻이 "커뮤니티"에서 "앱의 회원 쪽 전체(회원 · 글 · 앱 데이터)"로 넓어진다.
- blog가 Lookups `member-app`을 준다: 공개 앱 가운데 커뮤니티이거나 `code_manifest.members`가 참인 앱. 회원 API(`me` · `join` · `login` · `logout` · `PATCH me`)는 `member-app`, 글 · 댓글 · 신고는 지금처럼 `community-app`.
- 웹의 고정 화면 `/_/join` · `/_/login` · `/_/me`는 회원이 있는 모든 앱의 도메인에서 열린다. 글쓰기 · 댓글 · 신고 화면은 커뮤니티 앱만.
- 테마: `GET api/apps/by-slug/:slug`가 `members` · `theme`를 함께 준다. 웹의 `MemberFrame`이 색을 CSS 변수로, 로고를 머리에 입힌다.
- 앱 코드는 `cairn.me()`로 `{ member: { nickname } | null }`을 읽고, 로그인은 `cairn.login()`(고정 화면으로 보낸다)으로 한다. 비밀번호는 앱 코드를 거치지 않는다.

### 12.4 P3 앱 데이터 (community `data/`)

- **저장**: 앱마다 Postgres 스키마 `app_<앱 id의 16진 32자>`, 선언한 표마다 실제 표 하나. 모든 표에 `id uuid`(UUIDv7) · `owner uuid`(쓴 회원, 관리자가 넣은 행은 NULL) · `created_at` · `updated_at`. 선언한 칸은 모두 NULL 허용.
- **맞추기**: `blog.app_code.shown`을 받아(`AppTablesHandler`) 없는 스키마 · 표 · 칸을 더하고 규칙에 맞게 정책을 다시 건다. 지우는 DDL은 없다. 지금 열려 있는 표 · 칸 · 규칙은 `community.app_tables`(공간 · 앱 · 이름 · 칸 · 규칙 · 맞춘 버전)에 둔다: API는 이 목록의 이름만 SQL에 쓴다 (요청의 글자를 SQL에 넣지 않는다).
- **권한 (행 수준 보안)**: 표마다 RLS를 켜고 규칙을 정책으로 건다. 회원 쪽 API는 트랜잭션 안에서 `SET LOCAL ROLE cairn_app`(다른 스키마에 권한이 없는 역할, 마이그레이션이 만든다)과 `cairn.member`(회원 id, 없으면 빈 값)를 정한 뒤 쿼리한다: `owner` 규칙은 `owner = cairn.member`, `member`는 `cairn.member`가 있을 때. API 코드의 조건이 틀려도 DB가 남의 행을 주지 않는다. 관리자 · 일꾼의 쓰기는 역할을 바꾸지 않는다.
- **API (앱 도메인, `MemberGuard`)**: `GET api/community/data/:table?<칸>=eq.<값>&order=<칸>.desc&limit=&offset=`(연산 `eq` · `neq` · `gt` · `gte` · `lt` · `lte`, 100개까지, 내 줄만은 `owner=eq.me`. 읽기 규칙에 맞지 않는 줄은 오류 없이 빠진다: 방문자가 `member` · `owner` 표를 읽으면 빈 목록) · `POST`(만들기, `owner`는 서버가 넣는다) · `PATCH :id` · `DELETE :id`. 쓰기는 회원 API와 같은 세 겹(같은 사이트 · Origin · `X-Cairn-CSRF`).
- **한도**: 표 하나 10만 줄 · 회원 하나가 표마다 1,000줄 · 글 칸 1만 자 · json 칸 16KB · 쿼리 5초. 넘으면 422 · 429.
- **`cairn.js`** (`/_/cairn.js`, 웹이 준다): `cairn.open` · `cairn.me()` · `cairn.login()` · `cairn.logout()` · `cairn.from('<표>').select().eq().order().limit()` · `.insert()` · `.update(id)` · `.delete(id)`. Supabase 클라이언트와 모양만 비슷하고 호환되지는 않는다.
- **관리자**: `api/community/admin/:appId/data`(표 목록 · 줄 수) · `…/data/:table`(읽기 · 넣기 · 지우기), 콘솔 앱 관리의 데이터 탭.
- **일꾼**: 표에 쓰는 일은 바깥에 보이는 내용을 바꾸므로 설정 제안(`propose_setting` setting `app_data`, op `create`, fields `{ app_id, table, rows }`, 200줄까지)으로 올리고 관리자가 승인하면 들어간다 (원칙 7). 지금 표와 칸은 `get_settings kind: app_data`로 읽는다. 일꾼은 줄을 넣기만 한다 (회원의 줄을 고치거나 지우지 않는다).
- **경계 검사**: `app_<…>` 스키마는 community의 것이다. `pnpm db:check`가 주인 없는 스키마로 세지 않고, 플러그인은 그 모양의 스키마 이름을 쓰지 못한다.
- **서버 로직**: 앱 코드는 서버에서 돌지 않는다. 매일 레슨 만들기 · 순위표 정리 같은 일은 일꾼의 스케줄이 맡는다.

### 12.5 P4 내보내기 · 배포

- **앱 내보내기** (관리자): `GET api/community/admin/:appId/export` → zip. `tables.json`(선언) · `schema.sql`(CREATE TABLE) · `data.sql`(INSERT, Postgres가 값을 적는다) · `members.json`(아이디 · 닉네임 · 비밀번호 해시 · 가입한 때). 화면 코드는 이미 있는 `GET api/apps/:id/code/versions/:seq/zip`. 콘솔의 "앱 내보내기"가 둘을 받는다. `schema.sql` · `data.sql`은 어느 Postgres에나 들어간다.
- **배포 도구** (두 걸음, 결과물의 올리기 표와 같은 방식): ① MCP `app_code_upload { app, size, sha256, note? }`(write 권한) → `{ upload_path, header, token, expires_at }`. 표(`DeployTicket`)는 서버 키로 봉인하고 그 앱 · 그때의 마지막 버전 · 크기 · sha256 · 메모에 묶인다 (10분). ② `PUT api/apps/:id/code/versions`(본문이 zip, `Content-Type: application/zip`, 머리글 `X-Cairn-Deploy`에 표, 20MB까지, 로그인 없음). 기기 토큰은 `/mcp`에서만 요청자가 되고 JSON 본문은 512KB까지라 zip을 MCP에 싣지 않는다. 표와 다른 묶음 · 다른 앱은 403, 표를 받은 뒤 다른 버전이 생겼으면 409. 공개 앱은 확인 대기(관리자가 공개), 비공개 앱은 바로.
- **배포 기기**: OAuth scope `deploy` → 권한 `write`만 (이 컴퓨터로 돌아가는 연결만 요청할 수 있다). 승인 화면에 "초안 쓰기 · 앱 코드 올리기"로 보인다.
- **CLI**: `cairn app deploy <앱 주소> <폴더> [--site <블로그 주소>] [--note <메모>]`. 폴더를 zip으로 묶고(숨김 파일 · `node_modules` · 링크는 빼고 알린다), 처음에는 브라우저로 배포 기기를 승인받아 열쇠를 `~/.cairn/credentials.json`의 `deploy`에 둔다. 다음부터는 `--site` 없이 그 블로그로 올린다. 올리기는 `~/.cairn/bin/cairn-deploy.mjs`가 한다 (토큰 갱신을 훅과 같은 잠금으로).
- 큰 앱의 소스는 GitHub 저장소에 두고 코드 작업(code-github)으로 고친다. Cairn에는 빌드 결과만 올라온다.

### 12.6 P5 커뮤니티 화면 자유화

- 커뮤니티 앱도 자기 도메인에서 격리를 푼다. 앱 코드가 `cairn.community`로 글 · 댓글 · 신고 API(`api/community/topics` …)를 직접 부른다. 쓰기 확인 값은 `cairn.js`가 `me`에서 읽어 싣는다.
- 고정 화면(`/_/write` · `/_/comment` · `/_/report`)은 앱이 그리지 않을 때의 기본값으로 남는다. 가입 · 로그인 · 비밀번호는 늘 고정 화면이다.
- 커뮤니티 앱도 정적 앱(9.13)이 될 수 있다: 글 목록을 앱 JS가 API로 읽어 그린다 (검색에 잡히려면 템플릿 앱으로 둔다).
- 커뮤니티 앱은 `members`를 적지 않아도 회원 규칙(`member` · `owner`)의 표를 쓴다 (좋아요 · 북마크 같은 것).

### 12.6a 지도 (지도 플러그인, 2026-11-23)

- 관리자가 플러그인 `map`에 지도 회사(OpenStreetMap · 카카오 · 네이버 · 구글)와 브라우저용 키를 등록한다. 키는 방문자의 브라우저가 쓰는 공개 값이라 플러그인의 공개 설정이고, 각 회사 콘솔에 앱 도메인을 등록해 묶는다. 서버용 비밀 키는 받지 않는다.
- 앱 코드는 `cairn.js`의 `cairn.map.create(자리, { places: [{ lat, lng, name }], zoom?, onSelect? })` → `{ provider, map, sdk, select(i) }`만 쓴다. 회사마다 다른 스크립트 · 핀 · 이름 창 · 범위 맞추기는 `cairn.js`(웹 `_blog/cairn-map.ts`)가 감춘다. 회사를 바꿔도 앱 코드는 그대로다.
- 키가 있는 지도는 등록한 도메인에서 온 요청만 받는다. 격리된 화면(미리 보기 · 기본 도메인 · AI가 만든 페이지)은 어디서 왔는지를 보내지 않아 돌지 않으므로, 그 화면과 키가 빈 경우에는 키가 필요 없는 OpenStreetMap(Leaflet 1.9.4, `integrity` 고정)으로 그린다. 고른 회사의 지도를 10초 안에 받지 못해도 OpenStreetMap으로 그리고, 그것도 못 받으면 Error (앱은 목록을 남긴다).
- 앱 화면의 격리 머리글은 그 화면에서 쓰는 지도 회사와 OpenStreetMap의 호스트를 더 연다 (`_blog/map-config.ts`, 설정은 30초 기억). 앱의 `cairn.json` `hosts`에 지도 회사를 적지 않는다.
- 페이지(AI가 만든 HTML)는 늘 격리라 OpenStreetMap 지도만 그린다 (스킬 `cairn-make`의 `map.md`). 카카오 · 네이버 · 구글 지도가 필요한 것은 페이지 앱(정적 앱, 자기 도메인)으로 만든다.
- 확인 (2026-11-23, 브라우저): 앱 도메인에서 카카오 스크립트(테스트용 SDK로 바꿔 끼움)가 키와 함께 실리고 핀 2개 · 범위 맞춤 · 핀 누르기(`onSelect`) · 이름 창, 미리 보기(격리)에서는 OpenStreetMap 핀 2개 · 누르기, 카카오를 받지 못하면 OpenStreetMap. 실제 카카오 · 네이버 · 구글 키와 도메인으로는 아직 확인하지 않았다 (네이버는 키 이름 `ncpKeyId`를 실제 콘솔에서 확인할 것).

### 12.7 고르지 않은 것 · 나중에

- **PocketBase · Appwrite를 그대로 붙이기**: 회원 체계 · 백업 · 승인 흐름이 둘이 된다. Supabase 자체 설치는 프로젝트가 하나뿐이다.
- **앱마다 SQLite 파일**: 원본이 둘이 되고(원칙 1), 서버와 일꾼이 같은 파일에 쓴다. 떼어 가기는 내보내기(SQL)로 푼다.
- **앱마다 DB · 컨테이너**: 백업 · 마이그레이션 · 연결이 앱 수만큼 는다. 스키마가 독립이라 나중에 그 스키마만 옮길 수 있다.
- **앱이 SQL · 서버 코드를 직접**: AI가 만든 코드가 DB에서 임의의 SQL을 돌리지 않는다. 표는 선언으로만.
- **회원 쪽 API를 다른 DB 계정(로그인)으로**: 지금은 한 풀에서 `SET LOCAL ROLE`이다 (API의 조건 실수는 막지만, 임의 SQL이 들어오면 역할을 되돌릴 수 있다). 회원 쪽을 다른 컨테이너로 뗄 때(11.2) 그 계정으로 로그인하게 바꾼다.
- 나중: 실시간 갱신, 파일 저장, 식으로 쓰는 규칙, 표 사이 잇기, 앱 가져오기(내보낸 묶음을 다른 Cairn에), 도메인에서의 미리 보기.

### 12.8 만든 것과 확인 (2026-11-22)

P1~P5를 한 번에 만들고 확인했다.

| 확인 | 결과 |
|---|---|
| 서버 API 테스트 | 앱 데이터 10개 (규칙 · DB의 행 수준 보안 · 버전이 바뀔 때 · 내보내기 · 커뮤니티 정적 앱), 배포 도구 3개, 설정 제안 `app_data`, 배포 기기 |
| 러너 | 선언서 검사(`AppManifestCheck`: 회원 · 권한 · 테마 · 표) |
| CLI | `cairn app deploy` 4개 (폴더 zip · 첫 승인 · 다시 올리기 · 거절) |
| 브라우저 (앱 도메인) | 격리 없이 열림(`sandbox` 없음, `microphone=(self)`) · `localStorage` · 테마 입힌 가입 화면 · 가입 → 기록 넣기 → 순위 · 다른 회원은 남의 기록을 읽지 못하고 남의 점수를 고치지 못함(404) · 방문자의 쓰기 401 |
| 브라우저 (미리 보기 · 기본 도메인) | 미리 보기는 격리(`cairn.open` 거짓, 안내가 보임), 기본 도메인의 `/<앱>`은 그 도메인으로 308 |
| 콘솔 | 앱 관리의 회원 탭 · 데이터 탭(표 · 줄 수 · 규칙 · 내보내기) |
| 실제 서버에 배포 명령 | 승인 화면에 쓰기 권한만 보임 → 표 받아 올림 → 공개 앱은 확인 대기 버전. 둘째부터는 승인 없이 |

설계와 다르게 만든 것:

- 회원을 새 모듈로 떼지 않고 community 모듈을 넓혔다 (12.3).
- 앱마다 DB 계정을 두지 않고 역할 하나(`cairn_app`)를 `SET LOCAL ROLE`로 쓴다 (12.7).
- 배포 도구는 zip을 MCP에 싣지 않고 표를 받아 따로 올린다 (JSON 본문 512KB 한도, 12.5).
- 앱 가져오기는 만들지 않았다 (12.7 나중). 내보내기는 된다.
- 미리 보기 · 기본 도메인의 `/<앱>`은 격리 그대로라 회원 · 데이터는 그 앱의 도메인에서만 돈다.
- 복원한 백업의 앱은 버전을 다시 보일 때 표가 맞춰진다 (앱 데이터는 Cairn 백업 zip에 들지 않는다: 내보내기로 따로 받는다).

실제 환경에서 남은 확인: 실제 도메인 · Caddy(HTTPS)에서 마이크 권한과 서비스 워커, 실제 AI(Claude · Codex)가 `members` · `tables`를 선언한 앱을 만드는지.

## 13. 대화로 배포 · 수정 (2026-11-24)

사용자 결정: "배포해달라고 하면 어차피 우리 소스 내에서 열어주는 거니 배포도 하고, 수정해달라고 하면 수정도". 기획서 결정 기록 · 원칙 7.

**전과 후** (페이지 앱 하나, 메시지 보내기는 세지 않음):

| | 전 | 후 |
|---|---|---|
| "앱 만들어서 배포해줘" | 앱 만들기 승인 1 + 앱 관리로 가서 공개 · 확인 2 + 이동 | 앱 만들기 승인 1 |
| 공개 앱에 "이 부분 고쳐줘" | 결과 카드 승인 1 | 0 |

**흐름**: 관리자가 콘솔의 대화에 배포 · 수정을 쓴다 → 대표가 `publish_app { app_id, quote }`로 그 말을 글자 그대로 인용한다(일꾼에게 맡기기 전이든 뒤든) → 서버(task `ChatPublishService`)가 확인한다 (`OwnerAsk`):
- 인용이 24시간 안에 관리자가 콘솔로 보낸 이 대화의 말(회차 · 덧붙인 말의 지시, 요청 id가 콘솔의 UUID)에 글자 그대로 있는가. 기기(`via: device`) · 기능 패키지(텔레그램, 요청 id가 `telegram:`이고 패키지는 UUID 모양을 쓰지 못한다) · 자동화(`schedule:`) · 서버가 연 회차(`fix`)는 세지 않는다: 승인은 콘솔에서만
- 인용 바로 뒤가 "하지 마" · "아직" 같은 뒤집는 말이 아닌가 ("배포는 하지 마"의 "배포"만 떼어 쓰지 못하게)
- 배포 · 공개 말(배포 · 공개 · 올려 · 오픈 · deploy …)이면 `ship`, 고치기 말(고쳐 · 바꿔 · 수정 · 반영 …)이면 `edit`, 둘 다 아니면 거절

통과하면 바로 승인한 결재 `blog.app.publish`(대상 앱, `payload { quote, scope }`, `agent_decided`, 메모 "대화에서 관리자가 요청: «…»")를 남긴다 (`AppApproval.ownerAsked`):
- `ship`이면 blog의 `AppPublishHandler`가 비공개 앱을 공개로 바꾼다 (`App.publishAsked` → 관리자의 공개와 같은 `edit` 규칙). 커뮤니티는 도메인 확인 전이면 도구가 먼저 까닭과 함께 거절한다 (platform `ActionChecks`, `AppQuery.publishProblem`)
- 이 대화에서 기다리던 그 앱의 코드 공개(카드에 실리지 않은 것)를 함께 승인한다 (`Approval.grantAsked`)
- 24시간 동안 이 대화의 make 일이 낸 그 앱의 새 버전은 카드 없이 바로 승인된다 (`ChatResultService.offerAppCode` → `ApprovalRepository.askedFor`)

**되돌리기**: 앱 관리의 "비공개로 바꾸기", 코드 탭의 앞 버전 공개. 기록은 승인 목록에 "대화로 배포"로 남는다.

**고르지 않은 것**: 대표의 주장만 믿기(프롬프트 주입 · 착각으로 공개될 수 있다), 대화 아무 곳의 "배포"를 다 믿기(오래된 말 · 다른 앱의 말: 24시간 · 앱마다 · 그 대화만), 앱 만들기 승인도 없애기(설정 바꾸기는 원칙 7대로 승인. 다음에 비공개 앱 만들기만 따로 볼 수 있다), 텔레그램의 말도 승인으로 보기(승인은 콘솔에서만).
