# 스토어와 앱

> 상태: **설계안 승인** (2026-11-18, [기획서](기획서.md) 결정 기록). **1단계 인터페이스(8장) 승인** (2026-11-18), 1-1 ~ 1-5 구현. **1-6은 "앱 코드"로 바꿔(2026-11-18) 인터페이스(9장) 승인, 1-6a 서버 · 1-6b 웹 · 1-6c 러너 · 보관 구현.** 테이블 · API · 보관 형식은 단계마다 함께 고치고, 객체 설계는 1-6에서.

"블로그 하나"를 "스토어 안의 여러 앱"으로 올린다. Cairn은 앱들을 만들고 운영하고, AI 팀이 앱마다 글을 쓰고 커뮤니티를 관리하고 새 앱을 개발한다. 사람은 목적을 말하고 승인만 한다.

## 1. 개념

| 말 | 뜻 | 예 |
|---|---|---|
| 스토어 | 만들 수 있는 앱 종류의 목록이자 만든 앱을 관리하는 콘솔 화면 | 콘솔 독의 "스토어" |
| 앱 종류 | 코드로 만든 앱의 틀. 저장소(코어 또는 기능 패키지)에 있다 | 블로그 · 매거진 · 페이지 앱 · 커뮤니티 |
| 앱 | 앱 종류로 만든 서비스 하나. DB의 데이터다 | 개발 블로그 · 여행 블로그 · 카페 매거진 · 커뮤니티 |

- 개발 블로그와 여행 블로그는 같은 "블로그" 종류의 앱 두 개다. 코드는 같고 이름 · 주소 · 메뉴 · 운영 팀이 다르다.
- 카페 매거진은 "매거진" 종류다. 지금 있는 호 발행을 그대로 쓴다.
- 페이지 앱은 AI가 만든 HTML · JS 묶음이다. 지금의 "AI가 만든 페이지"를 앱 종류로 올린 것이다.
- 커뮤니티는 방문자가 회원으로 가입해 글을 쓰는 첫 기능이라 따로 단계를 둔다.

## 2. 구조

```
Cairn (내 서버 하나)
├─ store 모듈 (새로)        앱 종류 목록 · 앱(이름 · 주소 · 공개 여부 · 운영 팀 · 편집 방침)
├─ blog 모듈 (그대로)       글 · 메뉴 · 호 · 페이지 · 사진: 블로그 · 매거진 · 페이지 앱이 쓰는 글 엔진
├─ community 모듈 (3단계)   회원 · 글 · 댓글 · 신고
└─ vault · task · account · platform (그대로)

조직도: 대표 → 앱마다 운영 팀장 (개발 블로그 팀 · 여행 블로그 팀 · 매거진 팀 · 커뮤니티 운영 팀)
```

- `store`는 앱의 머리(무엇 · 어디 · 누가 · 아이콘 · 순서)만 갖는다. 글 · 메뉴 · 호 · 페이지는 blog가 갖고 `app_id`를 값으로 들고 있다 (모듈 사이 외래키 없음, 객체설계 9장).
- blog는 store를 가져오지 않는다. 앱이 있는지 · 공개인지는 platform 등록부(`Lookups`)로 묻는다 (R3b와 같은 방식).

## 3. 정한 것

| 정한 것 | 까닭 | 고르지 않은 것 |
|---|---|---|
| 앱 종류는 저장소 코드, 앱은 데이터. 스토어의 "만들기" = 앱 하나 만들기 | 남이 만든 앱 코드를 내려받아 서버에서 돌리지 않는다 | 외부 마켓에서 앱 코드 설치 |
| 블로그 · 매거진 · 페이지 앱은 지금 blog 모듈을 글 엔진으로 쓴다 | 글 · 버전 · 발행 승인 · 호 · RSS · 페이지가 테스트까지 있다 | 종류마다 엔진 새로 만들기 |
| 스키마 · 모듈 이름 `blog`는 그대로, 화면 · 문서의 "블로그"를 "스토어 · 앱"으로 | 이름만 바꾸면 마이그레이션 · 보관 형식 · 테스트 비용만 크다 | 모듈 · 스키마 이름 바꾸기 |
| 주소는 도메인 하나에 경로로 (`/dev`, `/travel`). 앱 주소로 못 쓰는 이름(`admin` · `api` · `login` · `install` · `connect` · `pages` · `posts` · `m` · `graph` …)은 막는다 | 인증서 · 프록시 설정이 그대로다 | 앱마다 도메인 (4단계 선택) |
| 지금 글 · 메뉴 · 호 · 페이지는 기본 앱 하나로 옮기고, 옛 주소(`/posts/…`, `/m/…`)는 새 주소로 넘긴다 | 들어온 정보는 버리지 않는다. 바깥 링크가 깨지지 않는다 | 처음부터 다시 |
| 앱 만들기 · 고치기는 대화에서도 제안(`propose_setting`의 `app`) → 승인 | AI는 설정을 제안만 한다 (2026-11-15 C) | AI가 앱을 바로 만들기 |
| 서버 기능이 필요한 새 앱 종류는 기능 패키지로 개발한다 | 자기 스키마 · 적은 확장 지점만 쓰고, 켤 때 권한을 허락받는다. AI가 쓴 코드의 피해 범위가 좁다 | 코어에 바로 넣기 |
| 커뮤니티는 따로 설계안 · 보안 검토 뒤에 | 회원 계정 · 스팸 · 개인정보(개인정보보호법) · 신고가 함께 생긴다 | 1단계에 함께 |

## 4. "앱 하나 만들어줘"의 흐름

대표가 요청을 보고 셋 중 하나로 보낸다.

| 길 | 언제 | 하는 일 | 승인 |
|---|---|---|---|
| ① 앱 만들기 | 있는 종류로 된다 ("요리 블로그") | 대표가 `propose_setting { setting: app, op: create }` → 결과 카드 → 승인하면 서버가 앱(비공개) · 운영 팀을 만든다 → 팀이 첫 글 초안 | 앱 만들기 1 + 글 공개 |
| ② 페이지 앱 | 화면만 있으면 된다 ("카페 지도", "경비 계산기") | 만들기 작업(코드 러너)이 HTML · JS · `data.json`을 만든다 → 미리 보기 → 승인하면 페이지 앱으로 등록 | 1~2 |
| ③ 새 앱 종류 | 저장 · 회원 · 결제 같은 서버 기능이 필요하다 ("예약") | 코드 작업 열기 → 코드 러너가 기능 패키지로 개발 · 테스트 → PR → 머지 → 배포(사람) → 켤 때 권한 허락 → ①로 앱 만들기 | 3 + 배포 |

## 5. 화면

화면을 먼저 정하고, 화면이 필요로 하는 데이터에서 API · 표를 정한다. 구현 순서는 지금 규칙대로 표 → 서버 → 웹이다 (웹의 타입은 서버 View에서 온다, `.claude/rules/web.md`).

### 콘솔

독(DOCK)에 "스토어"를 더한다 (대화 · 팀 · **스토어** · 오피스 · 승인 · 보관함). 설정의 "블로그 › 블로그 메뉴"는 앱 관리 안으로 옮긴다.

| 화면 | 주소 | 내용 |
|---|---|---|
| 내 앱 | `/admin/store` | 만든 앱 카드: 종류 · 이름 · 주소 · 공개 여부 · 글 수 · 승인 대기 · 운영 팀. "열기"(공개 주소) · "관리". 위에 "앱 만들기" |
| 스토어 | `/admin/store/new` | 앱 종류 카드: 블로그 · 매거진 · 페이지 앱 · 커뮤니티(준비 중) · 기능 패키지가 더한 종류. "만들기" → 만들기 시트. "대화에서 만들기" 안내 |
| 만들기 시트 | (시트) | 아이콘(그림 올리기, 없으면 종류 아이콘) · 이름 · 주소(`/` 뒤, 못 쓰는 이름은 바로 알림) · 설명 · 운영 팀(템플릿으로 만들기 · 있는 팀 · 나중에) · 시작 메뉴(종류마다 기본 세트). 비공개로 만들어진다 |
| 앱 관리 | `/admin/store/<앱 id>?tab=` | 머리: 아이콘 · 이름 · 종류 · 주소 · 공개 전환. 탭: 개요(든 것의 수 · 최근 글. 승인 대기 · 운영 팀의 진행은 2단계) · 메뉴(옛 설정 › 블로그 메뉴, 호 관리는 `/admin/store/<앱 id>/m/<메뉴 id>`) · 글(이 앱의 글, 새 글은 이 앱에 넣어 편집기로) · 설정(이름 · 주소 · 설명 · 순서 · 아이콘 · 삭제). 운영 팀 탭은 2단계 |
| 대화의 제안 카드 | (대화) | 지금 설정 바꾸기 카드 그대로: "새 앱: 요리 블로그 (/cooking, 블로그)" · "새 에이전트 3" 줄, 승인 · 수정 요청 · 반려 |

보관함의 "글" · "페이지"는 그대로 두고 앱으로 거르는 칩을 더한다.

### 공개 화면 (방문자)

| 주소 | 내용 |
|---|---|
| `/` | 설정 › 사이트의 "첫 화면"을 따른다. 기본은 "자동": 공개 앱 0개면 사이트 이름 · 소개 · "공개한 앱 없음", 1개면 그 앱의 첫 화면, 2개 이상이면 앱 아이콘 목록(휴대폰 홈 화면처럼 아이콘 · 이름 · 종류, 누르면 그 앱으로). 앱 하나로 고정할 수도 있다 |
| `/<앱>` | 그 앱의 첫 화면: 앱 설명 · 글 목록 (매거진은 최신 호, 페이지 앱은 그 페이지) |
| `/<앱>/posts/<글>` · `/<앱>/m/<메뉴>` · `/<앱>/rss.xml` | 지금 화면에 앱 주소가 앞에 붙는다 |
| `/posts/<글>` · `/m/<메뉴>` · `/rss.xml` | 기본 앱의 새 주소로 넘긴다 (308) |
| 비공개 앱의 모든 주소 | 없는 주소와 같은 404 ("없는 페이지"). 응답 · 문구가 같아 앱이 있다는 사실도 드러나지 않는다 (원칙 5) |

- 앱 아이콘은 앱마다 올린 그림, 없으면 종류의 선 아이콘. 순서는 내 앱 화면에서 끌어 정한다.
- 머리는 한 줄. 앱 목록(`/`)에서는 로그인만, 앱 안에서는 왼쪽 끝 "모든 앱" 버튼(앱 목록으로) · 앱 아이콘 · 앱 이름 · 그 앱의 메뉴 · 그래프 · 로그인. 공개 앱이 하나뿐이면 "모든 앱" 버튼이 없다.
- 아래쪽에 다른 공개 앱 링크와 그 앱의 RSS.
- 그래프는 사이트 하나 (공개 앱의 공개 글만). 공개 글이 없으면 링크를 숨긴다.
- 관리자가 로그인해 있어도 공개 화면은 방문자와 같다 (지금 규칙). 다른 점은 오른쪽 끝 "로그인" 대신 "콘솔". 비공개 앱은 앱 관리의 미리 보기로 본다.
- 오른쪽 끝 "로그인"은 관리자 로그인이다. 커뮤니티(3단계)에서 회원 로그인이 생기면 이 자리를 다시 정한다.

## 7. 바뀌는 원칙 · 문서

- 기획서 1장: "결과를 블로그로 내보낸다" → "결과를 스토어의 앱으로 내보낸다".
- 결정 기록: "블로그 → 스토어와 앱"(이 문서).
- 커뮤니티 단계에서 원칙 하나를 더할 예정: 회원은 콘솔 · 보관함 · 작업에 닿지 않는다. 회원 글의 삭제 · 제재는 관리자 승인으로만.
- 그대로: vault와 blog는 서로 의존하지 않는다, 비공개가 기본, 위험한 동작은 승인 뒤.
- 관련 문서: 테이블설계(store · blog의 `app_id`), API설계(`api/apps` · `api/app-types`), 객체설계 모듈 지도, 보관형식(앱 폴더), README(스토어).

## 8. 1단계 인터페이스 (승인 2026-11-18, 끝남)

### 8.0 설계안과 달라지는 점

| 설계안 | 바꾸자는 것 | 까닭 |
|---|---|---|
| 새 `store` 모듈이 `apps`를 갖고 blog는 `app_id`를 값으로, 공개 여부는 `Lookups`로 묻는다 | **`apps` 표를 blog 모듈(스키마 `blog`)에 둔다.** 코드 자리는 `blog/app/`, 화면 이름만 "스토어" | 글이 방문자에게 보이는가 = "글이 공개 **그리고** 앱이 공개"다. 같은 스키마면 SQL 조건 하나로 거른 뒤 개수 · 순서를 센다 (원칙 5). 다른 모듈이면 방문자 요청마다 `Lookups`로 묻고 결과로 다시 걸러야 해서 목록 · 개수 · 사진 · 호 · RSS 곳곳에 새는 틈이 생긴다. 3단계 커뮤니티 모듈은 blog가 `Lookups`로 내주는 `app`을 묻는다 |
| `/rss.xml`은 기본 앱으로 넘긴다 | `/rss.xml`은 **사이트 전체**(공개 앱의 공개 글)로 둔다. 앱마다는 `/<앱>/rss.xml` | "기본 앱"을 따로 정하지 않아도 되고, 구독자의 주소가 그대로 산다 |
| 1단계에 운영 팀 고르기 · 첫 화면 고정 | 2단계로 (6장의 2단계와 맞춤). 1단계 만들기 시트에서 "운영 팀" 칸을 뺀다 | 1단계는 앱의 뼈대와 공개 범위만. 메뉴의 운영 팀은 지금처럼 메뉴마다 |

### 8.1 표 (마이그레이션 하나 `blog_apps`)

```sql
CREATE TABLE blog.apps (
  id uuid PRIMARY KEY,                       -- UUIDv7
  space_id uuid NOT NULL,
  kind text NOT NULL CHECK (kind IN ('blog', 'magazine', 'page')),   -- 만들 때만
  name text NOT NULL,                        -- 1~40자
  slug text NOT NULL,                        -- 영어 소문자 · 숫자 · 하이픈 2~30자, 못 쓰는 이름 제외 (App.RESERVED)
  description text NOT NULL DEFAULT '',      -- 200자, 앱 목록 · 앱 첫 화면
  visibility text NOT NULL DEFAULT 'private' CHECK (visibility IN ('private', 'public')),
  sort integer NOT NULL DEFAULT 0,
  icon_blob_hash text,                       -- BlobStore.registerUse에 등록
  version integer NOT NULL DEFAULT 1,
  created_at timestamptz NOT NULL, updated_at timestamptz NOT NULL,
  UNIQUE (space_id, slug)
);
ALTER TABLE blog.menus ADD COLUMN app_id uuid REFERENCES blog.apps(id);   -- 옮긴 뒤 NOT NULL
ALTER TABLE blog.posts ADD COLUMN app_id uuid REFERENCES blog.apps(id);   -- NULL = 아직 앱에 없는 글
ALTER TABLE blog.pages ADD COLUMN app_id uuid REFERENCES blog.apps(id);   -- NULL = 앱 밖의 페이지 (지금처럼 /pages/<이름>/)
-- 메뉴 주소는 공간에서 하나 → 앱 안에서 하나: UNIQUE (space_id, slug) → UNIQUE (app_id, slug)
```

- **옮기기** (같은 마이그레이션): 글 · 메뉴 · 페이지가 있는 공간마다 기본 앱 하나 (블로그, 주소 `blog`, 이름 "블로그", **공개** — 지금 블로그가 공개라서). 모든 메뉴 · 글과 메뉴에 올린 페이지를 그 앱으로. 새로 설치한 곳은 앱이 없다.
- 글의 주소 · 페이지 이름은 지금처럼 공간에서 하나다 (`/posts/<글>`이 어느 앱인지 찾아 넘길 수 있게).
- 앞뒤가 맞아야 하는 것 (엔티티가 지킨다): 글을 메뉴 · 호에 올리면 글의 앱 = 그 메뉴의 앱. 앱에 없는 글은 공개 · 링크만으로 바꿀 수 없다.

### 8.2 방문자에게 보이는 것 (한 곳의 규칙)

| 대상 | 보이는 조건 |
|---|---|
| 앱 | `visibility = 'public'` |
| 글 | 지금 조건 **그리고** 앱이 공개 (앱 없는 글은 안 보임) |
| 메뉴 · 호 | 그 앱이 공개 (호는 지금처럼 발행한 것만) |
| 페이지 | 지금 조건 **그리고** (앱 밖이거나 앱이 공개) |
| 사진 | 방문자에게 보이는 글에 붙어 있음 |
| 앱 아이콘 | 앱이 공개 |
| 그래프의 글 | vault의 글 자리 사본에 앱 공개 여부를 더해 거른다 (8.5) |

조건은 같은 SQL 한 줄(`a.visibility = 'public'`)을 각 방문자 읽기(글 · 메뉴 · 호 · 페이지 · 사진 · 아이콘)에 걸고, 보이지 않는 것은 없는 것과 같은 404다. DB도 앱 없는 글의 공개와 메뉴 · 앱이 어긋나는 것을 막는다 (CHECK · 외래키). 테스트가 비공개 앱의 것을 하나씩 확인한다 (`app.api.test`).

### 8.3 REST

새 `api/apps` (묶음 `blog/app/`: `App` · `AppService` · `AppQuery` · `AppRepository` · `AppEdit` · Input · View):

| 요청 | 누가 | 하는 일 | 오류 |
|---|---|---|---|
| `GET api/apps` | 누구나 | 방문자: 공개 앱 `[{ slug, name, kind, description, iconUrl }]` 순서대로 (id는 내보내지 않는다). 관리자: 모든 앱 + `id · visibility · sort · version · counts { published, drafts, menus, pages }` | |
| `GET api/apps/by-slug/:slug` | 누구나 | 앱 머리 하나 (방문자는 공개 앱만) | 404 |
| `POST api/apps` | 관리자 | `{ requestId, kind, name, slug?, description?, menus?: string[], pageId? }` → 앱(비공개) + 시작 메뉴(블로그: 글, 매거진: 호, `menus`를 주면 그 이름들의 글 목록 메뉴, 5개까지). 페이지 앱은 `pageId`가 꼭 있고 그 페이지를 앱에 넣는다 | 422 주소 형식 · 못 쓰는 이름 · 페이지 앱인데 페이지 없음, 409 주소 겹침, 404 페이지 |
| `PATCH api/apps/:id` | 관리자 | `{ version, name?, slug?, description?, visibility?, sort? }` (종류는 못 바꿈) | 409 버전 · 주소 겹침, 422 |
| `POST api/apps/:id/delete` | 관리자 | `{ version }`. 글 · 페이지가 없을 때만, 빈 메뉴는 함께 지운다 | 409 "글 N개 · 페이지 N개가 있어요" |
| `PUT api/apps/:id/icon?version=` · `POST api/apps/:id/icon/delete` | 관리자 | 사이트 로고와 같은 모양 · 한도 (PNG · JPEG · WebP, SVG는 받지 않음) | 413 · 415 · 409 |
| `GET api/apps/by-slug/:slug/icon` | 누구나 | 공개 앱의 아이콘 (관리자는 비공개도) | 404 |

바뀌는 것:

| 요청 | 바뀌는 점 |
|---|---|
| `GET api/posts` | `?app=<앱 주소>` 거르기. `?menu=`는 `app`과 함께 (메뉴 주소가 앱 안에서 하나가 되어서) |
| `GET api/posts/by-slug/:slug` | 답에 `app: { slug, name } \| null`. 웹이 다른 앱 주소로 온 요청을 맞는 주소로 넘긴다 |
| `POST api/posts` | 새 글을 앱에 넣을 때 `appId?` (고쳐 쓰기 `PUT`이 아니라 올리기 API로 앱을 바꾼다: 앱 · 메뉴를 한 곳에서) |
| `POST api/posts/:id/menu` | `{ version, menuId \| null, appId? }`: 메뉴를 주면 앱은 그 메뉴의 앱, 메뉴 없이 앱만 주면 메뉴에서 빼고 그 앱으로 |
| `POST api/posts/:id/status` · 승인한 발행 | 앱에 없는 글이면 422 "앱에 넣은 뒤 공개해요" (승인한 발행은 `publish_failed`). 결과 카드 전의 확인(`PostQuery.publishProblem`)도 같은 말을 먼저 짚는다 |
| `GET api/menus` · `POST api/menus` | 목록은 `?app=` (방문자는 꼭), 만들기는 `appId`가 꼭. View에 `appId` |
| `GET api/issues/by-number/:menu/:number` | `by-number/:app/:menu/:number` |
| `PATCH api/pages/:id` | `appId?`(페이지를 앱에 넣기 · 빼기). 페이지 앱의 페이지는 앱을 지우기 전에는 뺄 수 없다 |
| `GET api/pages/site/*path` | 앱이 비공개면 방문자에게 404 |

### 8.4 대화 (설정 바꾸기)

`BlogSettings`에 하나 더 등록한다 (메뉴와 같은 모양):

```ts
AppEdit.SETTING = {
  setting: 'app', list: 'apps', ops: ['create', 'edit'],
  fields: ['name', 'slug', 'kind', 'description', 'sort', 'menus'],   // kind · menus는 만들 때만
  target: 'id', versioned: true, grants: [],
}
```

- `get_settings apps`: 앱 목록 (공개 여부는 읽기만).
- **AI는 공개 여부를 제안하지 못한다**: 페이지와 같은 규칙 (AI · 기기가 공개하는 길은 없다). 공개는 앱 관리의 전환 하나.
- 결과는 지금처럼 `blog.setting.changed`. 만들기의 `requestId`는 결재 키.

### 8.5 이벤트와 vault

- 새 이벤트 `blog.app.changed { appId, visibility, appVersion, deleted? }`: 공개 여부가 바뀌거나 앱을 지울 때.
- `blog.post.*`에 `appId`(없으면 null)를 더한다.
- vault: 글 자리 사본(`vault.post_marks`)에 `app_id`, 새 표 `vault.app_marks(app_id, space_id, public, app_version)`. `appVersion`이 더 큰 이벤트만 받는다 (글 자리 사본과 같은 규칙). 그래프의 방문자 읽기가 둘을 이어 SQL에서 거른다. 앱을 비공개로 바꾸면 행 하나만 바뀐다.

### 8.6 보관 형식 (번호 그대로, "있으면"만 더함)

- 새 파일 `blog/apps/<주소>.yml` (앱 하나에 파일 하나): `cairn_id · kind · name · slug · description · visibility · sort · icon?`. 아이콘은 사진처럼 `assets/<해시>.<확장자>`.
  앱마다 파일을 나눈 까닭: 공개 여부가 파일 단위라, 목록 파일 하나면 비공개 앱의 이름이 공개 저장소로 나간다.
- 글 앞부분에 있으면 `cairn_app`(앱 id).
- 공개 저장소에는 공개 앱의 파일과, 공개 앱에 든 공개 글 · 그 사진 · 공개 앱의 아이콘만 보낸다.
- 복원: 앱 파일이 있으면 앱부터 만든다 (id · 종류 · 공개 여부 · 아이콘 그대로, 버전은 1부터). 글이 없는 앱을 가리키거나, 공개 · 링크 공개 글이 앱 밖에 있으면 어느 글인지 알리고 멈춘다.
- 옛 백업: 앱 파일이 하나도 없는데 공개 · 링크 공개 글이 있으면 앱이 생기기 전의 백업으로 보고, 마이그레이션과 같은 기본 앱(블로그, `/blog`, 공개) 하나에 모든 글을 넣는다. **기본 앱의 id는 공간 id**라는 형식 규칙을 두어, blog와 vault가 서로를 모른 채 같은 앱을 가리킨다 (vault는 그 id로 그래프 사본을 만든다). 임시 글만 있으면 앱 없이 들어온다 (앱이 없는 Cairn을 왕복해도 앱이 생기지 않게).
- 메뉴 · 호 · 페이지는 지금처럼 싣지 않는다. 페이지 앱은 페이지 없이 들어오고 복원 결과에 알린다.

| 자리 | 하는 일 |
|---|---|
| `/` | `GET api/apps` → 0개 "공개한 앱 없음", 1개 그 앱의 첫 화면, 2개 이상 앱 아이콘 목록 (시안 6 · 7 · 8번) |
| `app/(blog)/[app]/…` | 앱 첫 화면(블로그: 글 목록, 매거진: 최신 호, 페이지 앱: 그 페이지를 틀로) · `posts/[slug]` · `m/[menu]` · `m/[menu]/[number]` · `rss.xml` |
| 옛 주소 | `/posts/<글>` → 그 글의 앱 주소로 **307** (계속 두는 고정 주소: 그래프 · 편집기 · 보관함 링크는 그대로). `/m/<메뉴>` · `/m/<메뉴>/<번호>` · `/m/<메뉴>/rss.xml` → 그 주소의 메뉴가 있는 첫 공개 앱으로 307. 308이 아닌 까닭: 글은 다른 앱으로 옮길 수 있고 앱은 비공개가 될 수 있어 넘길 곳이 바뀐다 (308은 브라우저가 기억해 옛 자리로 계속 보낸다). 방문자에게 안 보이는 글(초안 · 비공개 앱 · 앱 밖)은 관리자에게만 고정 주소에서 미리 보기로 그린다 |

| 콘솔 | 독에 스토어(`/admin/store`: 탭 내 앱 · 스토어) · 스토어(`/admin/store/new`: 종류 카드 · 만들기 시트, 아이콘은 만든 뒤 올림) · 앱 관리(`/admin/store/[id]`: 개요 · 메뉴 · 글 · 설정). 설정의 "블로그 메뉴"는 앱 관리 › 메뉴로 옮기고 지운다. 글 편집기의 발행 창에 앱 고르기(저장한 글은 바로 옮기고, 새 글은 첫 저장에 함께, 앱 관리 › 글의 "새 글"은 `?app=`). 보관함의 메뉴 고르기는 "앱 › 메뉴". 비공개 앱의 미리 보기는 1-6(앱 코드)에서 |

## 9. 1-6 앱 코드 인터페이스 (승인 2026-11-18)

시안: https://claude.ai/artifact/SAj3KxEguDUErcJXVdTh9P 의 넷째 줄 (코드 탭 · 미리 보기 · 대화 카드 · 시작 코드로 만든 앱 · 직접 쓴 코드의 앱). 2026-11-18 결정(기획서)으로 1-6 "앱 테마"를 "앱 코드"로 바꾼다.

### 9.0 한 장 요약

- **앱 = 자기 코드 묶음(HTML · CSS · JS · 그림) + Cairn의 데이터(글 · 메뉴 · 호).** 앱끼리 코드를 나누지 않는다. 공통 템플릿 · 테마 값이 없다.
- 코드는 **버전으로 쌓는다** (추가만). 공개 앱의 새 버전은 확인 대기로 두고, 관리자가 미리 보고 "이 버전 공개"를 누를 때 바뀐다 (페이지와 같은 규칙, 원칙 7).
- 앱 코드는 **우리 서버에서 실행되지 않는다.** 로직 없는 템플릿(Mustache)에 데이터를 채운 HTML을 브라우저로 보낼 뿐이다.
- 앱 화면은 **격리해서 연다** (CSP `sandbox`). 앱의 JS는 다른 출처로 취급되어 로그인 · 콘솔 API에 닿지 못한다. 바깥 주소는 그 버전의 `cairn.json`에 적은 호스트만.
- 코드가 없는 앱은 **종류의 시작 코드**로 보인다. 처음 고칠 때(AI 작업 · zip 올리기) 시작 코드 위에 버전 1이 생긴다.
- 1-4의 공개 화면 컴포넌트는 시작 코드(템플릿)로 옮기고 지운다. 앱 화면을 그리는 길은 하나다.

### 9.1 표 (마이그레이션 하나 `blog_app_code`)

```sql
CREATE TABLE blog.app_code_versions (
  id         uuid PRIMARY KEY DEFAULT platform.uuid_v7(),
  app_id     uuid NOT NULL,              -- blog.apps의 id (값). 앱을 지워도 버전은 남는다 (원칙 2)
  space_id   uuid NOT NULL,
  seq        int  NOT NULL CHECK (seq >= 1),
  files      jsonb NOT NULL CHECK (jsonb_typeof(files) = 'array'),   -- [{ name, blobHash, mime, sizeBytes }] 페이지 버전과 같은 모양
  source     text NOT NULL CHECK (source IN ('starter', 'upload', 'task', 'restore')),
  task_id    uuid,                       -- source = 'task'일 때만 (task의 것, 값)
  run_id     uuid,
  note       text NOT NULL DEFAULT '' CHECK (char_length(note) <= 2000),   -- 요청 글 · 올린 파일 이름
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT app_code_versions_seq UNIQUE (app_id, seq),
  CONSTRAINT app_code_versions_run UNIQUE (app_id, run_id),             -- 같은 이벤트를 두 번 받아도 버전은 하나
  CONSTRAINT app_code_versions_task CHECK ((source = 'task') = (task_id IS NOT NULL AND run_id IS NOT NULL))
);
-- 추가만: BEFORE UPDATE OR DELETE 트리거 platform.forbid_update_delete()

ALTER TABLE blog.apps
  ADD COLUMN code_seq         int,                          -- 방문자에게 보이는 버전. NULL = 시작 코드
  ADD COLUMN code_pending_seq int,                          -- 확인 대기 버전 (공개 앱만)
  ADD COLUMN code_versions    int NOT NULL DEFAULT 0,       -- 쌓인 버전 수
  ADD CONSTRAINT apps_code_seq CHECK (code_seq IS NULL OR code_seq BETWEEN 1 AND code_versions),
  ADD CONSTRAINT apps_code_pending CHECK (code_pending_seq IS NULL OR code_pending_seq BETWEEN 1 AND code_versions);
```

- 파일 내용은 지금처럼 BlobStore에 두고 버전마다 `registerUse`로 등록한다.
- 지금 있는 앱은 옮길 것이 없다 (`code_seq` NULL = 시작 코드).
- 버전을 바꾸면 `apps.version`이 오른다 (낙관적 잠금은 앱 하나로).

### 9.2 코드 묶음 규칙

| 규칙 | 값 |
|---|---|
| 파일 | 100개까지, 폴더 없는 이름, 형식 표는 페이지와 같다 (`PageFiles`를 그대로 쓴다). `index.html`이 꼭 있다 |
| 크기 | 버전 하나 20MB, 템플릿(`.html`)은 합쳐 1MB |
| 화면 → 템플릿 | 첫 화면 `index.html` · 글 `post.html` · 메뉴 목록 `list.html` · 호 `issue.html` · 앱 안의 없는 주소 `404.html`. 없으면 `index.html` (404는 Cairn의 404) |
| 부분 템플릿 | `{{> header}}` → 같은 묶음의 `header.html` |
| 정적 파일 | `{{files}}/style.css` → `/<앱>/files/style.css` |
| `cairn.json` (있으면) | `{ "cairn": 1, "hosts": ["fonts.googleapis.com", "fonts.gstatic.com"] }`. 호스트 10개까지, 정확한 이름만 (와일드카드 · IP · 포트 없음, https로만 연다) |

AI 작업의 결과는 바꾼 파일만 앞 버전 위에 얹는다 (`PageFiles.overlay`). 파일을 지우는 것은 zip 올리기(묶음 전체)로 한다.

### 9.3 데이터 약속 (`cairn: 1`)

템플릿에는 아래 데이터가 들어가고, 같은 값이 `<script type="application/json" id="cairn-data">`로 `</head>` 앞에 실린다 (앱 JS가 읽을 수 있게). 약속의 원본은 스킬 `cairn-make/references/app-code.md` 하나이고, AI와 사람이 같은 글을 본다.

| 이름 | 화면 | 값 |
|---|---|---|
| `cairn` · `screen` | 모두 | `1` · `'home' \| 'post' \| 'menu' \| 'issue'`, 섹션용 `isHome` · `isPost` · `isMenu` · `isIssue` |
| `base` · `files` | 모두 | 앱 주소 `/travel` (미리 보기는 `/travel/~<토큰>`) · 파일 주소 `/travel/files` |
| `title` | 모두 | 화면 제목 (앱 이름, 글이면 `글 제목 · 앱 이름`) |
| `site` | 모두 | `{ home: '/', loginUrl: '/login', graphUrl }` (공개 글이 없으면 `graphUrl` null). 웹이 `name`(사이트 이름)을 더한다 |
| `app` | 모두 | `{ name, description, kind, url, iconUrl, rssUrl }` |
| `apps` · `others` | 모두 | 공개 앱 `[{ name, url, iconUrl, current }]`, `others`는 이 앱을 뺀 것 (다른 앱으로 가는 줄, `{{#others.length}}`로 있을 때만) |
| `menus` | 모두 | `[{ name, url, kind, active }]` |
| `menu` | menu · issue · home(매거진: 첫 호 메뉴) | `{ name, url, kind, isPosts, isIssues, isPages, isPage, rssUrl }` |
| `posts` · `more` | home · menu | `[{ title, excerpt, url, date, tags }]` 20개씩 · 다음 쪽 `{ url } \| null` (`?cursor=`) |
| `post` | post | `{ title, excerpt, url, date, tags, body, html, center, listed, back }` (`body`는 md, 웹이 `html`로 그린다. `listed`가 거짓이면 링크 공개 글, `back`은 올린 메뉴 · 앱 첫 화면) |
| `issues` | home(매거진) · menu(호 메뉴) | `[{ number, title, intro, url, date }]` |
| `issue` | issue · home(매거진: 최신 호) | `{ number, title, intro, url, date, posts: [{ title, excerpt, url }] }` |
| `pages` | home(페이지 앱) · menu(페이지 메뉴) | 공개 페이지 `[{ title, url, date }]` |

- `html`이 붙은 값만 HTML(본문 md를 웹이 그려 거른 것)이라 `{{{ }}}`로 쓴다. 나머지는 `{{ }}`(이스케이프). 웹은 `date`가 있는 곳마다 `dateText`(예: `2026. 11. 16.`)를 더한다.
- 표지 그림(`coverUrl`)은 1-6a에 없다 (글에 대표 그림 칸이 아직 없다). 약속은 더하기만 하므로 나중에 더한다.
- 약속은 이름을 더하기만 한다. 빼거나 이름을 바꿀 때는 `cairn: 2`를 만들고 한동안 둘을 함께 받는다.

### 9.4 주소와 그리기 (웹)

| 주소 | 하는 일 |
|---|---|
| `/<앱>` · `/<앱>/posts/<글>` · `/<앱>/m/<메뉴>` · `/<앱>/m/<메뉴>/<번호>` (끝에 `/`를 붙이지 않는다: Next가 308로 한 번 더 보낸다) | route handler 하나(`app/(blog)/[app]/[[...path]]/route.ts`)가 ① 서버에서 화면 묶음을 받고(9.5) ② 본문 md를 HTML로 ③ 템플릿을 고르고 Mustache로 채우고 ④ 데이터 블록을 넣어 격리 머리글과 함께 보낸다 |
| `/<앱>/files/<이름>` | 서버의 파일을 그대로 흘려보낸다 (같은 격리 머리글) |
| `/<앱>/~<토큰>/…` | 미리 보기. 같은 경로들을 그 토큰의 버전으로. `base`에 토큰이 들어 있어 링크를 눌러도 미리 보기 안에 머문다. 글 본문의 사진(`/api/files/<해시>`)에는 웹이 `?ticket=<토큰>`을 붙인다 (격리된 화면에는 쿠키가 실리지 않아 비공개 앱 글의 사진을 토큰으로 연다, 9.5) |
| `/<앱>/rss.xml` · `/<앱>/m/<메뉴>/rss.xml` | 지금 그대로 (앱 코드와 상관없는 Cairn의 RSS) |
| `/` | 공개 앱 0개 "공개한 앱 없음", **1개는 `/<앱>`로 307** (1-4는 그 자리에서 그렸다. 이제 앱 화면은 앱 코드가 그린다), 2개 이상 앱 아이콘 목록 (Cairn의 화면) |
| 없는 앱 · 비공개 앱 | 같은 Cairn 404 (앱 코드를 거치지 않으니 응답이 같다). 공개 앱 안의 없는 글은 그 앱의 `404.html`(상태 404), 없으면 Cairn 404 |
| 그리기 실패 (템플릿 문법) | 500 "앱 화면을 그리지 못했어요". 미리 보기에서는 파일 · 줄을 보인다. 공개 앱은 미리 보기 뒤에 공개하므로 방문자에게 가기 전에 보인다 |

격리 머리글 (앱 화면 · 앱 파일):

```
Content-Security-Policy: sandbox allow-scripts allow-forms allow-modals allow-popups allow-popups-to-escape-sandbox allow-downloads;
  default-src <사이트> <hosts>; script-src <사이트> 'unsafe-inline' <hosts>; style-src <사이트> 'unsafe-inline' <hosts>;
  img-src <사이트> <hosts> data: blob: https:; font-src <사이트> <hosts> data:; connect-src <hosts>; form-action <hosts>;
  base-uri 'none'; frame-ancestors 'self'
```

- `sandbox`에 `allow-same-origin`이 없어서 앱 화면은 출처 없는 문서다: 우리 쿠키가 실리지 않고, 쓰기 요청은 `ActorGuard`의 출처 확인에서 막히고, 앱 JS가 콘솔 API의 답을 읽지 못한다. 대신 앱 JS는 자기 저장소(localStorage · 쿠키)도 못 쓴다 (4단계 앱별 도메인에서 풀린다).
- `<사이트>`는 사이트 주소(`CAIRN_WEB_URL`)를 그대로 적는다 (출처 없는 문서에서 `'self'`가 맞지 않는 브라우저가 있어서). 그림은 글 본문이 바깥 그림을 쓰므로 https 어디서나.
- 웹의 화면 머리글(`frame-ancestors 'none'` · `X-Frame-Options`)은 `/`와 웹의 최상위 경로에만 붙인다. 목록 `WEB_ROUTES`는 `next.config.ts`에 두고 구조 검사가 웹의 최상위 폴더 · `App.RESERVED`와 맞춰 본다. 앱 주소의 머리글은 route handler만 붙인다 (두 CSP가 겹치거나 콘솔의 미리 보기 창이 막히지 않게).

### 9.5 REST (묶음 `blog/app-code/`)

`AppCode`(버전 · 확인 대기 규칙) · `AppCodeService` · `AppCodeQuery` · `AppSiteQuery`(화면 묶음) · `AppCodeRepository` · `AppTicket`(미리 보기 토큰: `PageTicket`과 같은 모양, 서버 키로 봉인, 용도 `app-view`, 30분, 앱 하나 · 버전 하나에 묶임) · 시작 코드 `blog/app-code/starters/<종류>/`.

| 요청 | 누가 | 하는 일 | 오류 |
|---|---|---|---|
| `GET api/apps/site/:slug/screen?path=&cursor=&ticket=` | 누구나 | 화면 하나에 필요한 것 `{ status, seq, template, templates: { 이름: 글 }, hosts, data, redirect: null }` (`seq` 0은 시작 코드, 앱 안의 없는 주소는 `status` 404). 토큰이 없으면 공개 앱의 보이는 버전. 토큰이 있으면 그 앱 · 그 버전을 **공개된 것처럼** (그 앱의 공개 · 링크 공개 글만, 초안은 아님). 관리자가 토큰 없이 비공개 앱에 오면 `{ redirect }`(토큰 주소). 보는 사람이 누구든 데이터는 방문자 데이터다 | 404 (없는 앱 · 비공개 앱 · 틀린 토큰 모두 같은 404) |
| `GET api/apps/site/:slug/files/:name?ticket=` | 누구나 | 파일 하나. `ETag` = 해시, 공개는 짧은 캐시, 토큰은 `no-store` | 404 |
| `GET api/files/:hash?ticket=` (1-6b에 더함) | 누구나 | 글 사진. 지금 규칙(공개 앱의 공개 · 링크 공개 글 → 누구나, 나머지 → 관리자)에 더해, 미리 보기 토큰이 있으면 **그 토큰의 앱**에 든 공개 · 링크 공개 글의 사진도 (`no-store`). 앱 화면의 데이터와 같은 범위 | 404 (초안 · 다른 앱 · 틀린 토큰 모두 없는 파일과 같다) |
| `GET api/apps/:id/code` | 관리자 | `{ current, pending, versions: [{ seq, source, note, taskId, createdAt, fileCount, bytes }], files: [{ name, mime, sizeBytes }], hosts }` (`files`는 보이는 버전, 없으면 시작 코드) | 404 |
| `GET api/apps/:id/code/versions/:seq/changes` | 관리자 | 앞 버전과 비교 `{ added, changed, removed, hostsAdded, hostsRemoved, bytes }` (카드 · 코드 탭의 바뀐 점 줄) | 404 |
| `POST api/apps/:id/code/preview` | 관리자 | `{ seq? }` → `{ url }` (토큰 주소. 미리 보기 창 · 새 창) | 404 |
| `POST api/apps/:id/code/current` | 관리자 | `{ version, seq }` 이 버전 공개 (앞 버전으로 되돌리기도 같은 요청). 확인 대기를 비운다 | 409 버전, 404 |
| `POST api/apps/:id/code/versions?version=&note=` | 관리자 | zip 본문(20MB) → 201 새 버전(`upload`). 공개 앱은 확인 대기, 비공개 앱은 바로 보이는 버전 | 413, 415 zip 아님, 422 묶음 규칙(폴더 · 이름 · 개수 · `index.html` · `cairn.json`), 409 |
| `GET api/apps/:id/code/versions/:seq/zip` | 관리자 | 그 버전 zip (`seq` 0 = 시작 코드). zip은 `platform/base`의 `ZipFile` · `ZipReader` | 404 |
| `POST api/apps/:id/code/starter` | 관리자 | `{ version }` 시작 코드를 새 버전으로 (처음으로 되돌리기, 기록은 남음) | 409 |

- 공개 · 되돌리기 · 올리기 · 시작 코드는 **관리자 로그인만** (기기 토큰 · AI는 못 한다. 페이지와 같은 규칙).
- 앱 지우기(`POST api/apps/:id/delete`)는 지금 규칙 그대로. 코드 버전은 남는다.

### 9.6 AI로 고치기

1. 코드 탭의 "AI에게 맡기기" → 만들기 작업(`POST api/tasks`, kind `make`, payload `appCode: { appId }`, task의 `AppCodeOrder`, `PageOrder`와 같은 모양). 대화에서는 대표가 make 팀원에게 `delegate_task`의 하위 작업 `app_id`로 맡긴다 (9.11.2).
2. 러너: MCP `app_code_base { task_id }` → `{ app_id, name, kind, slug, seq, files: [{ name, size, text }], hosts }` (가장 새 버전, 없으면 시작 코드 `seq` 0. 글 파일은 내용까지 300KB)를 `inputs/app/`에 두고 지시문 틀 `make`의 `# 고칠 앱` 단락을 채운다(`AppCodeBase`). AI는 `cairn-make`의 앱 코드 지시(`references/app-code.md`)를 따라 바뀐 파일만 낸다. 러너가 받은 코드 위에 낸 파일을 얹어 검사하고(`AppCodeCheck`: 묶음 규칙 · 템플릿 문법 · 데이터 이름) `submit_result`의 checks로 올린다. 떨어지면 AI에게 한 번 더 맡기고(검증 고리 V), 묶음 · 문법이 그래도 틀리면 새 버전 없이 실패로 끝낸다 (9.11.3).
3. 작업이 끝나면 task가 `task.app_code.built { taskId, runId, appId, note, files }` → blog `AppCodeBuiltHandler` → 새 버전(`task`).
4. 공개 앱: 확인 대기 + `blog.app_code.added`(pending) → 알림 "앱 코드 확인 대기"(코드 탭으로, 공개하면 읽음). 코드 탭 · 미리 보기의 "이 버전 공개" = `POST …/code/current`. 공개하지 않아도 버전은 남는다. 비공개 앱: 바로 보이는 버전. 대화의 일이 낸 확인 대기 버전은 그 대화의 결과 카드에 공개 승인(`blog.app_code.show`)으로 실려, 고르면 공개된다 (9.11.2).
5. 이벤트: `blog.app_code.added { appId, name, seq, source, pending, taskId }`(`taskId`는 AI 작업이 만든 버전이면 그 작업, 아니면 null) · `blog.app_code.shown { appId, seq, settled }` · `blog.app_code.refused { appId, name, taskId, error }`(AI 결과가 묶음 규칙에 맞지 않아 버전을 만들지 못함 → 알림, 작업은 이미 끝났다) (`blog.events.json`에 등록).

### 9.7 콘솔

- 앱 관리에 탭 **코드** (시안): 버전 목록(확인 대기 · 공개 중 · 출처: 시작 코드 · zip 올림 · AI 작업 · 복원), 버전마다 미리 보기 · 이 버전 공개 · 되돌리기, zip 올리기 · 내려받기, 지금 버전의 파일, 바깥 주소(읽기만, 바꾸려면 `cairn.json`을 고친 새 버전), "AI에게 맡기기" 입력.
- 미리 보기 화면 `/admin/store/[id]/code/[seq]` (`seq`는 버전 번호 · `0` 시작 코드 · `live` 지금 보이는 코드): 데스크톱 · 폰(390px) 너비, 새 창, 앞 버전과 바뀐 파일 · 새 바깥 주소 한 줄, 이 버전 공개. 미리 보기 창(iframe)은 토큰 주소를 열고, 틀에도 같은 `sandbox`를 한 번 더 건다.
- "AI에게 맡기기" 입력은 보관함 › 페이지의 입력과 같은 부품(`_ui/InstructionForm`)이고, 고치는 중인 작업(`useAppCodeTasks`)을 그 아래에 보인다.
- 1-5에서 미룬 **비공개 앱 미리 보기**도 이것 (개요 탭의 "미리 보기").

### 9.8 보관 형식

- `blog/apps/<주소>/code/<파일>`: 보이는 버전의 파일, 이름 순서 (시작 코드면 쓰지 않는다). 공개 저장소에는 공개 앱의 코드만. 1-6c ✅ (`PostArchiveQuery.appCode`)
- 복원: 파일이 있으면 버전 1(`restore`)로 바로 보인다 (`RestoredAppCode`: 저장할 때와 같은 묶음 규칙, 들어오지 않는 앱의 코드면 멈춘다). 버전 기록과 확인 대기 버전은 싣지 않는다 (코드는 지금 모양이 곧 앱이다).

### 9.9 1-4에서 바뀌는 것

- `app/(blog)/[app]/`의 화면들(layout · page · posts · m)을 지우고 route handler 하나로. `_blog/`의 앱 화면 컴포넌트(AppShell · AppHeader · AppFooter · AppHome · PostList · IssueBody · PageFrame)는 시작 코드 셋(블로그 · 매거진 · 페이지 앱)의 템플릿으로 옮기고 지웠다 (1-6b). 지금 모습 그대로 옮겨서 있는 앱의 화면은 바뀌지 않는다. `PostArticle`은 관리자의 앱 밖 · 초안 글 미리 보기(`/posts/<글>`)가 계속 쓴다.
- `_lib/markdown`은 그대로 (편집기 미리 보기와 route handler가 쓴다).
- 고정 주소 `/posts/<글>` 307과 관리자의 앱 밖 · 초안 글 미리 보기는 Cairn 화면 그대로.
- 글 화면의 플러그인 자리(`Slot`, comments-giscus)는 앱 코드 데이터에 없다. 플러그인 계약을 바꾸는 일이라 따로 결재한다 (그 전에는 앱 코드에 giscus 스크립트를 넣고 `hosts`에 `giscus.app`).

### 9.10 새 라이브러리 `mustache` (객체설계 10장 순서)

### 9.11.1 1-6a에서 정한 것 · 1-6b로 넘기는 것

- 서버의 화면 데이터는 `AppScreenQuery`가 앱을 먼저 정한 뒤(공개 앱 또는 토큰의 앱) 그 앱 안만 읽는다: 앱 공개 조건을 다른 Query마다 넓히지 않고, 토큰 미리 보기도 같은 길로 비공개 앱의 공개 글을 본다.
- AI 결과가 묶음 규칙에 맞지 않으면 버전 없이 `blog.app_code.refused` 알림 (작업은 이미 끝나 되풀이하지 않는다). 그사이 다른 버전이 생겼으면 409로 일꾼이 다시 받아 새 바탕 위에 얹는다.
- 시작 코드는 `apps/server/starters/`(base + 종류)이고 서버 이미지에 함께 든다. 템플릿 파일(Mustache)은 HTML로 읽히지 않아 Biome 검사에서 뺀다.
- 1-6b로: 비공개 앱 미리 보기의 글 사진(`/api/files/<해시>`)은 격리된 화면에 쿠키가 없어 보이지 않는다 → 1-6b에서 둘 다 했다 (웹이 토큰을 싣고 파일 API가 받는다, 9.11.2). 페이지 앱의 시작 코드는 페이지를 틀로 넣지 않고 링크로 보인다 (출처 없는 화면 안에서는 `frame-ancestors 'self'`가 맞지 않는다).

### 9.11.2 1-6b에서 정한 것 · 미룬 것

- 앱 주소의 끝 `/`를 없앴다 (`/dev`, `/dev/~<토큰>`): Next가 끝 `/`를 308로 한 번 더 보내서 토큰 주소 · 미리 보기 창이 두 번 오갔다. 서버의 `base` · 앱 주소 · 미리 보기 주소 · 시작 코드의 링크가 모두 끝 `/` 없이.
- 미리 보기의 글 사진: 웹이 미리 보기에서만 본문 HTML의 `/api/files/<해시>`에 토큰을 붙이고, 파일 API가 토큰의 앱 · 공개 범위를 본다 (9.5). 토큰은 이미 주소에 있으므로 새로 드러나는 값은 없고, 미리 보기 화면은 `Referrer-Policy: no-referrer`다.
- 앱 JS가 콘솔 API에 닿지 못하는 까닭은 세 겹이다: ① `connect-src`에 사이트가 없다 ② 출처 없는 문서라 SameSite=Lax 쿠키가 실리지 않는다 ③ 응답에 CORS 허락이 없다. 관리자가 `cairn.json`의 `hosts`에 사이트 주소를 적어도 ②③이 남는다.
- **대화에서 앱 코드를 맡기는 길과 결과 카드 (1-6b 나머지, 2026-11-18).**
  - 맡기기: `delegate_task`의 하위 작업에 `app_id`를 적으면 그 make 일의 `payload.appCode { appId }`가 된다. make가 아닌 일에 적으면 `rule_violation`(`MakeOrder`). 주인이 고른 주문(`payload.make` · `page`)은 여전히 물려주지 않는다: `app_id`는 위 작업에서 물려받는 값이 아니라 대표가 적는 값이고, 그 결과는 공개 앱이면 확인 대기라 사람이 공개해야 방문자에게 보인다 (비공개 앱은 바로 보이지만 방문자에게는 없는 앱이다). 앱이 있는지는 위임 때 보지 않는다: 코드 탭의 `appCode`와 같이 러너의 `app_code_base`가 404, blog가 없는 앱의 결과를 버린다.
  - 결과 카드: `blog.app_code.added`에 `taskId`를 실었다. task의 `AppCodeCardHandler`가 그 작업이 대화의 일 아래이고 버전이 확인 대기(`pending`)일 때만 그 대화에 작업에 묶이지 않은 결재(`Approval.forAppCode`: 동작 `blog.app_code.show`, 대상 `app` · 판 = 버전 번호, 메모 "<앱> 버전 <n>")를 올린다. 같은 버전은 결재 하나 (`Idempotency`, 키 `<앱>:<버전>`). 결재에 `chat_id`가 있어 그 대화의 카드에 실린다.
  - 앱 코드 일의 결과물(파일)은 카드에 싣지 않는다 (`OutputRepository.uncardedInChat`가 `payload.appCode` 작업을 뺀다): 파일은 이미 버전이 되었고, 고르지 않은 결과물을 휴지통으로 보내는 카드 규칙이 버전과 어긋난다.
  - 승인하면 blog `AppCodeShowHandler`(`task.approval.granted` 중 `blog.app_code.show`) → `AppCodeService.showApproved`(`ApprovedActor`의 동작이 `blog.app_code.show`일 때만) → `AppCode.showApproved`: 그 버전이 아직 보이지 않을 때만 보인다. 그사이 관리자가 같은 버전이나 더 새 버전을 공개했으면 되돌리지 않고, 없는 버전 · 지운 앱이면 아무것도 하지 않는다. 작업에 묶이지 않은 결재라 결과를 task에 돌려주지 않는다. 고르지 않으면 반려되고 버전은 확인 대기로 남는다 (코드 탭에서 공개할 수 있다).
  - 카드 항목에 `targetVersion`을 실었다: 웹은 이 동작에 "미리 보기"(콘솔의 그 버전 미리 보기 `/admin/store/<앱>/code/<버전>`)를 붙인다.
- 미룸(그대로): 글 화면의 플러그인 자리(giscus, 9.9), 페이지 앱의 페이지를 틀로 넣기(9.11.1).

### 9.11.3 1-6c에서 정한 것

- **검사는 러너가 한다 (스킬의 검사 스크립트 대신).** 서버가 보내는 스킬 판은 `SKILL.md`와 `references/*.md`만 싣는다 (task `SkillFiles`): 스킬에 스크립트를 두면 콘솔에서 고친 판으로 돌 때 빠진다. 러너에는 런타임 의존 패키지가 없어(Dockerfile) Mustache 라이브러리 대신 태그만 훑는 `AppCodeCheck.scan`을 두었다: 여닫는 짝 · 없는 조각 · `{{{ }}}`/`{{& }}`는 `html` 값에만 · 구분자 바꾸기 금지 · 닫히지 않은 태그. 시작 코드 셋이 이 검사를 지나는지 러너 테스트가 본다.
- 검사 셋: `앱 코드 묶음`(받은 코드 위에 얹어 100개 · 합 20MB · 템플릿 합 1MB · `index.html`, 낸 `cairn.json`의 모양 — 서버 `AppCodeBundle`과 같은 한도) · `템플릿 문법` · `데이터 이름`. 묶음 · 문법은 일을 실패로 끝낸다(서버는 Mustache를 읽지 않아 틀린 템플릿도 버전이 되고, 비공개 앱은 바로 보인다). 이름은 알리기만 한다(없는 이름은 빈 칸으로 그려질 뿐이다).
- 데이터 이름 목록은 러너의 `AppCodeCheck.NAMES`다. 약속은 이름을 더하기만 하므로, 서버 테스트(`app-screen.view.test`)가 모든 화면의 데이터 이름(+ 웹이 더하는 `html` · `dateText` · `name`)이 그 목록에 있는지 본다. 약속에 이름을 더하면 그 목록에도 더한다.
- AI가 낸 템플릿 · `cairn.json`은 러너가 agent 권한으로 읽는다(`AgentUser.readFile`): AI가 둔 링크를 러너가 따라가지 않게.

### 9.12 나중에 생길 일에 버티는 법 · 고르지 않은 것

| 나중에 | 지금 모양이 버티는 법 |
|---|---|
| 앱마다 도메인 (4단계) | 그 도메인에서는 진짜 다른 출처라 `sandbox`를 풀고 저장소 · 쿠키를 쓸 수 있다. 코드 묶음 · 데이터 약속은 그대로 |
| 커뮤니티 (3단계) | 방문자 로그인 · 글쓰기는 앱 JS가 부르는 공개 API(CORS, 앱별 토큰)로. 데이터 약속에 이름을 더한다 (`cairn: 1` 그대로) |
| 폴더가 있는 앱 | 파일 이름 규칙(`PageFiles`)만 넓히면 된다 (`css/a.css`, `..` 금지) |
| 기능 패키지의 새 앱 종류 | 시작 코드 폴더 하나를 더한다 |

고르지 않은 것:

- **`blog.pages`를 앱 코드로 다시 쓰기**: 페이지 목록 · `/pages/` 주소 · 보관함 · 공개 여부마다 "앱 코드는 빼고"를 걸어야 하고 공개 여부가 페이지와 앱 둘로 갈린다. 파일 규칙(`PageFiles`) · 미리 보기 표 · 확인 대기 방식만 다시 쓴다.
- **앱 JS가 JSON API로만 그리기 (빈 HTML)**: JS 없이는 글이 안 보이고 검색에 안 잡히며, 출처 없는 문서에서 API를 부르려면 CORS를 열어야 한다.
- **Handlebars · Liquid**: 템플릿 안에 로직(helper · filter)이 들어온다. Mustache로 충분하다.
- **앱 코드를 서버에서 실행 (React · Node)**: 남이 만든 코드를 서버에서 돌리지 않는다 (2026-11-18 결정).
- **`sandbox`에 `allow-same-origin`**: 앱 JS가 우리 쿠키 · API에 닿는다.
- **앱마다 하위 도메인을 지금**: DNS · 인증서가 앱마다 필요하다. 4단계로.
- **1-4 화면을 두고 코드가 있는 앱만 템플릿으로**: 그리는 길이 둘이 되고, 기본 앱의 모양을 바꾸려면 Cairn 코드를 고쳐야 한다.
- **버전 표에 앱 외래키**: 버전이 추가만이라 코드를 고친 앱은 지울 수 없게 된다.

## 10. 2단계 앱별 운영 (설계안 승인 2026-11-18)

### 10.0 한 장 요약

관리자는 대표와만 대화하고, 대표가 앱의 일을 그 앱의 운영 팀에 맡긴다. 결과는 지금처럼 결과 카드로 승인한다.

| # | 정한 것 |
|---|---|
| 1 | 앱마다 운영 팀장(`apps.agent_id`)과 편집 방침(`apps.policy`, 4000자). 메뉴의 같은 칸과 같은 모양. 팀장은 맨 위 에이전트(대표가 맡길 수 있는 층)이고 비공개를 읽지 않는 에이전트만. 한 팀장이 여러 앱을 맡아도 된다 |
| 2 | 운영 팀 = 팀장과 그 아래 팀 전체. 앱 · 메뉴에 글을 놓는 에이전트는 비공개를 읽지 않고, 운영 팀이 정해져 있으면 그 팀 안이어야 한다. 메뉴에도 운영 팀이 있으면 메뉴가 정한다. 메뉴의 운영 팀도 "그 에이전트 하나"에서 "그 에이전트와 그 아래 팀"으로 넓힌다 (팀장이 팀원에게 나눠 맡기므로) |
| 3 | 팀 확인은 platform `AgentDirectory` 카드의 `chain`(보고 대상을 위로 따라간 id). blog는 task를 가져오지 않는다 |
| 4 | 대표는 `get_settings apps`의 `agent_id` · `policy`를 읽고 앱의 일을 그 팀장에게 맡긴다. 운영 팀이 없는 앱이면 `propose_setting app edit { agent_id }`를 `continue`와 함께 제안 |
| 5 | 대화에 앱: `task.chats.app_id` (앱 관리의 "맡기기"로 연 대화만, 확인 · 이름은 platform `Lookups`의 `app`). 회차마다 대표에게 앱이 가고, 그 대화에 묶인 자동화도 같다. `GET api/chats?app=`로 앱의 대화와 수 |
| 6 | MCP: `blog_menus { app_id? }`가 앱(방침 · 운영 팀)을 함께 내고, `blog_save_draft`에 `app_id`(메뉴 없이 앱에만) |
| 7 | 방문자 첫 화면 고정: `apps.home`(공간마다 하나, 공개 앱만, 비공개로 바꾸면 풀림), `PUT api/apps/home`(관리자만, 대화 제안 없음). `/`는 고정 앱이 있으면 그 앱으로, 없으면 지금처럼 자동 |
| 8 | 팀 템플릿 "앱 운영 팀": 편집장(팀장) · 작가(write) · 검토자 · 앱 디자이너(make) |

이미 된 것: 앱마다 RSS(1-4), 받을 것 넓히기(O-3: `blog` = 글 · 호 발행, `app_code` = 앱 코드. 값은 그대로, 화면 이름만 "글 발행").

단계: 2-1 서버 blog → 2-2 서버 task → 2-3 지시문 · 러너 · 스킬 → 2-4 웹 → 2-5 문서 · 전체 테스트 · 화면 확인 · main.

고르지 않은 것: 앱 운영 팀 표 따로(팀은 이미 조직도), 팀원 줄에 "운영하는 앱" 싣기(task가 blog를 읽는 길이 하나 더), 첫 화면을 사이트 설정(account)에(account가 blog의 앱 id를 들고 이벤트로 맞춰야 함), 작업 토큰에 앱을 넣어 대화의 앱 밖에 못 쓰게(운영 팀 규칙이 막는다), 앱 코드 일(make)도 운영 팀만(task가 blog의 팀을 읽어야 해서 뒤로. 공개 앱의 코드는 이미 승인을 거친다).

### 10.1 2-1 인터페이스: 서버 blog (승인 2026-11-18, 끝남)

설계안과 달라지는 점 두 가지:

- **편집 방침은 백업 파일에 넣지 않는다.** 공개 앱의 앱 파일은 공개 저장소로 갈 수 있는데 방침은 방문자에게 보이는 것이 아니다. 메뉴의 방침도 아직 파일에 없다 (보관형식 "아직 파일에 없는 것"). `home`만 넣는다.
- **`blog_menus`의 모양을 바꾸지 않고 더한다.** 지금 `{ menus }`를 두고 `apps`를 더한다 (깨지는 변경은 새 도구 이름이라는 API설계 2장 규칙).

표 (마이그레이션 하나 `blog_app_team`):

```sql
ALTER TABLE blog.apps
  ADD COLUMN agent_id uuid,                        -- 운영 팀장 (task 에이전트 id, 모듈 사이라 외래키 없음)
  ADD COLUMN policy text NOT NULL DEFAULT '',      -- 편집 방침
  ADD COLUMN home boolean NOT NULL DEFAULT false,  -- 방문자 첫 화면으로 고정
  ADD CONSTRAINT apps_policy_length CHECK (char_length(policy) <= 4000),
  ADD CONSTRAINT apps_home_public CHECK (NOT home OR visibility = 'public');
CREATE UNIQUE INDEX apps_one_home ON blog.apps (space_id) WHERE home;  -- 공간마다 하나
```

규칙 (`blog/app/app-team.policy.ts` `AppTeam`, 앱 · 메뉴가 함께 쓴다):

| 메서드 | 하는 일 |
|---|---|
| `AppTeam.ranks(actor, card)` | 에이전트면 `[자기 id, ...card.chain]`, 아니면 `[]` |
| `AppTeam.assertWriter(by, ranks, menuTeam, appTeam, where)` | 관리자 · 기기는 통과. 에이전트는 비공개를 읽으면 403, 운영 팀(`menuTeam ?? appTeam`)이 있는데 `ranks`에 없으면 403 "<where>의 운영 팀이 아니에요" |
| `AppTeam.allows(by, ranks, team)` | 위와 같은 판단의 참 · 거짓 (`blog_menus`의 `can_write`) |
| `AppTeam.assertLeader(card, forApp)` | 없으면 404, 비공개를 읽으면 422, 앱이면 맨 위(`chain` 비었음)가 아니면 422 "맨 위 에이전트만 앱의 운영 팀장이 될 수 있어요" |

- `Menu.assertWriter`는 지우고 `Post.placeIn(app, menu, by, ranks, now)` · `PostService.intoIssue`가 `AppTeam.assertWriter`를 부른다. `ranks`는 Service가 트랜잭션 전에 `AgentDirectory`로 읽는다 (놓는 요청이 있을 때만).
- platform `AgentCard`에 `chain: readonly string[]`(보고 대상, 가까운 순). task `AgentQuery.card`는 에이전트 자신도 읽는다 (`actor.id === id`).
- 지운 팀장은 카드가 없어 팀 밖과 같다 (관리자 · 기기만 놓는다). 휴지통에서 되살리면 그대로 돌아오게 값은 비우지 않는다 (메뉴와 같다).

REST (관리자만, 모양은 더하기만):

| 경로 | 바뀌는 것 |
|---|---|
| `POST api/apps` · `PATCH api/apps/:id` | 본문에 `agentId: uuid \| null` · `policy: string` (보내지 않으면 그대로). 팀장은 트랜잭션 전에 `AppTeam.assertLeader` |
| `PUT api/apps/home` (새로) | `{ appId: uuid \| null }` → 204 (화면이 목록을 다시 읽는다). 공간의 앱을 모두 잠그고 다른 앱의 고정을 푼 뒤 이 앱을 고정. 비공개 앱이면 422. 같은 값이면 그대로 (requestId · version 없음: 결과가 늘 같다) |
| `AppView` (관리자) | `agentId` · `policy` · `home` |
| `PublicAppView` (방문자) | `home` (웹 `/`가 본다) |

- `App.edit`이 공개 → 비공개면 `home`도 푼다 (DB CHECK도 막는다).

MCP (`blog.tools.ko.json`의 설명 함께):

| 도구 | 바뀌는 것 |
|---|---|
| `blog_menus { app_id? }` | 응답에 `apps: [{ id, name, slug, kind, policy, agent_id, can_write }]`(페이지 앱 빼고)를 더하고, `menus`의 줄마다 `app_id` · `can_write`. `app_id`를 주면 그 앱과 그 앱의 메뉴만 (없으면 not_found) |
| `blog_save_draft` | `app_id: uuid \| null` (메뉴 없이 그 앱에 넣기). `menu_id`와 함께 보내면 같은 앱이어야 한다 (아니면 422) |
| `get_settings apps` | 줄마다 `agent_id` · `policy` · `home`(읽기만) |
| `propose_setting app` | `fields`에 `agent_id` · `policy`. 미리 해 보기 · 적용도 `AppTeam.assertLeader`. `home`은 받지 않는다 (422, 공개 여부와 같은 규칙) |

메뉴: `MenuService`의 팀장 확인도 `AppTeam.assertLeader(card, false)` (깊이는 보지 않음).

보관 형식: 앱 파일에 `home: true`(고정일 때만). 복원은 공개 앱만, 둘 이상이면 멈춘다. `agent_id` · `policy`는 넣지 않는다 (위).

테스트: `app.api.test`(팀장 고르기: 맨 위 · 아래 · 비공개 읽기 · 지운 에이전트, 방침 길이, 첫 화면 고정 · 옮기기 · 비공개면 풀림 · 방문자 응답, 방문자 · 기기는 못 바꿈), `post-tool.api.test`(팀 안의 작가는 놓기, 팀 밖은 403, 메뉴 팀이 앱 팀보다 먼저, `app_id` · 메뉴와 앱이 다르면 422, `blog_menus`의 `apps` · `can_write`), 설정 바꾸기(`agent_id` · `policy` 제안 → 승인 → 적용), 복원(`home`).

줄 수: `post.ts`가 300줄이라 판단을 `AppTeam`으로 옮기며 늘리지 않는다.

2-1에서 정한 것: 놓는 요청자의 운영 팀 확인은 `Post.placeIn`이 아니라 `PostService`가 `AppTeam`으로 한다 (`intoIssue`와 같은 자리, 보고 대상을 트랜잭션 전에 읽어서 · `post.ts` 300줄). `PUT api/apps/home`은 204 (진입 계층은 메서드 하나만 부른다, 화면이 목록을 다시 읽는다). 방침이 4000자를 넘으면 입력 모양에서 400. 같은 앱의 `app_id`만 보내면 메뉴를 두고 그대로.

### 10.2 2-2 인터페이스: 서버 task (승인 2026-11-18, 끝남)

```sql
ALTER TABLE task.chats ADD COLUMN app_id uuid;  -- 대화의 앱 (blog 앱 id, 모듈 사이라 외래키 없음)

CREATE INDEX chats_app_idx ON task.chats (space_id, app_id, updated_at DESC) WHERE app_id IS NOT NULL;
```

### 10.4 2-4 인터페이스: 웹 (승인 2026-11-19, 끝남)

서버 API는 2-1 · 2-2 그대로 쓰고 새로 만들지 않는다. 타입은 서버 View에서 `import type`.

| 화면 | 바뀌는 것 |
|---|---|
| 앱 관리 › **운영 팀** 탭 (새로, `?tab=team`, `AppTeamTab.tsx`) | 운영 팀장 고르기(맨 위의, 비공개를 읽지 않는 에이전트 · 없음, `PATCH api/apps/:id { agentId }`) · 팀원 목록(조직도에서 팀장 아래) · 운영 팀이 없으면 "앱 운영 팀 만들기"(템플릿 `app`을 만들고 편집장을 팀장으로) · 편집 방침(`policy`) · "이 앱에 맡기기" 입력(`POST api/chats { appId }` → 그 대화로) |
| 앱 관리 › 개요 | "이 앱의 대화"(`GET api/chats?app=`: 제목 · 상태 · 승인 대기 표시, 5개 · 모두 보기는 대화 목록) |
| 내 앱 카드 | 운영 팀장 이름(없으면 "운영 팀 없음") · 승인 대기 수(대화 목록의 `appId` · `waiting_approval`) |
| 만들기 시트 | 운영 팀: 나중에 · 있는 팀장 · 앱 운영 팀 새로 만들기 (새로면 팀을 먼저 만들고 앱을 만든다) |
| 설정 › 사이트 | "첫 화면": 자동 · 공개 앱 하나 (`PUT api/apps/home`) |
| 대화 머리 | 앱 칩 (앱 이름, 누르면 앱 관리) |
| 공개 `/` | 고정 앱이 있으면 그 앱으로 307, 없으면 지금처럼 자동 |

확인: 화면 테스트(웹 단위), 브라우저로 데스크톱 · 폰 (운영 팀 탭 · 맡기기 → 대화의 앱 칩 · 내 앱 카드 · 만들기 시트 · 첫 화면 고정 → `/`).

2-4에서 정한 것: 같은 템플릿으로 만든 팀장은 이름이 같아서(편집장) 고르기 칸에 이미 운영하는 앱을 붙인다(`leaderLabel`: "편집장 · 개발 블로그 운영"). 만들기 시트의 "앱 운영 팀 새로 만들기"는 앱과 같은 requestId로 팀을 먼저 만든다 (다시 눌러도 팀은 하나). 내 앱 카드의 승인 대기 수는 대화 목록(최근 100개)에서 센다. 화면 확인: 내 앱 카드 · 운영 팀 탭(팀장 · 방침 · 팀원) · 운영 팀 없음 → 앱 운영 팀 만들기 · 맡기기 → 대화의 앱 칩 · 개요의 이 앱의 대화 · 만들기 시트의 운영 팀 칸 · 설정 › 사이트 첫 화면(고정 → 방문자 `/`가 그 앱으로 307, 자동으로 되돌림) · 폰.

### 10.5 2-5 마무리 (2026-11-19)

서버 테스트 · 러너 통합 테스트 · 러너 단위 · CLI · `pnpm check` 통과. 남은 확인(배포 서버): 실제 AI(Claude · Codex) 대표가 `get_settings apps`로 운영 팀장을 찾아 맡기는지, 작가가 `blog_menus`의 `can_write`를 보고 놓는지.


### 10.6 2-6 인터페이스: 대화로 앱 만들기 (승인 2026-11-19, 2-6a 서버 끝남)

목적: "여행 계획 사이트 하나 만들어 줘" 한마디로 대표가 앱 종류를 고르고, **승인 한 번에 앱과 운영 팀을 함께 만들고**, 이어서 첫 결과(첫 글 · 첫 화면)까지 낸다. 마이그레이션은 없다.

2-5 뒤에 코드를 보고 찾은 빈 곳:

1. 대표 지시문에 앱 만들기의 갈래(4장)가 없다. 같은 말에 블로그로 갈지 화면으로 갈지 정해져 있지 않다.
2. 대화로는 운영 팀 템플릿을 쓰지 못한다 (에이전트를 하나씩 제안해야 한다).
3. 대화의 "페이지" 결과(받을 것 `html`)는 결과물 파일(`.html`)이지 페이지(`blog.pages`)가 아니다. 페이지 앱은 페이지가 꼭 있어야 해서 대화로 끝까지 만들지 못한다. (그래서 처음 말한 "`page_id`를 받기"는 대화에서 쓸 수 없다.)
4. 새로 만든 앱은 비공개라 앱 코드의 새 버전이 승인 없이 바로 보인다. 받을 것이 `app_code`면 서버가 공개 승인(`blog.app_code.show`)을 찾지 못해 같은 일을 두 번 다시 맡긴다.

| 바뀌는 곳 | 모양 |
|---|---|
| blog `AppEdit.create` | 페이지 앱은 **페이지 없이도** 만든다 (`pageId` 선택). 화면은 앱 코드다. 페이지를 주면 지금처럼 그 페이지를 앱에 넣는다. 복원은 이미 페이지 없는 페이지 앱을 받는다 |
| blog `AppEdit.SETTING` (`propose_setting app`) | fields에 `new_team`(true, 만들 때만, 굵은 줄). `agent_id`와 함께 주면 422 "운영 팀장을 고르거나 새로 만들거나 하나만 해요", 고치기에 주면 422 "운영 팀 새로 만들기는 앱을 만들 때만 해요" |
| platform `AgentDirectory` | `registerTeamMaker(make)` · `teamFor(actor): Promise<string>`(팀장 id)를 더한다. 에이전트를 가진 모듈(task)이 등록하고, 승인한 설정 바꾸기가 부른 팀을 만든다. platform · blog는 템플릿 이름 · 구성원을 모른다 (platform에 업무 말을 두지 않으려고 이름을 일반으로) |
| task (등록하는 함수, `AgentService.createAppTeam`) | `ApprovedActor`(동작 `task.setting.change`)만 받는다. 그 결재를 읽어(`ApprovalQuery.asksAppTeam`) 승인됨 · `setting: app` · `op: create` · `new_team: true`인지 보고 아니면 Forbidden. 템플릿 `app`, requestId = 결재 id (결재마다 팀 하나, 다시 와도 같은 팀). 도구는 엔진 목록 첫 줄 (웹의 팀 만들기와 같다) |
| blog `AppService.applySetting` | `new_team`이면 트랜잭션 전에 `AgentDirectory.teamFor` → 팀장 id를 `agent_id`로 넣어 앱을 만든다 (앱 저장과 결과 `blog.setting.changed`는 지금처럼 한 트랜잭션). 팀 만들기가 규칙에 막히면 그 까닭으로 결재를 실패로 끝낸다. 이미 적용한 결재면 팀을 다시 찾지 않는다 |
| task `ChatResult.NEEDS`의 `app_code` | 공개 승인(`blog.app_code.show`) **또는** 이번 회차에서 끝난 앱 코드 만들기 일(`payload.appCode`, done, `ChatRepository.madeAppCode`). 비공개 앱은 승인 없이 바로 보이기 때문이다. 공개 앱은 지금처럼 카드에 공개 승인이 실린다 |
| 지시문 틀 `lead` | 새 앱 만들기 단락 (아래) |
| 도구 설명 `propose_setting` (`task.tools.ko.json`) | 앱 fields에 `new_team`(true면 앱 운영 팀(편집장 · 작가 · 자료 조사 · 앱 디자이너)을 새로 만들어 운영 팀장으로, `agent_id`와 함께 쓰지 않음, 만들 때만). `kind: page`는 "페이지 없이 만들고 화면은 앱 코드(make의 `app_id`)로" |
| 웹 만들기 시트 | 페이지 앱의 "앱이 될 페이지"에 "없음 · 앱 코드로 화면 만들기" |
| 웹 승인 줄 이름 (`_task/setting-labels.ts`) | `new_team: '앱 운영 팀 새로 만들기'` |
| 시작 코드 `starters/page` | 페이지가 없으면 앱 설명과 "준비 중" 한 줄 (공개 전에는 관리자만 본다) |

대표 지시문의 새 단락 (요지):

- 새 앱을 만들어 달라면 **방문자가 무엇을 하는지**로 종류를 고른다: 글을 읽는다 → `blog` (호로 묶어 낸다 → `magazine`) · 화면을 쓴다(일정표 · 계산기 · 지도) → `page` (페이지 없이, 화면은 앱 코드) · 가입 · 저장 · 결제가 필요하다 → 지금은 못 한다. 까닭과 가장 가까운 대안(앞의 둘 중 하나)을 짧은 답(`answer`)으로 낸다.
- 받을 것은 `setting`이 아니라 **앱의 첫 결과**로 정한다: `blog`면 `blog`(첫 글 발행), `page`면 `app_code`(첫 화면). 앱 만들기 승인은 `continue: true`로 올려 같은 대화에서 이어 간다.
- `propose_setting app create`(kind · name · slug · description · menus · policy)에 운영 팀: 맡을 팀장(맨 위, 비공개를 읽지 않음, 다른 앱을 맡지 않음)이 있으면 `agent_id`, 없으면 `new_team: true`.
- 승인 뒤 이어서 회차: `get_settings apps`로 새 앱의 id · `agent_id`를 읽고 그 운영 팀장에게 첫 결과를 맡긴다 (화면은 편집장이 앱 디자이너에게 kind make · `app_id`).

흐름 예 ("여행 계획 사이트 하나 만들어 줘", 화면 앱으로 판단한 경우):

1. 대표: `set_deliver app_code` → `propose_setting app create { kind: page, name: 여행 계획, slug: trip, new_team: true }`, `continue: true` → 결과 카드 (**승인 ①**: 앱 + 운영 팀)
2. 적용: task가 앱 운영 팀을 만들고 blog가 앱(비공개)을 그 편집장과 함께 만든다
3. 이어서 회차: 대표 → 편집장 → 앱 디자이너(make, `app_id`) → 앱 코드 버전 1 (비공개라 바로 보임) → 받을 것 충족 → 답 "앱 관리 › 코드에서 미리 보기"
4. 공개는 관리자가 앱 관리에서 한다 (AI는 공개하지 못한다). 공개 뒤 화면을 고치면 카드의 공개 승인 (1-6b)

글 앱이면 3에서 작가가 첫 글 초안을 앱의 메뉴에 놓고 카드에 발행 승인이 실린다 (**승인 ②**).

오류 경우:

| 경우 | 결과 |
|---|---|
| `new_team`과 `agent_id`를 함께 | 제안에서 422 rule_violation |
| 고치기(`op: edit`)에 `new_team` | 제안에서 422 rule_violation |
| 같은 결재가 두 번 옴 | 팀 하나 · 앱 하나 (requestId = 결재 id, `SettingOutcome`) |
| 팀은 만들었는데 앱이 막힘 (승인 사이에 다른 앱이 그 주소를 씀) | 결재 실패 "이미 쓰는 앱 주소예요". 팀은 남는다 (팀 화면에서 휴지통으로 · 앱 관리에서 팀장으로 고를 수 있다) |
| 그 결재가 아닌 요청자(관리자 REST · 제안의 미리 해 보기 · 다른 결재)가 `teamFor`를 부름 | Forbidden |

나중에 버티는 법:

- 템플릿을 고르는 칸이 필요해지면 `new_team: true`를 템플릿 키로 넓힌다 (true = `app`). 템플릿은 task 안에만 있어 blog는 바뀌지 않는다.
- 새 앱 종류(커뮤니티 등)가 생기면 지시문의 갈래 한 줄과 kind 값만 더한다.
- 페이지로 페이지 앱 만들기(`page_id`)는 대화에서 페이지가 생기는 길이 생길 때 더한다.

고르지 않은 것:

- **대화로 `page_id` 받기**: 대화의 결과는 결과물 파일이라 페이지가 없다. 결과물 → 페이지 바꾸기를 따로 만들어야 하고, 페이지 앱의 첫 화면은 페이지를 링크로만 보인다(9.11.1). 앱 코드는 이미 버전 · 미리 보기 · 카드의 공개 승인이 있다.
- **승인 두 번** (task의 팀 만들기 설정 + blog의 앱 만들기 설정): 바뀌는 곳은 적지만 관리자가 두 번 누르고 대표가 회차를 한 번 더 돈다.
- **이벤트로 잇기** (blog가 앱을 만들고 팀을 이벤트로 부탁 → task가 만들고 → blog가 팀장을 넣음): 그사이 이어서 회차가 먼저 열려 운영 팀장 없는 앱을 볼 수 있고, 실패가 두 곳에 생긴다.
- **이어서 회차에서 받을 것 바꾸기 허용**: 검사를 피하는 길이 된다. 첫 회차에 최종 결과로 정하게 한다.

테스트: blog 설정 제안(`new_team` → 승인 → 앱 + 팀, 앱의 `agent_id` = 편집장 · 같은 결재 두 번 → 하나 · `new_team` + `agent_id` 422 · 고치기 422), 페이지 없는 페이지 앱(관리자 REST · 제안), task `teamFor`의 요청자 확인(관리자 · `SettingActor` · 다른 결재는 Forbidden), 결과 검사(비공개 앱의 앱 코드 일이 끝나면 다시 맡기지 않음), 지시문 틀 검사, 웹 만들기 시트, 화면 확인(카드의 "앱 운영 팀 새로 만들기" 줄).

순서: 2-6a 서버(platform · blog · task) → 2-6b 지시문 · 도구 설명 → 2-6c 웹 · 문서(1장 페이지 앱 · 4장 흐름 · API설계 · 기획서 결정 기록) · 확인 → main.
