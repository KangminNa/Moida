# 알림 메일 (플러그인 `email`)

콘솔의 알림(승인 요청 · 작업 실패 · 자동화 멈춤 …)을 관리자의 메일로도 보낸다 (2026-11-26, 기획서 결정 기록).
코어는 메일을 모른다: 알림이 푸시로 보내기로 정한 것마다 `platform.notice.sent`를 남기고, 플러그인이 받아 한 통씩 보낸다.

## 언제 · 무엇이 가나

- 푸시와 같은 때 · 같은 묶음이다. 콘솔 › 설정 › 알림의 조용한 시간 · 묶음 간격 · 종류마다의 경로를 그대로 따른다.
  경로가 "알림 센터만" · "끄기"인 종류는 메일도 가지 않는다. 즉시 알림이 네 개 넘게 쌓이면 "알림 n개" 한 통으로 묶인다.
- 브라우저 푸시를 켜지 않아도 메일은 간다.
- 메일에는 제목과 콘솔 링크만 싣는다. 메일은 메일 회사를 거치므로 대화의 답 같은 내용은 "알림 본문도 싣기"를 켤 때만 싣는다.
- 승인 단추는 없다. 승인은 늘 콘솔에서 한다 (원칙 7).
- 보내다 실패하면 일꾼이 다시 시도한다 (8번 실패하면 설정 › 일 › 처리 실패에 보인다). 메일 서버가 받았는데 답을 놓치면 같은 메일이 두 번 갈 수 있다.

## 자동화 결과 메일 (2026-11-27)

자동화(스케줄) 레시피의 "결과를 메일로 받기"를 켜면 그 레시피가 연 회차의 답이나 실패를 관리자 메일로도 보낸다 (기획서 결정 기록).
대화에서 "매일 아침 요약해서 메일로 보내 줘"라고 하면 대표가 `mail: true`인 레시피를 제안하고, 승인하면 켜진다. 콘솔 › 자동화의 폼에서도 켠다.

- 대화로 보내는 레시피에서만 켠다. 메일 플러그인이 꺼져 있거나 설정 전이면 켜지 못한다 (502).
- 받는 사람은 이 플러그인의 "받을 주소"(비우면 보내는 계정) 하나다. 다른 주소로 보내는 길은 없다 (전송은 원칙 7).
- 코어가 회차 작업에 `payload.chat.mail`을 싣고 최종 답 · 실패의 `task.chat.said`에 `mail: true`를 붙인다. 플러그인(`chat-said.handler.ts`)이 받아 한 통씩 보낸다.
  덧붙인 말의 답 · 검토는 보내지 않는다. 서버가 다시 맡긴 회차(받을 것이 빠짐 · 검토 반영)는 물려받아 그 답도 간다.
- 관리자가 골라 켠 것이라 "알림 본문도 싣기"와 상관없이 답(앞 3,500자)을 싣는다. 결과물 · 승인은 대화와 정리한 HTML 링크로 연다.
- 이 기능 때문에 플러그인이 `event:task.chat.said`를 더 쓴다. 이미 켜 둔 서버는 새 버전에서 플러그인을 한 번 다시 허락해야 한다.

## 가입자 소식 메일 (2026-11-27)

가입할 때 "(선택) 소식 메일 받기"에 체크한 가입자에게, 대표가 쓰고 관리자가 승인한 메일을 보낸다 (기획서 결정 기록).

- 동의: 가입 화면(스토어 `/join` · 앱의 `/_/join`)의 선택 칸(기본 해제) · 내 정보에서 켜고 끄기. 코어가 `community.accounts.news_agreed_at`에 적고 `community.account.news { accountId, agreed }`를 남긴다 (주소는 싣지 않는다)
- 받는 사람: 플러그인이 그 이벤트를 받아 서버 자신만 묻는 읽기 `news-address`(플러그인 API 0.15)로 주소를 받고 `email.subscribers`에 계정 줄(앱 없음, `account_id` · `space_id`, 바로 active)을 둔다. 동의를 끄거나 탈퇴하면 줄을 지운다
- 보내기: 대표의 MCP `mail_news_draft { request_id, subject, body }` → `email.sends`에 소식(`kind: news`, draft) → `request_approval(email.news.send, 대상 email_send, 판 1)` → 결과 카드의 "자세히"에서 제목 · 본문 · 받을 수를 보고 승인 → 그때 동의한 가입자마다 대기열 → 일꾼이 하루 상한 안에서 보낸다. 반려 · 수정 요청이면 그 초안은 취소. 콘솔의 "보내기"로는 나가지 않는다
- 메일: 제목 앞 `(광고)`, 본문 끝에 보낸 곳과 수신 거부 링크, 원클릭 해지 머리글. 해지 링크로 끊으면 줄을 지우고 `plugin.email.unsubscribed { accountId }`로 코어의 동의도 지운다
- 이 기능 때문에 플러그인이 이벤트 · 읽기 · 도구를 더 쓴다 (`event:community.account.news` · `event:task.approval.*` · `lookup:news-address` · `tool:mail_news_draft`). 이미 켜 둔 서버는 다시 허락해야 한다

## 인증코드 메일 (2026-11-26)

회원 가입 · 비밀번호 다시 정하기와 관리자 비밀번호 다시 정하기 · 로그인 메일 바꾸기의 6자리 인증코드도 이 SMTP로 나간다 (기획서 결정 기록).
코어가 코드를 만들어 서버 메모리에만 두고(10분), 플러그인이 등록한 길(`cairn.provideMail`, 플러그인 API 0.14, `uses`의 `mail`)로 바로 보낸다.
코드를 이벤트로 넘기지 않는다: outbox(DB)에 코드 원문이 남지 않게.

- 플러그인이 꺼져 있거나 보내는 계정 · 앱 비밀번호를 채우지 않았으면 코드를 보내지 못해 회원 가입을 받지 않는다 (502 "메일 플러그인 설정이 필요해요").
  이미 켜 둔 서버는 새 버전에서 `mail` 권한이 늘어 플러그인을 한 번 다시 허락해야 한다.
- 인증코드 메일도 하루 상한(`dailyMax`) 안에서 보낸다 (알림 · 소식과 따로 센다, 서버 메모리).
- Gmail은 하루 약 500통이라 회원 가입이 많아지면 Amazon SES · Resend 같은 발송 서비스의 SMTP(465)로 칸만 바꾼다.
  보내는 주소의 도메인(예: moida.ai.kr)에 SPF · DKIM · DMARC를 걸어야 스팸함으로 덜 간다.

## 메일 서버

메일 서버를 직접 띄우지 않는다. 가정용 회선은 25번 포트가 막혀 있고, 집 IP와 DuckDNS 도메인으로는 PTR · SPF · DKIM을 맞출 수 없어
보낸 메일이 닿지 않는다. 메일 회사의 SMTP에 로그인해 보낸다. 465 포트(TLS로 바로 붙기)만 쓴다.

### Gmail로 설정하기

1. Google 계정 › 보안에서 2단계 인증을 켠다.
2. 같은 곳의 "앱 비밀번호"에서 하나 만든다 (16자리). 계정 비밀번호는 넣지 않는다.
3. 콘솔 › 설정 › 플러그인 › 알림 메일(`email`)을 켜고 칸을 채운다.

| 칸 | 값 |
|---|---|
| SMTP 서버 · 포트 | `smtp.gmail.com` · `465` (기본값) |
| 보내는 계정 | Gmail 주소 |
| 앱 비밀번호 | 2에서 만든 16자리 (비밀 칸, 서버 키로 암호화) |
| 받을 주소 | 비우면 보내는 계정으로 |
| 이 Moida의 바깥 주소 | `https://…` (메일 안 링크의 앞부분) |

4. "테스트 메일 보내기"를 누른다. 명령줄은 `pnpm plugin email test`.
   로그인 거절(535)이면 앱 비밀번호를 다시 만든다. 오지 않으면 스팸함을 본다.

Gmail은 하루 약 500통까지 보낸다. 관리자 알림에는 충분하다.
배포 서버에서 `smtp.gmail.com:465`로 나가는 연결이 열려 있어야 한다.

## 코드

- `plugins/email/server/smtp.gateway.ts`: 라이브러리 없이 `node:tls`로 SMTP (EHLO · AUTH PLAIN · MAIL · RCPT · DATA · QUIT). 인증서는 Node의 기본 검사.
  587(STARTTLS)은 쓰지 않는다. 오류 글에는 메일 서버의 번호와 글만, 비밀번호는 싣지 않는다
- `mail-message.ts`: 메일 한 통. 제목은 UTF-8 encoded-word, 본문은 base64. 주소는 모양을 보고 제목은 한 줄로 만들어 머리글을 끼워 넣지 못한다
- `notice-mail.ts`: 알림 메일의 내용. 링크는 이 Moida 안의 경로만
- `notice-sent.handler.ts`: `platform.notice.sent` 하나에 메일 한 통 (일꾼, 트랜잭션 밖)
- `news.ts`: 가입자 소식 메일 (동의 맞추기 · 초안 도구 · 승인 뒤 대기열 · 반려 · 승인 화면의 읽기)
- `chat-said.handler.ts`: `task.chat.said`의 `mail: true`(메일로 받는 자동화의 최종 답 · 실패) 하나에 메일 한 통
- 테스트: `email.test.ts`가 127.0.0.1의 테스트용 SMTP 서버(`fake-smtp.ts`, TLS 없이)로 주고받기 · 로그인 거절 · 받는 사람 거절을 본다.
  코어 쪽은 `push.api.test.ts`가 보내기로 정한 알림마다 이벤트가 한 번 남는지 본다

## 앱 소식 구독 (2026-11-26)

방문자가 스토어 화면(`/` · `/store`)의 "새 글을 메일로 받기"에서 앱을 골라 구독한다.

1. 앱 · 메일 주소 · 동의 → `POST /api/p/email/subscribe` (곳마다 시간당 10번). 답은 늘 "확인 메일을 보냈어요"라 주소가 이미 있는지 드러나지 않는다
2. 일꾼(`deliver`, 30초마다)이 확인 메일을 보낸다: 링크는 `/store?mail=confirm&token=…`
3. 링크를 열면 확인 단추가 보이고, 눌러야 구독된다 (`POST …/confirm/:token`). 메일 보안 검사기가 링크를 미리 열어도 바뀌지 않는다. 확인하지 않은 신청은 7일 뒤 지운다
4. 앱의 글이 공개되면 소식이 생긴다 (`blog.post.published`, 구독자가 있는 공개 앱만, 글 하나에 한 번)
5. 관리자가 콘솔 › 운영 › 메일 구독에서 **보내기**를 눌러야 지금 구독 중인 사람들에게 나간다 (원칙 7). 일꾼이 하루 상한(`dailyMax`, 기본 300통) 안에서 천천히 보낸다
6. 메일마다 해지 링크(`/store?mail=unsubscribe&token=…`)와 원클릭 해지 머리글(`List-Unsubscribe`, RFC 8058). 해지하면 구독 줄을 바로 지운다 (원칙 2 예외: 해지한 구독자의 주소)

- 구독 칸은 설정의 "스토어에 구독 칸 보이기"를 켜고 메일 설정이 갖춰져야 보인다
- 열쇠(token)는 한 번의 신청에 하나, 그 신청의 앱들이 함께 쓴다. 메일마다 해지 링크에 넣어야 해서 그대로 저장한다 (새어도 할 수 있는 일은 그 구독의 확인 · 해지뿐)
- 보내다 실패한 메일은 다시 보내지 않는다 (잡은 채 10분이 지나면 실패로). 오류 글에 든 메일 주소는 지운다
- 표: `email.subscribers` · `email.sends` · `email.deliveries` (`plugins/email/migrations`)
- 코어는 플러그인 API 0.13만 더했다: `work.lookup('app' | 'app-id' | 'app-url')`(공개 앱의 이름 · 주소 → id · 바깥 주소), 반복 작업의 `run(own)`(자기 동작을 서버 자신으로: 잡기 → SMTP → 적기), 웹 자리 `store.after`
- Gmail로도 보낼 수 있다 (하루 약 500통). 구독자가 많아지면 자기 도메인과 발송 회사(SPF · DKIM)로 바꾼다

## 정하지 않은 것
